# Разработка и стандарт интерфейсов NaPare

## Выбор объёма работы

Маленькая правка: уточнить ожидаемый результат по запросу → прочитать правила и соседний код → выполнить минимальное изменение → запустить затронутую проверку → сообщить результат и границы. Не вызывать полный набор Skills, MCP, субагентов и сборок ради текста или изолированного исправления.

Существенная задача проходит следующий цикл; пропущенный этап получает конкретное объяснение, а не вымышленный результат.

1. Зафиксировать пользовательский сценарий, роли, ограничения и критерии приёмки.
2. Проследить текущий код и найти существующую реализацию. Проверить source cards и модульную документацию.
3. Спроектировать изменение с границами API, данных и совместимости; для сложного решения написать ADR.
4. Сверить документацию с реальными версиями зависимостей через Context7 или официальный первичный источник. Не отправлять приватный код без необходимости.
5. Подготовить план, команды проверки и владение файлами. Параллелить только независимые области.
6. Для UI согласовать композицию с задачей, реальным контентом и токенами NaPare; проверить реальный API до создания новых компонентов.
7. Реализовать минимальный завершённый сценарий с типизацией, обработкой ошибок и серверными правами.
8. Добавить содержательные regression tests для нового поведения, затем запустить затронутые тесты. Избегать тестов, повторяющих реализацию.
9. Проверить изменённые интерфейсы в реальном браузере через Playwright: mobile/desktop, авторизованные роли, loading/error/empty, клавиатура. Синтетические fixtures маркировать явно.
10. Через Chrome DevTools проверить console, network и производительность на сценарии. Сравнивать измерения в одинаковых условиях; не выдавать один Lighthouse балл за полную оценку.
11. Проверить права, tenant boundaries, DTO, утечки в errors/logs/analytics, зависимости и хранение локальных данных. Проверять и успешный, и запрещённый доступ.
12. Провести review diff, API контракта, миграций, UI состояний и проверок; для независимого review дать агенту только diff и релевантный контекст.
13. Исправить выявленные проблемы и повторить только связанные проверки.
14. Завершить lint, typecheck, affected build и необходимые интеграционные проверки. Ошибка окружения остаётся ограничением, а не успешной сборкой.
15. Обновить docs и передать список изменений, команды с результатами, оставшиеся пробелы. Push/deployment требуют авторизации пользователя.

## Команды и доказательства

Из корня: `pnpm lint`, `pnpm typecheck`, `pnpm build`. Для области: `pnpm --filter @napare/backend exec tsc --noEmit`, `pnpm --filter @napare/web-student exec tsc --noEmit`, `pnpm --filter @napare/web-student build`; заменить имя на затронутое приложение. Backend unit: `pnpm test:unit`; backend E2E: `pnpm test:e2e` только с отдельным тестовым окружением, не с рабочей БД.

Backend script `lint` содержит `--fix`; для проверки без мутаций использовать корневой `pnpm lint`. `git diff --check` проверяет формат diff. Документация: `pnpm lint:docs`; структура DevKit: `node scripts/ai-devkit/verify.mjs`. Историческая команда `scripts/verify-ai-documentation.cjs` в этом checkout отсутствует и не должна заявляться как выполненная. Существующий CI в `.github/workflows/ci.yml` выполняет lint/typecheck/unit/E2E; отчёт локального агента не заменяет результаты CI.

Для текущей задачи DevKit проверять конфиги, discovery Skills, реальный запуск доступных MCP, installer повторно, отсутствие секретов и diff. Полная продуктовая E2E или redesign не являются результатом установки инструментария.

## Цикл проверки изменений

Общий сценарий для `napare-qa` и `napare-code-review`, адаптированный из [ECC verification-loop](../../scripts/ai-devkit/skill-adapters/ecc/upstream/verification-loop.md). Выбирайте применимые проверки по характеру изменения и [руководству по тестированию](../ops/testing.md).

1. **Сборка.** При изменении приложения или его сборочного контракта запустите build затронутого workspace. Для документации и инструкций DevKit проверяйте Markdown и структуру DevKit.
2. **Типы.** Выберите охват typecheck по изменённым пакетам и потребителям общего контракта. Используйте команды из раздела выше.
3. **Линт.** Для продукта используйте корневой `pnpm lint`, для документации — `pnpm lint:docs` или целевой Markdownlint. Review-only требует проверок без перезаписи исходников.
4. **Тесты.** Проверяйте изменённый сценарий и необходимые регрессии. Для прав проверьте разрешённый доступ и корректный отказ чужому tenant на синтетических данных. Браузер, PostgreSQL, Docker и Android проверяйте по применимости отдельно. Coverage приводите по фактически запущенному набору и правилам проекта.
5. **Безопасность.** Сверьте права, границы данных и затронутые зависимости. Результат поиска секретов фиксируйте только как путь, номер строки и тип совпадения, без фрагмента значения или полного вывода сканера.
6. **Diff и отчёт.** Сверьте фактический base/head или снимок рабочего дерева, включая незастейдженные и новые файлы в области задачи. Выполните `git diff --check` и проверьте пробелы в новых файлах отдельно. Для каждой проверки укажите команду или сценарий, окружение, наблюдаемый статус и причину пропуска. Deployment и production подтверждайте отдельно по конкретному окружению и только в рамках разрешённого доступа.

Для каждой выполняемой команды сохраняйте её реальный код завершения перед фильтрацией вывода. Отделяйте ошибки, вызванные изменением, от уже существовавших и ограничений окружения.

## Единый UI стандарт

Приоритеты: явное задание пользователя → `AGENTS.md` и контракты NaPare → существующие `packages/design-tokens` и `packages/ui` → подтверждённый Figma макет → профильный `napare-*` Skill → выбранные рекомендации vendor Skills. Внешний Skill не вправе переименовать бренд, добавить вымышленных клиентов/метрики или заменить стек проекта.

| Источник | Использовать для | Как разрешать конфликт |
| --- | --- | --- |
| UI/UX Pro Max | Поиск UX паттернов и анализ читаемости | Не генерировать новую палитру поверх semantic tokens NaPare |
| Impeccable | Критика композиции, плотности, типографики и состояний | Исправлять подтверждённую проблему конкретного экрана; не применять массовый редизайн без задания |
| Taste Skill | Визуальный ритм, выразительная композиция, избегание шаблонов | Общий компонент и бренд важнее предпочитаемого автором эффекта или стека |
| Anthropic Frontend Design | Осмысленная композиция и работа с реальным контентом | Не добавлять декоративные анимации и сторонние шрифты без причины; учитывать existing Inter/token scale |
| Figma MCP | Чтение разрешённого макета, assets и размеров | Сопоставлять с существующими компонентами; конфликт поведения уточнять по API и задаче |
| Vercel Skills | React/Next rendering и performance patterns | Проверять совместимость с Next 15.5 и React 18; не переносить API новых major версий автоматически |

Перед изменением экрана: определить основное действие и иерархию данных; найти текущие tokens, layout и navigation; перечислить реальные loading/error/empty/success states. Использовать общие button/input/RequestState patterns и существующий стиль карточек. Уменьшать визуальный шум; цвет должен кодировать смысл. Анимации добавлять для обратной связи, поддерживать reduced motion.

Критерии интерфейса: читаемые заголовки и текст, последовательные отступы и сетка, ясная навигация, реальный работающий CTA, отсутствие горизонтального overflow на проверенной мобильной ширине, keyboard focus, доступные labels и ошибки, достаточный контраст. Сверять статусные цвета с semantic tokens; успех/ошибка не должны зависеть только от цвета.

## Параллельная работа и контекст

Владелец задачи задаёт агенту цель, ограниченный список файлов, ссылки на контракты, обязательные проверки и формат результата. Backend API и общий клиент меняются согласованно; два агента не редактируют один lockfile или shared UI одновременно. Интегратор проверяет итоговый diff и фактические тесты. Прочитанная инструкция не является проверкой работоспособности агента.

Hooks не должны автоматически запускать миграции, удаление файлов, `--fix`, публикацию или установщики. Обязательные проверки выполняются видимыми воспроизводимыми скриптами/CI, а не обещанием в prompt. Недоступный MCP можно заменить разрешённым локальным инструментом с явной границей доказательства.

## Опциональная подсказка для ECC

Для работы над интеграцией можно запустить `codex -C docs/ecc` из корня NaPare. В доверенном проекте Codex обнаруживает [локальный SessionStart](../ecc/.codex/hooks.json) для старта и возобновления сессии. Откройте `/hooks`, проверьте команду и [обработчик](../../scripts/ai-devkit/ecc-session-start.mjs), затем при необходимости подтвердите этот hook. Из корня проекта такой запуск не требуется, а протокол AGENTS.md применяется в любом случае.

Обработчик проверяет наличие требований, плана и прогресса и возвращает короткую подсказку со ссылками. Для отключения снимите доверие или отключите только этот обработчик в `/hooks`. Статус RTK в корневом локальном `.codex/hooks.json` относится к отдельной настройке.

Из корня проекта эти команды воспроизводят офлайн-проверки ECC из [DevKit workflow](../../.github/workflows/ai-devkit.yml). На runner команда Python вызывается как `python`.

```powershell
node scripts/ai-devkit/verify.mjs
py scripts/ai-devkit/install-ecc-references.py --check
node --test scripts/ai-devkit/ecc-session-start.test.mjs
```

## Контекст Codex

Для новой задачи начните с AGENTS.md, области из руководства разработчика и одного профильного Skill. Подключайте дополнительные источники и MCP по мере появления конкретного вопроса. Для независимого поручения передавайте пути, ожидаемый результат и относящиеся к задаче выдержки. Для проверки ECC перечитывайте три документа состояния, а доказательства открывайте по ссылкам на нужный этап.

В отдельном сеансе CLI ненужный MCP можно скрыть параметром запуска, например `codex -c mcp_servers.playwright.enabled=false` для проверки документации. Применяйте override к уже настроенному серверу. Команда действует в пределах запуска.

Сопоставляйте `skills/list`, `mcpServerStatus/list` и `turn.completed.usage` отдельно. Первые два показывают обнаруженные возможности. Usage относится к конкретному прогону и зависит от вызовов инструментов и кеша. [Каталог Skills и его бюджет](https://learn.chatgpt.com/docs/build-skills).
