# Мастер подключения вуза

Дата: 22 октября 2026. Тип: инструкция владельцу платформы и администратору вуза. Адрес: `/deanery/onboarding`, ссылка находится в содержимом настроек университета. Navigation/header/Avatar/logo и student-приложение не изменяются.

## 1. Владелец создаёт вуз

Дополнение 24 октября: администратор на шаге проверки готовности отдельно получает серверное подтверждение для [аналитики времени подключения](product-analytics.md). При выключенном сборе маркер не сохраняется. Ошибка измерения не отменяет загруженный checklist; повтор безопасен. Это не юридическое или эксплуатационное подтверждение готовности.

Войдите учётной записью владельца платформы и откройте мастер. Введите название и город; новая запись создаётся со статусом `pending`. Можно выбрать существующий вуз и продолжить настройку. Только наличие роли developer/superadmin без статуса владельца не разрешает создание вуза.

Используются существующие `GET platform/access`, `GET/POST platform/universities`. В мастере нет автоматической активации и переноса чужого вуза в текущую сессию. Если ответ создания потерян, кнопка повторного создания блокируется до обновления списка: проверьте, не появилась ли запись. Существующий POST университета не поддерживает ключ идемпотентности; мастер этого свойства ему не приписывает.

## 2. Факультеты и группы

Добавьте факультет с названием/кодом, затем его группы с курсом 1–12. Название группы должно совпадать с файлом расписания. Данные читаются со всех страниц API. Сбой загрузки не показывается как отсутствие факультетов или аккаунтов и не разрешает слепо создавать первый аккаунт.

Владелец использует `platform/organization/faculties` и `platform/organization/groups` с выбранным universityId. Администратор продолжает только свой вуз через `admin/faculties` и `admin/groups`. Соответствие факультета вузу и scope проверяет backend. Сохранённые шаги не откатываются при закрытии страницы; продолжение выполняется по существующим данным. Черновики полей не сохраняются в localStorage.

## 3. Первый администратор

Владелец создаёт `university_admin` через существующий `POST platform/accounts`, указывая выбранный вуз. Нужны ФИО, email и начальный пароль от 12 символов; backend дополнительно ограничивает пароль 72 байтами UTF-8. Пароль остаётся только в состоянии формы и очищается после успешного ответа. В URL, storage и журнал мастера он не записывается. Письмо/приглашение автоматически не отправляется.

После создания мастер показывает существующего администратора. Пароль передайте защищённым способом. **Далее этот администратор входит в собственный аккаунт** и открывает тот же мастер: текущие admin API импортируют только в вуз JWT-сессии. Мастер не выполняет impersonation, не меняет основную роль владельца и не расширяет его campus-контекст ради импорта.

## 4. Первое расписание

Войдя администратором нового вуза, откройте шаг импорта. Форматы: CSV, JSON, ICS, XLSX, Moodle, СИБИТ. Для файла нужны непустые данные до 2 МиБ; XLSX передаётся base64. Укажите постоянное имя источника и смещение времени вуза от UTC. По умолчанию поле содержит `+06:00`; для своего вуза проверьте его вручную.

Точный формат, стабильные ID, UTC/ограниченные RRULE ICS и требования Moodle/SIBIT описаны в [инструкции импорта](../integrations/schedule-import.md). Для ICS можно выбрать группу и номер пары по умолчанию. Moodle и СИБИТ требуют заранее настроенного коннектора; произвольный URL/токен в импорте не принимаются.

Кнопка отправляет `POST admin/schedule/upload` с `queued=true` и UUID idempotencyKey. При повторе неизменённого намерения в открытой форме используется прежний ключ. Новый файл/параметры создают новый ключ. Проверка адаптером происходит на сервере до постановки; применение — фоновым worker. Отсутствующие занятия не удаляются: `replace` здесь не включается.

Мастер опрашивает `GET admin/schedule/imports/:id`, показывает queued/processing/completed/failed, причину ошибки и реальные imported/updated/deleted/unchanged. При ошибке чтения автопросмотр останавливается до повторного запроса. ID последнего полученного задания сохраняется в sessionStorage отдельно по actorId/universityId для восстановления вкладки; payload, файлы, пароль и токены этот механизм не сохраняет.

Если запрос создания потерян до получения jobId, повторите ту же открытую форму с прежним намерением. После перезагрузки без полученного ID эта гарантия не сохраняется; существующий журнал/источник следует проверить до нового импорта. Если queued не меняется, проверяется worker на сервере; мастер не сообщает «импорт завершён» по успешной постановке.

## 5. Готовность и преподаватели

Выберите период от 1 до 32 дней и смещение времени вуза, затем выполните проверку. Локальные границы суток преобразуются в точные ISO instants для существующего `/schedule/range`, чтобы занятия возле полуночи не пропадали из дня. Читаются все страницы факультетов, групп, пользователей и расписания. Проверяется:

- название и город;
- наличие факультетов и групп;
- хотя бы одно занятие каждой группы **в выбранном периоде**;
- связь каждого полученного занятия с активным аккаунтом `teacher`;
- действующий `university_admin`.

При ошибке любого запроса результат готовности не вычисляется. Смена периода сбрасывает результат и отменяет незавершённый запрос. Полный список проблемных групп и страницы по 20 непривязанных занятий доступны в интерфейсе.

Для сохранённого занятия можно явно выбрать своего преподавателя и применить существующий `PATCH schedule/:id`. Это конкретная ручная связь, без сопоставления ФИО. Автор/основание попадают в существующую историю изменения занятия. Если аккаунта нет, создайте его в разделе пользователей. Для внешнего виртуального занятия СИБИТ мастер направляет к связи sourceTeacherId в пользователях и синхронизации; такие ID не отправляются как UUID локального занятия.

«Учебная настройка готова» относится только к проверенным данным и периоду. Нельзя переносить её на весь семестр, фактическое качество источника, документы по ПД, нагрузку, backup, TLS или production readiness. Администратор не получает право активировать вуз или менять инфраструктуру этой кнопкой.
