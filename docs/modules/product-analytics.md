# Продуктовая аналитика своего вуза

Дата: 24 октября 2026. Тип: контракт реализации в ветке `codex/p3-product-analytics`. Читатель: администратор вуза и оператор платформы. Это встроенный аналог базовой продуктовой аналитики на PostgreSQL; внешний PostHog, cookies, запись экрана и отправка данных третьим лицам не подключаются. Production не изменяется. Блок ещё проходит итоговые проверки.

## Открыть показатели

Страница `/deanery/analytics` доступна по ссылке в содержимом настроек университета. Администратор задаёт начало семидневной недели UTC и включительные даты семестра продолжительностью 14–210 дней. Backend выбирает вуз из проверенной сессии; параметра выбора чужого вуза нет. Студенты, преподаватели, работодатели и технические роли не получают этот отчёт.

`GET /api/v1/analytics/report` принимает `weekStart`, `semesterStart`, `semesterEnd` в формате `YYYY-MM-DD`; невозможные даты отклоняются. Ответ `no-store, private` содержит десять агрегатов, определения, числители/знаменатели, границы периода и ограничения. Данные читаются в одном read-only repeatable-read снимке. Имена, тексты событий, список пользователей и индивидуальные дневные записи в отчёт не входят.

При ошибке экран сохраняет введённые даты и позволяет повторить чтение. Смена сессии отменяет запрос и очищает отчёт. Есть отдельные состояния загрузки, ошибки, отключённого сбора и отсутствия данных. Общие navigation/header/Avatar/logo и student-приложение не меняются.

## Определения десяти метрик

| Показатель | Расчёт и источник |
| --- | --- |
| Возврат студентов к концу семестра | Среди наблюдаемых активных студентов первых 7 дней семестра — доля активных в последние 7 дней. Источник: `product_activity_days`; окна не пересекаются |
| Активные аккаунты за неделю | Уникальные аккаунты с измеряемым успешным API-запросом в 7 сутках UTC. Не количество просмотров и не время за экраном |
| Доля активных студентов | Активные студенты недели, которые сейчас действуют в своём вузе, / текущие действующие студенты. Исторический состав не восстанавливается |
| Наблюдаемое время подключения | Часы от `universities.createdAt` до первой успешной серверной проверки готовности. Не длительность непрерывной работы администратора |
| Доля операций отметок через QR | Сумма `records` в событиях `attendance.updated` с `source=qr` / сумма с известным `source=qr/manual`. Повторное ручное сохранение — новая операция; это не уникальные студенты |
| Опубликовано заданий | Число событий `homework.created` за неделю; содержимое задания не возвращается |
| Успешные импорты | `completed` / (`completed` + `failed`) по `schedule_import_jobs.updatedAt` за неделю. Ожидающая очередь не входит |
| Заявления закрыты в срок | Закрытые за неделю заявления с `closedAt <= dueAt` / закрытые заявления с известным сроком. Источник: `student_requests` |
| Принято работ в недельной когорте | Работы, созданные за неделю и сейчас находящиеся в `accepted`, / все работы той же когорты. Привязка к вузу — через задачу. Не показатель оплаты/трудоустройства |
| Группы с расписанием | Текущие группы с неудалёнными занятиями, начинающимися в выбранную неделю, / все текущие группы своего вуза. Границы начала совпадают с API расписания |

Пустой знаменатель возвращает `value: null`, а наблюдаемый ноль при ненулевом знаменателе — `0`. Удержание не вычисляется до завершения семестра, при отсутствии начальной когорты, начале сбора позже семестра или выходе за срок хранения. Дата начала наблюдений не доказывает непрерывность сбора: отключение, простой сервера и ошибки записи не восстанавливаются. Старые события посещаемости без канала исключаются из знаменателя QR; число таких записей показывается отдельно. Неполная неделя/история маркируется.

Когорта и окно возврата соответствуют общему подходу [PostHog retention](https://posthog.com/docs/product-analytics/retention), но формулы и реализация этого модуля принадлежат НаПаре; совместимость со всем PostHog API не заявляется.

## Как собирается активность

Глобальный HTTP interceptor после успешного ответа 2xx записывает не более одной строки на `(вуз, аккаунт, день UTC)`. Роль фиксируется при первой записи дня. Измеряются разделы schedule, pair-space, my-day, absences, academic, requests, career и admin. Анонимные запросы, auth refresh, notifications, event streams, self export/privacy и сама аналитика не измеряются. Технические роли и employer исключены. Запрос интерфейса может быть автоматическим: факт API-активности не доказывает внимание человека.

URL, IP, user agent, поисковая строка и тело запроса не сохраняются. Ошибка аналитики не отменяет успешное бизнес-действие. Невыполненный/запрещённый запрос не создаёт активность. Старые дневные записи очищаются при запуске и раз в час для явно настроенных вузов; задача не получает доступ к остальным вузам.

## Зафиксировать готовность подключения

Мастер подключения после явного нажатия «Проверить готовность» вызывает `POST /api/v1/analytics/onboarding-observation` с ISO `startDate/endDate`, периодом до 32 дней. Backend независимо от клиентских флажков проверяет заполненные название/город, наличие факультета и групп, действующего администратора, занятия каждой группы в выбранном периоде и действующих преподавателей всех таких занятий. Первый успешный момент и проверенный период сохраняются; повтор не переносит начало метрики. Отказ аналитики не уничтожает загруженный список проверки. При отключённом сборе наблюдение не записывается.

Это первое наблюдение готовности для выбранного периода, а не утверждение, что вуз полностью готов по юридическим, эксплуатационным или всем учебным требованиям.

## Настроить оператору

Сбор по умолчанию отключён. После утверждения целей, основания/срока хранения и информирования пользователей оператор задаёт в окружении backend:

```text
PRODUCT_ANALYTICS_ENABLED=true
PRODUCT_ANALYTICS_UNIVERSITY_IDS=<UUID своего пилотного вуза>,<другой явно разрешённый UUID>
```

Пустой список не разрешает ни одного вуза; wildcard и невалидные UUID запрещены. Изменение конфигурации требует перезапуска backend. Отключение `PRODUCT_ANALYTICS_ENABLED` останавливает новые записи, но очистка просроченных дневных данных продолжается для сохранённого списка UUID. Удаление UUID из списка и простой backend останавливают эту очистку: оператор контролирует её выполнение. Автоматические удаления по времени относятся к дневной продуктовой активности старше 400 дней, а не к учебному архиву и не к `event_records`.

Новые таблицы `product_activity_days` и `product_analytics_state` защищены FORCE RLS и четырьмя restrictive policies; отдельные self-export/erasure capabilities ограничены собственными строками. Это соответствует механике [PostgreSQL RLS](https://www.postgresql.org/docs/current/ddl-rowsecurity.html). Миграция 41 не допускает автоматического разрушительного rollback истории; требуется отдельная архивная миграция.

Дневная активность входит в собственный JSON export и физически удаляется при self deletion, включая предыдущий вуз. Чужие строки остаются. Неизменяемый маркер удалённого аккаунта не допускает запоздалой записи с прежней сессией. Агрегаты после удаления могут измениться. Сведения о вузе и первой проверке готовности не содержат идентификатора администратора и сохраняются.

## Проверки и ограничения

Прошли 16 focused policy unit-сценариев и 5 unit-сценариев HTTP interceptor; полный backend — 46 suites/492 tests. Исправлена изоляция старой notification fixture: mock quiet-hours сбрасывается перед каждым тестом, поведение сервиса не менялось. Guard matrix — 4568 probes; inventory — 369 маршрутов. Backend/admin typecheck, root lint, docs и guards прошли.

Все 9 настоящих JWT/HTTP/PostgreSQL сценариев прошли повторно после последних серверных правок: default-off/allowlist, FORCE RLS, успешная активность/дедупликация/исключение ошибок, роли и чужой вуз, десять расчётов с известными числами, незавершённый семестр/пустая когорта, первая готовность, scoped очистка 400 дней при отключённом сборе, export/delete и запрет запоздалой записи. Нулевой интервал проверки готовности отклоняется. Фикстуры синтетические, роль PostgreSQL — NOSUPERUSER/NOBYPASSRLS.

Реальный браузер Next/Nest/PostgreSQL проверил 10 карточек, известные retention=50% и QR=25%, четыре ширины 320/768/1024/1440 без переполнения; scoped axe — 0 violations/0 incomplete, page errors отсутствуют. Дополнительно прошли серверное наблюдение готовности через мастер и появление длительности подключения, HTTP 400 при коротком семестре с сохранением дат, восстановление после исправления и очистка отчёта при настоящем межвкладочном storage event. После обновления страницы данные снова загружаются. Скриншоты просмотрены. Это проверка указанных состояний, не полное подтверждение WCAG AA.

[PR 24](https://github.com/DeminLab/NaPare/pull/24) опубликован. Первый завершённый CI 125 подтвердил Linux build/typecheck/lint/unit; общий E2E потребовал явную классификацию `product_analytics_state` в каталоге self-export. Таблица хранит общие даты вуза без account/actor reference, поэтому исключена из личных наборов; собственные `product_activity_days` остаются в export. После исправления все пять личных HTTP/PostgreSQL export-сценариев локально прошли, включая полную проверку metadata. Отдельные high dependency advisories исправляются патчем PR 25. Повторный CI и интеграция ещё не подтверждены. Реальные вузы, непрерывность сбора в production, утверждение политики и эксплуатация не подтверждены.
