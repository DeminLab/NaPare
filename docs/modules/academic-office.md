# Учебный офис и заявления

Статус: текущая реализация ветки `codex/p1-academic-office`, 22 октября 2026; production не изменялся. Основа: [утверждённая модель](../product/academic-office-requests-model.md). Читатель: администратор вуза, учебный офис и сопровождающий backend.

## Подготовить рабочее место

Откройте «Настройки университета → Учебный офис: заявления и согласования». Прямой адрес — `/deanery/requests`. Navigation, header, Avatar и logo не изменяются. Страница использует существующий кабинет вуза; каждый запрос проверяется backend независимо от наличия ссылки в интерфейсе.

1. В настройках учебного офиса назначьте действующим сотрудникам обязанности `office`, `methodologist` или `dispatcher`. Основная роль аккаунта сохраняется.
2. Выберите факультеты и/или группы. Списки объединяются; пустые оба списка означают отсутствие доступа. Диспетчерское назначение не открывает заявления автоматически.
3. Для подачи сотрудником от имени студента отдельно включите разрешение у обязанности `office`. Сам по себе доступ администратора к настройкам этого разрешения не даёт.
4. Назначьте декана в существующем разделе факультетов. Для последней стадии нужен действующий `faculty_dean`, указанный именно у факультета заявления.
5. При необходимости задайте маршрут конкретной группы и типа заявления. Отсутствие: офис → активный куратор группы или декан; перевод/пересдача: офис → методист → декан. Ответственные проверяются при настройке, подаче и каждом решении.

Без отдельного маршрута выбираются первые подходящие действующие назначения, затем куратор/декан. Порядок стабилен по времени назначения и UUID; неоднозначные кадровые решения лучше закрепить явным маршрутом. Для кураторской стадии сохраняется существующая модель дополнительных назначений, включая студента-куратора чужого заявления. Согласование собственного обращения запрещено. Назначение на обязанности офиса/методиста/диспетчера студенту не выдаётся.

Срок маршрута задаётся в календарных днях от подачи: по умолчанию 5 дней на стадию, настраивается от 1 до 90. Это локальная настройка очереди, а не заявление о нормативном сроке. Уточнение и смена ответственного не обнуляют прежние сроки и решения.

## Провести заявление

Типы: отсутствие, перевод, пересдача. Студентский self API создаёт только свои заявления; student UI этого выпуска не меняется. Уполномоченный офис выбирает группу и студента, создаёт черновик и подаёт его отдельным действием. Авторство оператора сохраняется отдельно от заявителя. Черновик виден студенту и действующему автору-оператору; администратор не получает чужие черновики автоматически.

После подачи офис принимает заявление. Решение принимает текущий согласующий; будущий этап нельзя завершить раньше предыдущего. Можно запросить уточнение с причиной, вернуть дополненное заявление в подачу, отказать, отозвать до решения и закрыть завершённое обращение с основанием/реквизитами результата. Пользователь видит только действия, доступные по текущему назначению. Повторная проверка при исполнении защищает от отозванных после открытия карточки назначений.

Смена исполнителя доступна офису своего подразделения только для незавершённого этапа. Новый сотрудник должен подходить для его обязанности. Версия маршрута заявления увеличивается; история хранит прежнего и нового согласующего, стадию, автора и основание. Изменение шаблона группы влияет только на будущие подачи.

Решение не меняет группу, оценку, LMS или официальный приказ автоматически. Реквизиты результата — текст, не произвольная ссылка для скачивания. Реестр задолженностей сообщает об отсутствии подтверждённого источника и возвращает `records: []`, `source: null`, `available: false`; вымышленных оценок нет. Семестровый Moodle-обзор остаётся отдельной задачей P2-1.

## Права и данные

- Все шесть таблиц имеют scalar `universityId`, ENABLE/FORCE RLS и обязательные политики из миграции 29. Новые миграции 31/32 устанавливают их до запуска приложения.
- Офис читает заявления своего scope; методист и куратор — только назначенные им этапы при действующей обязанности. Декан ограничен своим факультетом и назначенным этапом; администратор контролирует поданные заявления своего вуза и настройки.
- Техническая роль сама по себе не даёт доступа. Отдельный межвузовский технический API в этом модуле не вводится; прямые запросы без разрешённого назначения отклоняются. Это не заменяет существующую систему сохранённых platform grants.
- Диспетчер получает отдельную выборку сохранённых занятий назначенных групп. Для teacher/curator дополнительное назначение разрешает PATCH времени и места через существующий schedule API. Свежая проверка scope, обязательное основание, формат времени и положительная длительность до суток сохраняются на сервере. Перенос группы/преподавателя/источника и удаление чужого занятия этим назначением не разрешаются. Первичные права остальных ролей не расширяются и не отзываются.
- Назначения доступны штатным учебным ролям teacher, curator, faculty_dean, department_head, university_admin. Career-аккаунты сохраняют существующее ограничение career-разделом в JWT guard; employer/student и технические роли через настройки офиса не назначаются.
- Документы принимаются как UUID существующих незаблокированных `file_attachments`, загруженных самим студентом и связанных с PairSpace его вуза. Произвольные URL запрещены. В карточке возвращаются метаданные связи, без URL файла и без обхода разрешений исходного раздела. Специального медицинского файлового реестра нет.
- Общий audit содержит IDs, действие, статусы, версии и изменения назначения. Текст заявления и документов туда не копируется. Решения доступны в истории заявления; API редактирования/удаления истории не существует.
- Команды используют `version` и UUID `idempotencyKey`. Одинаковая команда возвращает прежний ответ; изменённое содержимое с прежним ключом даёт 409. Создание черновика тоже идемпотентно. Одинаковое действующее назначение повторно не дублируется; revoke сохраняет запись.
- Транзакционная advisory-блокировка по вузу упорядочивает office grant/revoke, настройки маршрутов и решения; строка заявления блокируется дополнительно. Списки получают scope пакетно, без SQL-запроса для каждой группы/стадии.

## API

Все пути ниже начинаются с `/api/v1/requests`, требуют JWT и привязки к вузу. Проверки администратора и назначений находятся в сервисах, поэтому JWT-допуск из общей role matrix не означает разрешение бизнес-операции.

| Метод / путь | Назначение |
| --- | --- |
| `GET context` | Действующие назначения, доступные группы/факультеты, ответственные и состояние источника задолженностей |
| `GET dispatch/lessons` | Сохранённые занятия группы, назначенной диспетчеру; даты и pagination |
| `GET candidates` | Поиск сотрудников для настроек; с groupId — согласующие группы для офиса |
| `GET students?groupId=UUID` | Студенты для явно разрешённой подачи оператором |
| `GET students/:id/debts` | Явное пустое состояние неподключённого источника |
| `GET/POST assignments`, `DELETE assignments/:id` | Назначить/отозвать обязанность; только администратор своего вуза |
| `GET/PUT routes` | Шаблоны групп, optimistic version; только администратор |
| `GET /`, `GET report` | Пагинация и фильтры типа/статуса/группы/факультета/ответственного/просрочки/названия |
| `POST /` | Черновик с ключом идемпотентности |
| `GET :id` | Заявление, доступные действия, этапы, история и связи документов |
| `POST :id/commands` | submit, accept, needs_changes, revise, approve, reject, withdraw, close, reassign |

CSV в интерфейсе выгружает только текущую страницу отфильтрованной очереди; это явно указано в кнопке и имени файла. Полная выгрузка всех страниц этим действием не заявляется. Описание и содержимое документов в CSV не включаются.

## Проверить изменение

```powershell
pnpm --filter @napare/backend exec jest --config ./test/jest-e2e.json --runInBand requests.e2e-spec.ts
pnpm --filter @napare/backend exec tsc --noEmit
pnpm --filter @napare/web-admin exec tsc --noEmit
node scripts/security-route-inventory.cjs --check
node scripts/verify-ai-documentation.cjs
node scripts/verify-role-workspace-boundaries.cjs
pnpm lint
pnpm lint:docs
```

Для E2E нужен `OFFICE_TEST_DATABASE_URL` новой локальной БД с именем `curation_test_*`, runtime-роль без SUPERUSER/BYPASSRLS. Suite применяет настоящие миграции 31/32 к пустым feature-таблицам, затем проверяет HTTP/JWT/services/PostgreSQL: два вуза, два факультета, foreign IDs, приватность черновика, отзыв назначения на живой JWT, dispatcher/method scope, самоодобрение, конкуренцию, идемпотентность, уточнение/смену исполнителя, версии маршрута, отсутствие источника задолженностей и student-curator. Удаление feature-таблиц разрешено только в disposable fixture; это не инструкция для production.

Оператор перед развёртыванием согласует реальные подразделения, сроки, состав документов и подписанта результата. Реальные сотрудники, юридическое оформление решений и production в локальных проверках не участвовали.

Локальная приёмка 22 октября: 14 PostgreSQL/HTTP сценариев модуля прошли; Playwright проверил настоящий Next → Nest → PostgreSQL на синтетических аккаунтах, включая клавиатуру, retry, CSV, согласование, создание оператором, настройки маршрута и диспетчерские изменения на 320/768/1440 px. `next build` скомпилировал `/requests` и статические страницы с кодом 0; Windows выдал EPERM при копировании symlink в standalone. Это не подтверждает готовность Windows standalone-пакета; Linux-сборка проверяется отдельно в CI.
