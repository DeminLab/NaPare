# Проект ТЗ: система сопровождения учебного дня

Дата: 22 октября 2026. Заказчик: **[ЗАПОЛНИТЬ]**. Версия/commit поставки: **[ЗАПОЛНИТЬ после приёмки кандидата]**. Это функциональная заготовка на основе репозитория; поля в квадратных скобках не являются согласованными условиями.

## Предмет и объём

Предоставление доступа к системе сопровождения учебного дня, настройка и сопровождение для одного учебного заведения. Конкретную правовую форму доступа, срок и состав услуг определяет договор. Доступ студентов включён в закупаемый вузом объём. Исключительные права не передаются этим проектом.

| Поле заказчика | Что заполнить до расчёта цены |
| --- | --- |
| Срок и этапы | Начало/окончание доступа, сроки подготовки и опытной эксплуатации |
| Объём | Студенты, сотрудники, группы, филиалы, максимальные одновременные подключения |
| Модули | Обязательное ядро; отдельные опции; модули, исключённые из поставки |
| Источники | Форматы расписания, версия Moodle/права API, идентификаторы и ответственные |
| Размещение | Площадка РФ или инфраструктура заказчика, подтверждённые адреса/операторы/резервные копии |
| Поддержка | Часы, каналы, приоритеты, время реакции/восстановления, окно работ |
| Приёмка | Представители сторон, среда, выборка, длительность испытаний, допустимые дефекты |
| Нагрузка и доступность | Согласованные численные цели и методика испытаний; текущих production SLA нет |
| Данные | Роли оператора/обработчика, состав, основания, сроки, выгрузка/уничтожение и исключения |

## Функции и проверка

Требования ниже описывают результат пользователя. Названия конкретных технологий/поставщиков в исходниках не устанавливают обязательный товарный знак для закупки.

| ID | Требование | Приёмочный сценарий на синтетических данных |
| --- | --- | --- |
| F01 | Личное расписание и изменения | Создать группу и занятия на две даты; студент видит свою группу и изменение времени/аудитории |
| F02 | Контекст занятия | Открыть занятие, материалы и разрешённые обсуждения; чужой студент не получает закрытые записи |
| F03 | Посещаемость и отсутствия | Выдать код/QR по действующему сценарию; отметка относится к своей паре; куратор видит назначенные группы |
| F04 | Импорт расписания | Загрузить согласованный CSV/JSON/ICS/XLSX или настроенный коннектор; повтор с тем же ключом не создаёт дублей; журнал показывает изменения |
| F05 | Подключение вуза | Владелец создаёт вуз и первого администратора; администратор входит отдельно, импортирует и проверяет свою структуру |
| F06 | Заявления учебного офиса, опция | Создать заявление своего вуза; пройти этапы с назначенными сотрудниками; self approval и чужая область запрещены |
| F07 | Роли и изоляция | Одинаковые запросы актёрами двух вузов: чужие чтение/изменение запрещены; отдельные платформенные grants проверяются |
| F08 | Сохранённое расписание офлайн | После явного сохранения открыть расписание без сети; после выхода кэш очищается; оценки/сообщения/материалы не объявляются доступными офлайн |
| F09 | Оценки Moodle, опция | Проверить числовую привязку, источник, ноль/скрытую оценку, страницы и недоступность; реестр долгов отдельно, отсутствие источника не означает «долгов нет» |
| F10 | Уведомления, опция | На согласованном канале проверить согласие/устройство, доставку, retry/dead letter и отзыв; локальные mocks не принимаются за доставку на устройство |

Поддержку браузеров/устройств, ограничения ICS и сопоставление внешних ID согласовать по [импорту](../integrations/schedule-import.md), [offline](../clients/student-offline.md) и [Moodle](../integrations/moodle-semester.md). Каждый внешний источник предоставляет заказчик с разрешением доступа; пароль/токен не включается в ТЗ или акт.

## Безопасность и эксплуатация

До передачи реальных данных стороны согласуют [матрицу ПД](../privacy/data-map.md) и [размещение](../legal/rf-deployment-assessment.md). В поставке должны быть ограничение доступа по вузу/роли, журнал административных действий без секретов, TLS, резервное копирование и проверка восстановления. Целевые RPO/RTO, сроки хранения журналов, площадка и модель угроз заполняются заказчиком совместно с оператором; имеющиеся локальные тесты не подтверждают их эксплуатационное исполнение.

Не заявлены как завершённые: полное самообслуживание export/обезличивания, соответствие WCAG 2.1 AA, официальный реестр задолженностей, проверка компании по реестру, полный XLSX-отчёт занятости, сертификация ФСТЭК, включение в реестр российского ПО. Если это обязательное требование заказчика, оно получает отдельный этап, бюджет и приёмку до поставки; его нельзя подписывать по этому проекту как уже выполненное.
