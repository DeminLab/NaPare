# Управление платформой

Текущая локальная реализация, 17 октября 2026. Не является подтверждением установки на production.

Кабинет разработчика `/developer/control` содержит сервисы, аккаунты, университеты, разрешения, настройки и журнал действий. Единственный владелец хранится как UUID существующего аккаунта в `platform_control`. Основная роль developer или superadmin сама по себе не даёт новых платформенных разрешений. Старые университетские полномочия superadmin сохраняются; его доступ к новой панели также требует назначения владельцем.

Владелец выдаёт и отзывает разрешения на чтение/изменение аккаунтов, университетов, настроек, аудит, чтение логов, рестарт и ребилд. Сервисные разрешения дополнительно ограничены списком сервисов. Отзыв действует при следующем запросе с тем же JWT. Готовый профиль «DevOps · полное оперативное управление» выбирает все эти разрешения и все сервисы; назначение применяется только после сохранения. Это профиль доступа существующего developer/superadmin, а не новая основная роль и не автоматическое повышение всех разработчиков.

Делегированный `platform_grants.universityIds` задаёт область данных: `NULL` означает глобальную область (так сохраняется поведение существующих назначений), `[]` — ни одного вуза, массив UUID — только перечисленные вузы. Владелец всегда глобален независимо от поля. Ограниченная область применяется к аккаунтам и структуре университетов, посещаемости/отсутствиям, личным записям, сдачам, уведомлениям и push-устройствам, кураторству, QR-сессиям, PairSpace, вложениям, академическим данным, системным событиям и обсуждениям. Эти API фильтруют списки и проверяют фактический вуз при открытии карточки и каждой мутации. Карьерные записи с однозначной связью с вузом доступны в области grant. Каталог компаний, управление их глобальными участниками, глобальные настройки, сервисы, логи и внешний доступ сервер отклоняет для ограниченного гранта. В `PUT /api/v1/platform/permissions/:id` пропущенное поле области сохраняет существующую область, а для нового назначения сохраняет совместимость старого клиента и означает глобальную область; новый интерфейс всегда отправляет поле явно. Список ограниченной области не включает компании платформенного уровня или другие записи без однозначной связи с вузом.

DevOps с accounts.write управляет пользователями всех вузов, включая блокировку, пароль и сессии других технических аккаунтов. Аккаунт владельца и собственный доступ защищены. Назначение/смена платформенной роли и выдача разрешений остаются только у владельца. Старые административные маршруты также защищают владельца и изменение платформенных ролей.

## Контур доверия владельца

Только владелец видит раздел «Контур доверия», назначает полномочия команды и выполняет экстренный отзыв. `POST /api/v1/platform/trust/emergency-revoke` требует актуальный JWT владельца, его текущий пароль и точную фразу `ОТОЗВАТЬ ТЕХДОСТУП`. Одной транзакцией удаляются все делегированные платформенные назначения и увеличивается sessionVersion всех developer/superadmin, кроме владельца. Изменение и аудит атомарны, пароль не журналируется. Назначения и отзыв сериализованы транзакционной блокировкой. Владелец сохраняет свой доступ; учебные аккаунты и данные не затрагиваются.

Это отзыв доступа через платформенный API: основные роли сохраняются, повторный вход остаётся возможным без отозванных разрешений. Старые университетские полномочия superadmin, SSH-ключи и внешние токены не отзываются. Уже принятые агентом задания продолжаются. Передача владения через интерфейс по-прежнему отсутствует; её нельзя подменять назначением профиля DevOps.

Доступны создание аккаунтов, просмотр карточки, редактирование email, имени, фамилии, телефона, аватара, основной роли, статуса, университета и учебной группы, сброс пароля и завершение сессий. Карточка показывает даты аккаунта, вуз и группу, факт привязки MAX/Telegram без раскрытия внешних ID, активные назначения куратора и десять последних действий по аккаунту. Поиск аккаунтов поддерживает email, имя, фамилию, телефон, группу и UUID. Группы возвращаются только для выбранного университета; для СИБИТ допустим также проверенный внешний ID из каталога расписания.

Управление внешними привязками доступно по `identity-links.read/write`. `POST /api/v1/platform/accounts/:id/identity/max/unlink` требует причину, защищает собственного пользователя и владельца, очищает MAX ID, увеличивает `sessionVersion` и записывает аудит. Внешний ID не сохраняется в аудите и не возвращается API; повторная связь выполняется через подтверждённый вход MAX. Для Telegram карточка аккаунта показывает только число ожидающих подключений и ближайший срок действия; хеши challenge-токенов не раскрываются. `POST /api/v1/platform/accounts/:id/identity/telegram/revoke` отзывает Telegram-привязку и все ожидающие подключения; если связь была активна, сессии пользователя завершаются. Оба действия требуют причину, защищают самого оператора и владельца и пишутся в аудит.

Изменения email, роли, статуса, вуза или группы увеличивают `sessionVersion`; правка имени, телефона или аватара не завершает сессии. Перенос в другой вуз требует предварительно отозвать активные назначения пользователя как куратора. Новые назначения группы проверяются по вузу; внешние группы СИБИТ проверяются через scraper. Для правки аккаунта интерфейс требует причину. Аудит аккаунта хранит старые и новые значения вместе с причиной; пароль, `sessionVersion`, `maxUserId` и `telegramUserId` в ответ управления не входят. Пароли хешируются bcrypt и не попадают в аудит. Удаление аккаунтов и передача владения через панель отсутствуют. Кураторство по-прежнему назначается отдельным действием в разделе кураторства.

Карточка аккаунта не означает доступ к его учебным, личным, карьерным записям или сообщениям. Для них требуется отдельное разрешение и доменные операции; `accounts.read/write` не расширяются до посещаемости, сообщений, заданий, карьерных работ или пользовательских настроек.

## Глобальные данные студентов

Раздел «Данные студентов» доступен по отдельным `student-data.read` и `student-data.write`. Сейчас в нём есть поиск по отсутствиям и посещаемости всех вузов для глобального доступа или выбранных вузов для ограниченного гранта, постраничная выдача и фильтры по вузу (если выдано `universities.read`), периоду, типу отсутствия, необходимости подтверждения и отметке посещаемости. Каждая строка поиска показывает название вуза, чтобы различать одноимённых студентов в разных организациях; исправления выполняются отдельными операциями с аудитом. Исправление требует причины, проверяет принадлежность студента и занятия тому же вузу и сохраняет старое и новое значения в журнале. Изменения выполняются через отдельные серверные операции; универсального доступа к таблицам БД нет.

Решения по отсутствиям доступны через `GET /api/v1/platform-data/absence-confirmations`, `GET /api/v1/platform-data/absence-confirmations/:id` и `PATCH /api/v1/platform-data/absence-confirmations/:id` в тех же permission scopes `student-data.read/write`. Поиск фильтруется по статусу и вузу; свободный запрос используется для поиска, но аудит сохраняет только факт его наличия, без текста `q`. Просмотр записывает оператора, студента, вуз, отсутствие, IP и user-agent; исправление статуса, комментария или даты решения требует причины и сохраняет старые/новые значения, IP и user-agent. Сервер проверяет связь решения с существующими отсутствием, студентом и вузом. `curatorId` остаётся привязанным к решению и не меняется при исправлении.

## Сдачи домашних заданий

Раздел «Сдачи домашних заданий» использует отдельные `homework-data.read` и `homework-data.write`. Поиск `GET /api/v1/platform-homework/submissions` фильтруется по тексту, вузу, статусу и датам; строка результата показывает вуз, чтобы различать глобальные записи. `GET /api/v1/platform-homework/submissions/:id` открывает содержимое и записывает просмотр в аудит. Исправление через `PATCH /api/v1/platform-homework/submissions/:id` требует причину и сохраняет старые и новые значения в аудите. Можно исправить статус сдачи, время, ссылку на вложение и комментарий; оценки в этом разделе не выставляются. Сервер повторно проверяет связи сдачи с заданием, пространством пары, занятием того же вуза и пользователем.

## Уведомления и входящие

Раздел «Уведомления и входящие» использует отдельные `notification-data.read` и `notification-data.write`. `GET /api/v1/platform-notifications/records` ищет уведомления (`kind=notification`) или входящие задачи (`kind=inbox`) по тексту, UUID пользователя и вуза, с фильтром по статусу; `GET /api/v1/platform-notifications/records/:kind/:id` открывает полный текст и параметры. Исправление через `PATCH /api/v1/platform-notifications/records/:kind/:id` требует причину и пишет в аудит старые и новые значения, оператора, пользователя и контекст запроса. Поиск и открытие записи тоже аудируются. Для уведомления доступны заголовок, текст, ссылка и состояние прочтения; для inbox — заголовок, описание, ссылка, статус, приоритет и даты срока/завершения. Сервер проверяет тип записи, допустимые поля и связь с существующими пользователем и университетом. `GET /api/v1/platform-notifications/devices` ищет push-устройства по пользователю и показывает идентификатор, владельца, платформу, имя устройства, активность и даты, но не токен; поиск аудируется. `PATCH /api/v1/platform-notifications/devices/:id/revoke` требует причину и деактивирует запись (`isActive=false`) без удаления. Отзыв сохраняет оператора, пользователя, платформу и имя устройства с причиной в аудите.

Глобальные назначения кураторов доступны по отдельным `curation-data.read/write`. `GET /api/v1/platform-curation/assignments` ищет активные назначения (или историю по `status=revoked|all`), `GET /assignments/:id` показывает исходный университет, группу, аккаунт и операторов выдачи/отзыва. `GET /groups` и `/candidates` ограничены выбранным университетом. `POST /assignments` назначает действующий аккаунт допустимой роли группе того же вуза; `PATCH /assignments/:id/revoke` мягко отзывает связь, сохраняя её историю. Обе операции требуют причину и записывают актёра, целевого пользователя, вуз, группу, IP и user-agent в аудит; поиски и открытие карточки также аудируются без сохранения текста поискового запроса. Старый `Group.curatorId` поддерживается как указатель на первое активное назначение, но не используется для проверки доступа. `curation-data.read` также открывает чтение списка вузов для выбора области управления.

QR-сессии посещаемости доступны по `attendance-qr.read` и `attendance-qr.revoke`. `GET /api/v1/platform-attendance-qr/sessions` ищет активные, истёкшие и отозванные сессии; ответ содержит только метаданные занятия и создателя, никогда не `tokenHash`. `PATCH /sessions/:id/revoke` отзывает только ещё действующую сессию, требует причину и повторно проверяет связь с занятием и вузом. Поиск и отзыв записываются в аудит с актёром, вузом, занятием, причиной и контекстом запроса. Уже истёкшие сессии отдельно отзывать нельзя.

Объявления PairSpace доступны по `pairspace-content.read/write`. `GET /api/v1/platform-pair-space/announcements` и `GET /announcements/:id` ищут и открывают записи с исходным автором, вузом, группой, занятием и пространством пары. `PATCH /announcements/:id` позволяет исправить только текст или закрепление и требует причину. Сервер проверяет связи с занятием, университетом, группой и автором; старые/новые значения, оператор и контекст запроса сохраняются в аудите. Автор, учебные связи и происхождение синхронизации не меняются.

Пространства пар доступны в той же панели через `GET /api/v1/platform-pair-space/spaces`, `GET /spaces/:id` и `PATCH /spaces/:id`. Поиск показывает контекст занятия, курса, группы, преподавателя, академического вхождения и число дочерних записей; detail проверяет совпадение tenant и связей с каталогом, а чтение и поиск пишутся в аудит. `PATCH` позволяет изменить только `isActive`, требует причину и повторно проверяет вуз и занятие в одной транзакции. Синхронизируемые поля и ссылки на учебные сущности остаются только для чтения, поэтому корректировки источника расписания выполняются в канонических разделах расписания и каталога.

Просмотр и изменение расписания занятий во всех или выбранных вузах доступны по `academic-data.read/write`. Вкладка «Расписание» объединяет текущие `LessonOccurrence` и старые записи `Lesson` без связанного occurrence. `GET /api/v1/platform-academic/occurrences` ищет конкретные занятия по тексту, университету, периоду и статусу; карточка `/occurrences/:id` показывает курс, группу, преподавателя и последние изменения. `PATCH /occurrences/:id` исправляет время, аудиторию, корпус или статус только для ручных (`source=manual`) занятий, требует причину и атомарно добавляет `ScheduleChange` и запись аудита. Для старой модели `GET /api/v1/platform-academic/lessons` ищет по тексту, вузу и датам; `GET /lessons/:id` открывает связи и последние изменения; `PATCH /lessons/:id` позволяет исправить предмет, даты и время, аудиторию, корпус, примечание и отметку изменения только для ручной записи. Старый маршрут блокирует импортированные записи, проверяет отношения вуза/группы/курса/серии/преподавателя, атомарно пишет `LessonChange`, `ScheduleChange` и аудит, затем публикует событие. Импортируемые занятия доступны для чтения; их нужно исправлять в исходной системе синхронизации. Удаление не предоставляется.

Подрежим «Академические события» управляет доменными записями `AcademicEvent`, отдельно от технической ленты `EventRecord`. Поиск и карточка показывают только разрешённые поля и не раскрывают произвольный JSON `payload`. Самостоятельные события без связи с occurrence и без внешнего источника можно исправить с причиной; связанные с занятием и импортированные записи доступны только для просмотра. Скрытие и восстановление доступны с причиной, обратимы и исключают скрытую запись из обычного `GET /academic/events`, не меняя формат ответа. Поиск, открытие и изменения записываются в аудит. Миграция `1700000000026-AcademicEventModeration` добавляет поля мягкого скрытия и не применена автоматически.

Подрежим «Курсы и серии» использует те же `academic-data.read/write`. `GET /api/v1/platform-academic/catalog/courses` и `/series` ищут записи по тексту и вузу; карточки показывают связи, происхождение, историю аудита и предупреждения о некорректных связях. `PATCH` требует причину и редактирует только ручные записи. Курс проверяет факультет и в той же транзакции обновляет `CourseSpace` при переименовании или деактивации; конфликт кода внутри вуза возвращает `409`. Серия проверяет группу и преподавателя этого же вуза и его роль, но сохраняет уже созданные occurrences как прежние снимки. `GET /catalog/options?universityId=...` выдаёт только имена и ID факультетов, групп и активных преподавателей выбранного вуза. Идентификаторы вуза, курса и provenance остаются неизменяемыми через эти маршруты.

Системные события выбранных вузов открываются во вкладке «События» по разрешению `events-data.read`; глобальный грант видит события всех вузов. Поиск охватывает тип, цель, университет и безопасные контекстные поля из allowlist. В карточке видны актёр, цель, приоритет, время и число адресатов, но не сами адресаты, полный payload или ключ идемпотентности. Для контекста payload показываются только предмет, курс, группа, идентификаторы занятия/преподавателя, срок и локальная ссылка; строковые значения очищаются и ограничиваются по длине. Поиск и просмотр аудируются без сохранения текста запроса.

Реестр вложений PairSpace доступен по `attachments-data.read/write`. Он ищет по идентификаторам материала, пространства и занятия, имени файла, автору, группе или предмету; университет можно выбрать отдельным фильтром. `GET /api/v1/platform-attachments/:id` показывает происхождение ссылки и состояние. `PATCH /:id/revoke` временно скрывает запись в PairSpace, а `PATCH /:id/restore` возвращает её; обе операции требуют причину. API выдаёт только HTTP(S) origin и path без учетных данных, query и hash. Никакие внешние URL не загружаются и физические файлы не удаляются. Если прямую ссылку уже знают, её доступность может сохраниться: текущая модель хранит ссылку и метаданные, а не само хранилище файла. Поиск, просмотр и изменения записываются в аудит.

Для других личных записей есть отдельный раздел «Личные записи» с полномочиями `personal-data.read/write`: настройки уведомлений, избранные группы и преподаватели, личные заметки к занятиям и личный прогресс по подготовке. Изменения требуют причины, проверяются относительно владельца записи и университета/занятия и атомарно сохраняют старые и новые значения в журнале. Старые записи можно исправить и удалить после перевода пользователя в другой вуз или группу: сервер проверяет владельца и целостность исходной связи с университетом, занятием или пространством пары. Для заметок интерфейс показывает название исходного вуза, а не только текущее место учёбы пользователя. Просмотр карточки тоже записывается в аудит; журнал содержит оператора, пользователя, IP и user-agent. Push-токены и внешние секреты не раскрываются; содержимое уведомлений доступно только по `notification-data.read`.

Раздел «Карьерные профили и допуски» и раздел «Практика» используют отдельные `career-data.read/write` и ищут профили, допуски, отклики и работы в области grant. Глобальный grant видит записи всех вузов; ограниченный — только выбранных вузов с совпадающей связью владельца/задачи. Каталог компаний и управление участниками компании доступны только глобальному grant; в контексте вузовой задачи или партнёрства показываются только ID и название компании. Раздел «Карьерные задачи» ищет все задачи; редактирование доступно только черновикам без откликов и работ, при неизменных связях с компанией и вузом. Сервер проверяет статус, связи и подтверждённое партнёрство повторно при сохранении. Раздел «Компании и партнёрства» ищет компании и связи с вузами; карточка компании разрешает исправлять только название и описание с причиной. Решение по партнёрству возможно только для ожидающей заявки, требует причину и недоступно создателю и действующему участнику этой компании. Раздел «Карьерные доступы» ищет назначения работников карьерных центров и компаний, позволяет обратимо отзывать назначение и передавать владение компании действующему участнику; оба действия требуют причину и записываются в аудит. Последнего владельца нельзя отозвать без передачи. Раздел «Карьерные тесты» ищет тесты и попытки студентов. Правильные ответы выдаются только при аудируемом открытии карточки теста; вопросы нельзя менять после первой попытки, чтобы не менять смысл сохранённых результатов. Раздел «Карьерный контент» ищет кейсы, отзывы и уведомления пользователя. Исправление или скрытие кейса аудируется; изменение текста отзыва автоматически снимает согласие автора на публикацию и скрывает связанный кейс. Поиск, просмотр и изменения записываются в карьерный аудит. Полные тексты профиля и заявки открываются отдельным запросом, который записывает просмотр в аудит. Исторические записи остаются доступны для исправления после перевода пользователя в другой вуз или смены роли; связь с исходным университетом и заданием сохраняется. Исправление профиля сбрасывает подтверждение, исправление допуска возвращает его в ожидание, а исправление отклика или результата сохраняет прежние/новые значения и причину. Административный выбор кандидата повторно проверяет текущий вуз, активность и допуски студента, срок задачи и лимит трёх активных работ; остальные отклики закрываются, все затронутые записи аудируются, участникам отправляются уведомления. Решение по работе возможно только на состоянии «на приёмке» и проходит штатный переход `accepted` или `revision`; принятие результата не означает оплату. Журнал аудита фильтрует личные и карьерные значения по соответствующим правам; просмотр учётных действий дополнительно требует `accounts.read`.

Раздел «Обсуждения» ограничивается выбранными вузами и использует отдельные `discussion-data.read/write`. Он ищет сообщения по автору, университету, предмету и тексту; карточка с полным текстом записывает просмотр в аудит. Исправление текста требует причины. Модератор может скрыть сообщение или восстановить его, сохраняя содержимое и историю; обычные ответы Pair Space показывают только видимые сообщения. Каждое действие хранит старые/новые значения, причину, автора изменения, IP и user-agent. Схема включается миграцией `1700000000024-DiscussionModeration`.

Решения по карьерным заявкам и работам доступны в отдельных операциях с проверкой переходов, автора и происхождения данных; обсуждения модерируются с сохранением автора и истории; импортируемое расписание доступно для чтения, его нужно исправлять в исходной системе. Административное исправление результатов Moodle потребует отдельного workflow. Кураторские назначения управляются отдельными операциями выдачи и мягкого отзыва. Эти данные нельзя менять как произвольные строки. Секреты, токены, QR-данные, пароли, ключи и техническая metadata не должны попадать в общий редактор.

Настройки карьерного планирования доступны через отдельный поиск всех вузов для глобального доступа или разрешённых вузов для ограниченного grant: бюджет недельных часов, часовой пояс, рабочие окна и периоды недоступности. Административная правка использует валидацию пользовательского API, сохраняет исходный университет и аудируется с причиной.

Настройки сохраняют название, контакт поддержки, объявление и режим обслуживания. Название/контакт/объявление доступны через публичный API метаданных; это не переименование всех существующих шапок интерфейса. Обслуживание блокирует мутации учебного API, сохраняя вход, чтение и управление платформой. Раздел университетов позволяет искать вузы, а внутри выбранного вуза — искать и редактировать факультеты и группы. Изменение факультета или группы требует причину и пишется в аудит; проверяется, что факультет и группа принадлежат тому же вузу. Для факультета доступны название и код. Для группы доступны название, курс, специализация и факультет; внешний ID источника только отображается, а назначение куратора изменяется отдельно. Факультеты и группы не удаляются из панели, чтобы не рвать связанные учебные данные. Секреты коннекторов не возвращаются.

## Серверные операции

API обращается по приватному сокету к отдельному host-процессу с HMAC, временной меткой и защитой от повторного запроса. API не получает Docker socket. Агент запускает только фиксированные команды Compose с массивом аргументов без shell. Произвольный терминал, удаление томов, обновление Git, резервные копии и откат релизов не реализованы.

Разрешён рестарт выбранного сервиса; ребилд доступен приложениям с build context. PostgreSQL, Redis и Nginx используют готовые образы. Ребилд выполняет build, затем up -d --no-deps только выбранного сервиса. Необходим ввод имени сервиса. Задание сохраняется до ответа API, имеет ключ идемпотентности и выполняется независимо от API. Проверяется running/healthy. После остановки самого агента выполнявшееся задание помечается interrupted: автоматического повтора потенциально выполненной команды нет. При недоступном агенте API возвращает ошибку, а не успешную операцию.

Логи ограничены по объёму и проходят редактирование известных секретов/типовых токенов. Это не гарантия обнаружения любого произвольного секрета в выводе приложения. Хранилище заданий требует контроля свободного места и периодического архивирования завершённых файлов оператором.

Установка и привязка владельца: [операционная инструкция](../deployment/platform-control.md).

## Проверка

Тесты `platform.e2e-spec.ts` используют свежую локальную PostgreSQL, настоящие Nest HTTP/JWT и подписанный транспорт агента. Выполнение Docker в локальном стенде заменено тестовым исполнителем: эти тесты не доказывают реальный рестарт контейнеров. `agent.test.mjs` отдельно проверяет подписи, allowlist, идемпотентность, сокрытие секретов и восстановление истории.
