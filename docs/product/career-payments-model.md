# Оплата карьерных задач: проект для согласования

Дата: 22 октября 2026. Статус: владелец выбрал Т-Кассу для оплаты услуг платформы без выплат студентам; реализация этого варианта разрешена. Переводы вознаграждений студентам требуют отдельной договорной и технической схемы и не входят в утверждённый объём.

## Что оплачивается

Предлагается отдельно учитывать услугу платформы (размещение/доступ работодателя) и вознаграждение исполнителю. Не хранить «кошелёк студента» и не обещать escrow. Для вознаграждений сначала согласовать с провайдером marketplace/split/payout продукт, идентификацию исполнителей, налоги и возвраты. Сумма карьерной задачи в нынешней модели не означает принятые или зарезервированные деньги.

## Провайдеры

| Вариант | Применение | Что подтвердить до разработки |
| --- | --- | --- |
| ЮKassa — рассмотренный | Hosted confirmation, API платежей и возвратов, webhook-события | Оператор/мерчант, договор, предмет услуги, чек, тестовый магазин; отдельно договориться о выплатах |
| Т-Касса — выбранный | Hosted PaymentURL, одно-/двухстадийная оплата, GetState, Cancel, уведомления | Компания/ИП, терминал и договор; схема выплат и fiscal receipt отдельно |

Документация подтверждает технические возможности [ЮKassa](https://yookassa.ru/developers/payment-acceptance/getting-started/payment-process) и [Т-Кассы](https://www.tbank.ru/kassa/dev/payments/). Это не подтверждение подключения НаПаре, согласования тарифа или права принимать деньги за исполнителей. Комиссии не зафиксированы в спецификации: они зависят от договора и продукта.

## Модель данных

| Сущность | Поля |
| --- | --- |
| PaymentOrder | UUID, universityId, companyId, taskId nullable, product/service, amountMinor integer, currency RUB, expectedRecipient, createdBy, immutable description snapshot |
| PaymentAttempt | orderId, provider, providerPaymentId unique, idempotencyKey unique, status, confirmationUrl, expiresAt, checkedAt |
| PaymentEvent | provider + eventId/dedup key unique, paymentId, receivedAt, verifiedAt, processingStatus, normalized status. Не сохранять платёжные реквизиты карты |
| Refund | paymentId, amountMinor, providerRefundId unique, idempotencyKey unique, state, reason, actorId, timestamps |

Сумма и предмет заказа создаются сервером из опубликованной услуги, не из суммы клиента. Tenant и компания проверяются по сохранённому членству. Баланс возврата блокируется транзакцией; сумма успешных и ожидающих возвратов не превышает оплату. Каждая смена состояния аудитируется без платёжных секретов.

## Состояния и доставка событий

Внутренние статусы попытки: `created → pending → authorized → succeeded`; из незавершённого состояния возможен `canceled/failed`. `authorized` используется только для подтверждённого двухстадийного сценария. Возвраты имеют отдельные `pending/succeeded/canceled/failed`; общий платёж помечается как частично/полностью возвращённый по сумме завершённых возвратов.

Webhook обрабатывается идемпотентно. Сначала проверить источник предусмотренным провайдером способом, затем запросить объект server-to-server и сопоставить merchant, ID заказа, сумму и валюту. Redirect в браузере не подтверждает оплату. События, пришедшие повторно или не по порядку, не откатывают финальное состояние. Worker периодически сверяет незавершённые попытки; сетевой timeout не создаёт новый платёж с новым ключом.

ЮKassa описывает [входящие уведомления и проверку их достоверности](https://yookassa.ru/developers/using-api/webhooks); для Т-Кассы требуется её [проверка токена уведомления](https://developer.tbank.ru/eacq/intro/developer/notification). Универсальная проверка «секрет в URL» не заменяет эти механизмы.

## Условия запуска

Владелец подтверждает провайдера и финансовую схему, идентифицирует юридическое лицо/ИП мерчанта, расчётный счёт, договор/оферту, услуги и правила возвратов. Бухгалтер/юрист подтверждает чек и налогообложение; для выплат — договоры с исполнителями и соответствующий продукт провайдера. Ключи хранятся только на сервере, sandbox/live магазины разделены. До production допуска проходят sandbox сценарии успеха, отказа, повторного webhook, подмены суммы/заказа, timeout и полного/частичного возврата.

Решение владельца: Т-Касса для оплаты услуг платформы без автоматических выплат студентам. Реальная регистрация мерчанта, договор и платежи отдельно выполняются оператором. До live-конфигурации применяется sandbox и отключённая по умолчанию отправка.
