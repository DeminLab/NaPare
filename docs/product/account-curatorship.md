# Кураторство на существующем аккаунте

Статус: реализовано в рабочей копии 15 октября 2026 года. Публикация и миграция production в эту работу не входят.

## Правила продукта

- Основная роль пользователя сохраняется. Студент, преподаватель и сотрудник деканата получают дополнительные назначения на группы без отдельного аккаунта и повторного входа.
- У группы несколько кураторов; у человека несколько групп. Назначение и снятие доступны деканату (`faculty_dean`), администратору университета и superadmin в контексте выбранного университета.
- Кураторские возможности одинаковы для всех основных ролей и действуют только в назначенных группах. Полномочия сотрудника, полученные по основной роли, сохраняются независимо.
- Доступны список студентов, расписание ближайших семи дней и рассмотрение обращений об отсутствии. Кураторство само по себе не даёт права менять роли, расписание, оценки, преподавательские материалы или отметки посещаемости.
- Собственное обращение нельзя подтвердить или отклонить. Его рассматривает другой куратор либо деканат.
- Кнопка «Кураторство» появляется внутри обычного кабинета. Проверка назначений выполняется при открытии, возвращении в окно и каждые 30 секунд. Сервер проверяет доступ на каждом запросе, независимо от состояния кнопки или открытой вкладки.

## Реализация

`curator_assignments` хранит группу, университет, пользователя, автора и время назначения/снятия. Действующее назначение уникально для пары пользователь–группа; снятые записи сохраняются. Основная роль, собственная учебная группа, пароль и версия сессии не меняются.

Кураторские запросы учитывают назначение, университет и настоящую группу студента. Учитываются локальные UUID групп и внешние идентификаторы СИБИТ через `Group.externalId`. Идентификаторы из интерфейса не являются разрешением на доступ.

Решения сохраняются в `absence_confirmations` с автором, временем, статусом и отдельным комментарием. Исходная причина отсутствия не перезаписывается. Блокировки группы и обращения в транзакции исключают два решения по одному обращению и сериализуют решение с отзывом назначения. Повторное решение возвращает 409. Назначения, снятия и решения записываются в аудит.

Уведомления об обращении направляются назначенным кураторам, самому студенту и действующим сотрудникам деканата/администрации. Рассылка всем аккаунтам с прежней основной ролью `curator` прекращена. Ссылка куратора открывает нужную группу и обращение; сервер повторно проверяет назначение.

## Интерфейсы

- `/student/curation`, `/staff/curation`, `/deanery/curation` используют один общий компонент.
- «Мои группы»: выбор группы, обращения, студенты и расписание, пагинация.
- «Назначение кураторов»: поиск группы, действующие кураторы, поиск существующего аккаунта по имени/email, назначение и снятие с подтверждением.
- Заголовки, аватары, логотипы и общие компоненты навигации не изменены.

## API

Новые маршруты начинаются с `/api/v1/curation`. Все требуют действующей JWT-сессии с привязкой к университету. Коллекции возвращают `{ data, meta }`.

| Метод и путь | Назначение |
| --- | --- |
| `GET /context` | Доступ к кураторству и управлению, число назначенных групп |
| `GET /groups` | Только назначенные группы |
| `GET /manage/groups` | Группы университета для деканата/администратора |
| `GET /manage/candidates` | Действующие аккаунты своего университета |
| `GET /groups/:groupId/curators` | Действующие кураторы группы для управления |
| `PUT /groups/:groupId/curators/:userId` | Идемпотентное назначение |
| `DELETE /groups/:groupId/curators/:userId` | Идемпотентное снятие с сохранением истории |
| `GET /groups/:groupId/students` | Студенты назначенной группы без паролей, телефонов и email |
| `GET /groups/:groupId/lessons` | Расписание назначенной группы; по умолчанию ближайшие 7 дней |
| `GET /absences` | Обращения назначенных групп; фильтры `groupId`, `absenceId`, `status=pending` |
| `GET /absences/:id/context` | Группа обращения из уведомления с проверкой назначения |

Решения используют существующие `PATCH /api/v1/curator/absences/:id/confirm` и `/reject` с проверкой назначения в сервисе. Прежние административные/преподавательские маршруты решения также используют ту же транзакцию; преподаватель сохраняет собственные полномочия на свои занятия.

В `GET /api/v1/absences/my` добавлены `status` и `decision`; существующие поля сохранены. `comment` остаётся причиной отсутствия, `decision.comment` — комментарием к решению.

## Совместимость и перенос

Миграция `1700000000020-CuratorAssignments` переносит прежний `Group.curatorId`, только если найден действующий допустимый аккаунт в том же университете. Некорректные привязки не превращаются в доступ. Основные роли и аккаунты не объединяются автоматически.

`Group.curatorId` остаётся совместимым указателем на первого действующего куратора для старых читателей; разрешения из него больше не выдаются. Новые назначения выполняются отдельными маршрутами. Старые попытки назначить куратора через создание/редактирование группы или замену основной роли получают понятную ошибку. Прежняя роль `curator` поддерживается для входа, с доступом к назначенным группам; новые отдельные аккаунты с этой ролью создавать не следует.

### Фактически проверено локально 15 октября 2026 года

- 266 backend unit-тестов прошли; после уточнения прав старой роли куратора дополнительно прошли целевые проверки academic/permissions.
- 12 интеграционных HTTP-сценариев прошли на отдельном PostgreSQL с реальной авторизацией: миграция, несколько групп/кураторов, ограничение университета/группы, сохранение основной роли и JWT, запрет самопроверки, гонка решений, уведомления, отзыв и история.
- В браузере проверены реальные запросы к этой тестовой базе через локальный шлюз: отказ/рассмотрение обращения студентом-куратором, назначение/снятие деканатом, кабинет администратора, вход из обычного профиля, отзыв при открытом списке, сохранение сессии и ссылка из уведомления. Ответы API не подменялись.
- Студенческий и staff-экраны проверены на 320, 390, 768 и 1440 px; административный — на 390 px. Переполнения страницы и ошибки JavaScript в этих сценариях не обнаружены.
- Локальные снимки и логи сохранены в игнорируемом `output/playwright/curation/`; они не входят в репозиторий. Результаты выше относятся к проверке 15 октября, повторный браузерный прогон при синхронизации документации не выполнялся.

Это локальные интеграционные и браузерные проверки на синтетических аккаунтах, не проверка реальных данных университета или production. Миграция на рабочую базу, Docker-сборка и публикация не выполнялись.
