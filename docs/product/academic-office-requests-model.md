# Учебный офис: модель заявлений для согласования

Дата: 22 октября 2026. Статус: спецификация P1-4 утверждена владельцем в этом чате; реализация разрешена. Читатель: владелец продукта и предметный эксперт учебного офиса. Утверждение модели не является подтверждением готовности кода.

## Предлагаемый первый выпуск

Три типа обращения: отсутствие (`absence`), перевод (`transfer`), пересдача (`retake`). Заявление содержит данные студента своего вуза, текст, ссылки на разрешённые документы, ответственного, срок и историю решений. Решение по заявлению не меняет автоматически группу, оценку, LMS или официальный приказ: соответствующее действие оформляется отдельно и отражается ссылкой на результат. Реестр академических задолженностей показывает только сведения подтверждённого источника; при его отсутствии сообщает об отсутствии данных.

Рабочие места задаются дополнительными назначениями существующим сотрудникам: `office` принимает и ведёт заявления, `methodologist` готовит академическое заключение, `dispatcher` работает с расписанием. Основные 11 ролей не меняются. Администратор вуза назначает обязанности только сотрудникам своего вуза и ограничивает их выбранными факультетами/группами. Делегирование владельца платформы остаётся отдельной системой.

## Модель хранения

| Сущность | Поля и ограничения |
| --- | --- |
| `office_assignments` | UUID, universityId, userId, duty, facultyIds/groupIds, assignedBy, revokedAt, timestamps. Пустой список scope означает отсутствие доступа, глобального scope между вузами нет |
| `student_requests` | UUID, universityId, studentId, groupId на момент подачи, type, status, title, description, assignedTo, dueAt, workflowVersion, version, createdBy, submittedAt, closedAt, timestamps |
| `request_steps` | requestId, universityId, sequence, duty/role, assigneeId, state, dueAt, decidedBy/At, reason. Уникальные requestId + sequence; следующая стадия только после предыдущей |
| `request_decisions` | UUID, universityId, requestId, stepId, actorId, action, fromStatus, toStatus, reason, timestamp. Добавление без редактирования и удаления через API |
| `request_documents` | UUID, universityId, requestId, attachmentId, addedBy, timestamps. Только существующий разрешённый файл; произвольный URL не принимается |

Все таблицы входят в RLS по universityId. Иностранные student/group/assignee/attachment отклоняются до записи. Обновление использует optimistic version; повтор команды с тем же idempotency key возвращает прежний результат. История и сроки сохраняются при смене исполнителя. В audit не копируется текст медицинского документа.

## Состояния и переходы

| Из | Команда | В | Условие |
| --- | --- | --- | --- |
| `draft` | Подать | `submitted` | Автор/уполномоченный оператор; валидные поля и маршрут |
| `submitted` | Принять | `in_review` | Оператор своего подразделения назначил ответственного |
| `in_review` | Уточнить | `needs_changes` | Обязателен текст запроса |
| `needs_changes` | Отправить уточнение | `submitted` | Автор дополнил сведения; история не обнуляется |
| `in_review` | Согласовать этап | `in_review` или `approved` | Текущий согласующий; последний этап завершает решение |
| `in_review` | Отказать | `rejected` | Текущий согласующий; обязательная причина |
| `submitted`, `needs_changes` | Отозвать | `withdrawn` | Автор; решение ещё не принято |
| `approved`, `rejected`, `withdrawn` | Закрыть | `closed` | Учебный офис зафиксировал доставку результата/основание |

Просрочка вычисляется из dueAt и незавершённого состояния, а не заменяет статус. Повторное открытие закрытого заявления не предусмотрено первым выпуском: создаётся новое со ссылкой на исходное.

## Маршруты согласования по умолчанию

| Тип | Стадии | Результат |
| --- | --- | --- |
| Отсутствие | Учебный офис → куратор назначенной группы/деканат | Решение и ссылка на запись существующего модуля отсутствий; самостоятельного дублирующего медицинского реестра нет |
| Перевод | Учебный офис → методист → деканат | Заключение и реквизиты решения/приказа; группа не меняется автоматически |
| Пересдача | Учебный офис → методист/руководитель подразделения → деканат | Разрешение и согласованный срок; оценка остаётся в LMS/официальной системе |

Изменения маршрута после подачи требуют новой версии и отдельного решения в истории. Нельзя назначить самого заявителя согласующим собственного обращения. При отсутствии назначенного ответственного подача отклоняется с понятной причиной и действием для администратора.

## Права

| Участник | Доступ |
| --- | --- |
| Студент | Свои заявления, уточнение/отзыв до решения. В первом выпуске student UI не меняется; backend self API может использоваться позднее |
| Учебный офис | Реестр и приём обращений своего scope, назначение ответственного, запрос уточнений, закрытие, отчёт |
| Методист | Назначенные академические этапы своего scope и заключение; без управления аккаунтами и интеграциями |
| Диспетчер | Только расписание и связанные согласованные действия; заявления автоматически не открываются |
| Куратор | Только назначенный этап по активным группам; без самостоятельного расширения scope |
| Деканат | Решения своего факультета/групп при назначении, без чужих факультетов |
| Администратор вуза | Настройка назначений/маршрутов, делегирование, контроль сроков своего вуза; просмотр чувствительных документов по отдельному разрешению |
| Технический сотрудник | Только через явное сохранённое разрешение владельца, tenant scope и аудит |

## Интерфейс и проверки приёмки

В `web-admin` создаётся страница учебного офиса: очередь с фильтрами типа, состояния, подразделения, срока и ответственного; карточка обращения с текущим шагом и полной историей; настройки назначений. Ссылка открывается из существующей контентной страницы управления вузом, navigation/header/Avatar/logo не меняются. Для действия показывается его результат и следующая стадия.

Обязательные тесты: два вуза и два факультета, чужой ID в URL/body, отзыв назначения на существующей JWT-сессии, запрет самоодобрения, невозможный переход, конкурентное решение, повтор команды, смена исполнителя с сохранением истории, пустой источник задолженностей, keyboard/focus/error/empty состояния UI.

Модель подтверждена владельцем; реализация разрешена. Продуктовые вопросы следующего этапа: точные сроки и подразделения, состав документов, кто подписывает официальный результат, допустимость подачи сотрудником от имени студента. Проектируемый первый выпуск допускает такую подачу только с явным разрешением и аудитом автора.
