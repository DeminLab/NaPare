# Решения по интеграции ECC

Снимок анализа от 19 ноября 2026 года (Asia/Omsk). Основания и команды проверок приведены в [VERIFICATION.md](VERIFICATION.md). Решения о составе приняты для плана. Внедрение каждого компонента требует соответствующего этапа.

## Исходные точки

- **ECC.** Ветка `main`, коммит `3f14a103a8694e51c1df9a806217a6d0b5f7a6f7` от 17 ноября. Файл `VERSION` и Codex manifest указывают `2.2.3`. Снимок получен через Git в отдельный временный каталог для чтения исходников. Для последующей установки использовать этот SHA и сохранять применимый notice MIT. [Дерево ECC](https://github.com/affaan-m/ECC/tree/3f14a103a8694e51c1df9a806217a6d0b5f7a6f7), [лицензия](https://github.com/affaan-m/ECC/blob/3f14a103a8694e51c1df9a806217a6d0b5f7a6f7/LICENSE).
- **NaPare.** На начало анализа `main` на два коммита впереди локальной ссылки `origin/main`, HEAD `9160158f9c9fde814fc3c1886801e740ec26faea`. В рабочем дереве уже были изменения в приложениях, документах и DevKit. Состав DevKit относится к фактическому рабочему дереву, включая незакоммиченные файлы. Ориентиры: [руководство разработчика](../DEVELOPER_GUIDE.md), [архитектура DevKit](../ai-devkit/architecture.md), [контракты ролей](../ai-devkit/agents.md).

Источники: [root manifest](../../package.json), [lockfile](../../pnpm-lock.yaml), [backend manifest](../../apps/backend/package.json), [dev Compose](../../docker-compose.dev.yml).
- **Клиент.** Windows/PowerShell, Codex CLI `0.146.0`, Node `24.11.1`, pnpm `9.15.4`. Локальный app-server прочитал проектный слой конфигурации и обнаружил 20 включённых `napare-*` Skills. Общие docs Codex обновляются независимо от установленного клиента. Для событий, полей и поведения клиент проверяется отдельно. [Справочник конфигурации Codex](https://learn.chatgpt.com/docs/config-file/config-reference).

## D1. Выборочный перенос в существующий DevKit

У ECC есть нативный marketplace-плагин. На локальном CLI доступны команды `plugin marketplace` и `plugin add`. В исходниках ECC поддержка указана начиная с `0.146.0`, а регистрация относится к активному `CODEX_HOME`. Манифест подключает весь `skills/`, `.mcp.json` и `hooks/codex-hooks.json`. Установка и обнаружение этого плагина в NaPare ещё не проверялись. [Манифест ECC](https://github.com/affaan-m/ECC/blob/3f14a103a8694e51c1df9a806217a6d0b5f7a6f7/.codex-plugin/plugin.json), [инструкция ECC](https://github.com/affaan-m/ECC/blob/3f14a103a8694e51c1df9a806217a6d0b5f7a6f7/.codex-plugin/README.md), [структура плагина Codex](https://developers.openai.com/plugins/build/plugins).

Для NaPare выбран проектный перенос двух кандидатов после полного просмотра на этапе 2 и адаптация в существующих Skills на этапе 4. Механизмы Codex в NaPare уже покрывают загрузку Skills и конфигурации. Перенос сохраняет контроль состава, происхождения, обновления и отката файлов. Массовый плагин увеличивает каталог и добавляет второй Chrome DevTools и внешний hook. Устаревший sync ECC пишет в глобальный Codex home и создаёт лишний слой. Upstream wizard, глобальные Git hooks, ECC CLI/ECC2, автономные сценарии и hosted ECC Pro исключены из состава по области, стоимости или требуемым разрешениям. [Варианты установки и platform matrix ECC](https://github.com/affaan-m/ECC/blob/3f14a103a8694e51c1df9a806217a6d0b5f7a6f7/README.md).

## D2. Роли используют проектные контракты

В ECC есть конфигурация для `explorer`, `reviewer` и `docs_researcher`. На примере upstream reviewer обнаружены привязка модели и `sandbox_mode`; файл подключается через reference config. Текущий standalone формат Codex требует `name`, `description`, `developer_instructions`. Sandbox, provider и MCP определяются родительской сессией. У NaPare уже есть 12 отдельных профилей с нужными полями, включая `code-reviewer` и `technical-writer`. Оставить встроенного `explorer`, адаптировать существующие контракты при необходимости, сохранять наследование разрешений и арбитраж файлов у интегратора. Обнаружение роли и её фактический запуск подтверждать раздельно по клиентам. [Роли ECC](https://github.com/affaan-m/ECC/tree/3f14a103a8694e51c1df9a806217a6d0b5f7a6f7/.codex/agents), [схема subagents](https://learn.chatgpt.com/docs/agent-configuration/subagents), [предыдущая проверка NaPare](../ai-devkit/codex-verification.md).

## D3. MCP через существующие подключения

В `.mcp.json` плагина ECC одна активная запись. Она запускает `npx -y chrome-devtools-mcp@1.10.1`. В NaPare уже есть отдельный launcher с lockfile и Chrome DevTools `1.13.0`, а также Context7, Playwright, DBHub, GitHub, Figma и Sentry. Использовать существующие подключения и тестовые сценарии. Для DBHub единственный допустимый контур в этой интеграции — синтетическая база с эффективной read-only SQL ролью. Для внешних MCP учитываются отдельная авторизация, права и разрешение на данные. Next DevTools в текущем проекте отключён по версии Next. [MCP ECC](https://github.com/affaan-m/ECC/blob/3f14a103a8694e51c1df9a806217a6d0b5f7a6f7/.mcp.json), [конфигурация NaPare](../../.codex/config.toml), [runtime lockfile](../../scripts/ai-devkit/runtime/package-lock.json), [MCP DevKit](../ai-devkit/mcp.md).

## D4. Короткий локальный hook и самостоятельные проверки

В Codex-проекции ECC один `SessionStart`. Его Node bootstrap зависит от `PLUGIN_ROOT`, выставляет `CLAUDE_PLUGIN_ROOT` и вызывает upstream runtime; по исходникам `session-start.js` может обращаться к локальным session leases. В NaPare уже обнаружен локальный игнорируемый Git файл `.codex/hooks.json` с `rtk hook codex` и matcher `Bash`. Фактическое совпадение matcher в Windows-сеансе пока не проверено. На этапе 7 проверить протокол и lifecycle на текущем клиенте, спроектировать узкий opt-in handler с подсказкой о возобновлении и сохранить RTK. Для команды систематические проверки опираются на существующие скрипты DevKit и CI. Запуск автоматически не получает права на установку, миграцию, запись данных или публикацию. [Hook ECC](https://github.com/affaan-m/ECC/blob/3f14a103a8694e51c1df9a806217a6d0b5f7a6f7/hooks/codex-hooks.json), [Codex Hooks и trust](https://learn.chatgpt.com/docs/hooks), [CI DevKit](../../.github/workflows/ai-devkit.yml).

## D5. Память и бюджет контекста

Из ECC Memory Vault принять локальные Markdown-записи, ссылки на подтверждение и явное замещение устаревших записей. Текущий статус интеграции хранится в пяти документах, устойчивые решения в действующих ADR и профильных документах NaPare. Для восстановления использовать короткую запись в AGENTS.md и точечное чтение. Память должна работать в новом сеансе с чистой историей. Автоматический сбор сессий, глобальный ECC Vault, внешние хранилища и эмбеддинги в состав не входят.

Codex сначала читает метаданные Skills, подробности загружает при выборе. Снимок NaPare содержит 70 Skills по результату DevKit verifier, включая 20 профильных. Измерять видимость и usage до настройки лимитов. В манифесте ECC указано 281, но в снимке Git найдено 327 путей `skills/<name>/SKILL.md`. Количество обнаруженных клиентом Skills ECC неизвестно. Для оценки установки ориентироваться на дерево и проверку обнаружения на целевом клиенте. [ECC Memory Vault](https://github.com/affaan-m/ECC/blob/3f14a103a8694e51c1df9a806217a6d0b5f7a6f7/docs/design/ecc-memory-vault.md), [бюджет Skills Codex](https://learn.chatgpt.com/docs/build-skills).

## D6. Локальная установка справочных материалов

На этапе 2 установлены три файла из ECC `2.2.3` с сохранением байтов Git. [Манифест источников](../../scripts/ai-devkit/skill-adapters/ecc/sources.json) фиксирует репозиторий, полный коммит, исходный путь, имя назначения и SHA-256 каждого файла. Папка назначения `scripts/ai-devkit/skill-adapters/ecc/upstream/` наследует проектное правило Git `eol=lf` для адаптеров. Это сохраняет хеши при checkout на Windows. Адаптация под проект выполняется на этапе 4.

| Установленный файл | Назначение и замечания для адаптации |
| --- | --- |
| [verification-loop.md](../../scripts/ai-devkit/skill-adapters/ecc/upstream/verification-loop.md) | Последовательность build, types, lint, tests, security и diff. Полезно сохранить отдельную оценку целевого окружения. Исходные примеры используют Bash и Claude-команду `/verify`, показывают совпавшие строки при поиске секретов и задают общий порог coverage. На этапе 4 выбрать реальные команды NaPare, выводить только безопасные метаданные совпадений и применять действующие правила проекта. `git diff HEAD~1` заменить сверкой с фактической границей задачи |
| [mcp-dependency-review.md](../../scripts/ai-devkit/skill-adapters/ecc/upstream/mcp-dependency-review.md) | Статическая классификация npm, Docker и Python selectors. Закреплённая прямая версия подтверждает только фиксированный selector. На этапе 4 сверять TOML Codex, launcher и транзитивный lockfile. Связанные ECC Skills и внешний MCP Drift Check указаны как справочные и для применения метода не требуются |
| [LICENSE](../../scripts/ai-devkit/skill-adapters/ecc/upstream/LICENSE) | MIT notice из корня того же коммита. Upstream хранит оба навыка как обычные текстовые файлы и не содержит отдельной лицензии в их каталогах |

[Установщик DevKit для vendor Skills](../../scripts/ai-devkit/install-vendor-skills.py) всегда пишет под `.agents/skills` и требует `SKILL.md`. Для справочных копий добавлен отдельный [установщик](../../scripts/ai-devkit/install-ecc-references.py) на Python стандартной библиотеки. Он читает указанные блобы локального Git, сверяет весь набор до записи и публикует готовые файлы с запретом перезаписи. Повторный запуск проверяет содержимое и оставляет файлы на месте. Публикация использует жёсткие ссылки на одном томе, что проверено в рабочем дереве Windows. При коллизии рабочая копия остаётся в исходном месте, а исходник для сравнения остаётся в закреплённом Git-объекте.

### Повторение и проверка установки

Из корня NaPare в PowerShell. Получение точного коммита занимает отдельный временный каталог и не выполняет checkout.

```powershell
$eccManifest = Get-Content -Raw scripts/ai-devkit/skill-adapters/ecc/sources.json | ConvertFrom-Json
$eccSourceRepo = Join-Path ([IO.Path]::GetTempPath()) ('napare-ecc-' + [guid]::NewGuid())
git -c core.hooksPath=NUL init -q $eccSourceRepo
if ($LASTEXITCODE -ne 0) { throw 'Не удалось создать временный Git-каталог ECC' }
git -C $eccSourceRepo -c core.hooksPath=NUL fetch --no-tags --depth=1 $eccManifest.repository $eccManifest.revision
if ($LASTEXITCODE -ne 0) { throw 'Не удалось получить закреплённый коммит ECC' }
py scripts/ai-devkit/install-ecc-references.py --source-repo $eccSourceRepo
if ($LASTEXITCODE -ne 0) { throw 'Предварительная проверка ECC завершилась ошибкой' }
py scripts/ai-devkit/install-ecc-references.py --install --source-repo $eccSourceRepo
if ($LASTEXITCODE -ne 0) { throw 'Установка справочных копий ECC завершилась ошибкой' }
py scripts/ai-devkit/install-ecc-references.py --check
```

Для проверки установленной копии достаточно последней команды. Если исходник нужно сравнить с локальной правкой, взять его командой `git -C $eccSourceRepo show "$($eccManifest.revision):<исходный путь>"` с путём из манифеста. Для отката сначала проверить SHA-256 каждого из трёх файлов по манифесту и переместить только совпавшие файлы этапа в резервную папку. При изменённом файле сохранить его и отдельно сверить diff. После отката цель установки уже не будет проходить `--check` до восстановления файлов.

Владелец установки и манифеста — сопровождающий NaPare AI DevKit. При обновлении сначала просмотреть diff и лицензии кандидатов на новом закреплённом коммите, зафиксировать решение и новые хеши. Затем сохранить старые справочные файлы, установить новый набор и повторить проверку. Код первоисточника и необязательные ссылки проверяются отдельно перед любым запуском.

## D7. Корневые инструкции Codex

[Корневой AGENTS.md](../../AGENTS.md) остаётся общей точкой входа. Блок `Working in Codex` связывает три шага: найти затронутую область по карте, выбрать профильный workflow в индексе Skills и подтвердить результат проверками из руководства по тестированию. В корне остаются только общие инструкции, а команды и сценарии имеют собственные источники. Область изменений ECC ограничена руководством и инструментами DevKit. Проектные правила прав, защиты данных и внешних операций действуют при любой работе.

На пути от корня до `apps/backend` дополнительных AGENTS.md или AGENTS.override.md не найдено. Для этой интеграции достаточно одного корневого файла. Вложенные инструкции применяются, когда Codex запускается из соответствующего поддерева. `AGENTS.override.md` заменяет обычный файл того же уровня. Совместимость проверена локально на CLI и на отдельном синтетическом дереве. [Правила обнаружения Codex](https://learn.chatgpt.com/docs/agent-configuration/agents-md#how-codex-discovers-guidance)

Для адресного отката убрать добавленный в этапе 3 раздел `Working in Codex` с его тремя пунктами, предварительно сверив его с текущим diff. Сохранить остальное содержимое файла, включая раздел `ECC integration`. Проверенный откат на копии вернул исходные байты. Пользовательский Codex home и параметры обнаружения в проектном TOML в этот этап не добавлялись и не правились.

## D8. Два сценария ECC в существующих Skills

`napare-qa` и `napare-code-review` используют общий [цикл проверки изменений](../ai-devkit/workflow.md#цикл-проверки-изменений). Из ECC перенесены сборка, типы, линт, тесты, безопасность и сверка diff. Область определяется изменением и фактической командой репозитория. Coverage, статические проверки, локальный результат и подтверждение целевого окружения учитываются отдельно. При поиске секретов в отчёт попадают только путь, строка и тип совпадения.

`napare-devops` и `napare-security` используют общую [статическую проверку зависимостей MCP](../ai-devkit/mcp.md#статическая-проверка-зависимостей-mcp). DevOps отвечает за цепочку selector → launcher → манифест → lockfile. Security оценивает права, секреты и область доступа. Проверка работает с TOML как с данными. Для прямого источника фиксируется точная версия, изменяемая ссылка или необходимость ручной сверки. Решение о включении и runtime-проверки MCP относятся к этапу 6.

| Стек | Существующее покрытие |
| --- | --- |
| Next.js App Router и React | [`napare-frontend`](../../.agents/skills/napare-frontend/SKILL.md), workspace API и shared UI |
| NestJS и DTO | [`napare-backend`](../../.agents/skills/napare-backend/SKILL.md), guards и validation |
| TypeORM, PostgreSQL и RLS | [`napare-database`](../../.agents/skills/napare-database/SKILL.md) и `napare-security`, изолированная схема и tenant boundaries |
| Docker и CI | [`napare-devops`](../../.agents/skills/napare-devops/SKILL.md), Compose, CI, DevKit и границы production |
| Playwright и Chrome DevTools | [`napare-qa`](../../.agents/skills/napare-qa/SKILL.md), браузерный сценарий, console/network и контекст реального маршрута |
| Android WebView | [`napare-mobile`](../../.agents/skills/napare-mobile/SKILL.md), Android build и проверка на устройстве отдельно от mobile web |

Для стека достаточно существующих навыков. Новые пункты ссылаются на два проектных раздела, подробности открываются по требованию. Исходные тексты и лицензия ECC сохраняются по хешам этапа 2. Для отката убрать только добавленные пункты, восстановить прежние описания DevOps и Security, затем убрать два добавленных раздела из проектных документов. Перед этим сверить diff и сохранить последующие изменения.

| Роль в ECC | Применение в NaPare |
| --- | --- |
| `explorer` | Встроенный `explorer`. В поручении указываются узкая область, путь исполнения и ожидаемые ссылки на файлы и символы |
| `reviewer` | [`code-reviewer`](../../.codex/agents/code-reviewer.toml). Замечания по влиянию с путём, строкой, триггером, последствием и проверкой. Корректность и регрессии приоритетнее стилистики |
| `docs_researcher` | [`technical-writer`](../../.codex/agents/technical-writer.toml). Утверждения об API, фреймворках и релизах требуют первичного источника нужной версии, точной ссылки и явного статуса при отсутствии доказательства |

Профили сохраняют имена, назначение и профильные Skills. Общие ограничения берутся из AGENTS.md. Модель, разрешения, sandbox и MCP задаются родительским сеансом. Проектный лимит — три дочерних потока. Инструкция роли определяет работу с файлами; технический режим чтения настраивается в родительской сессии. [Схема Codex](https://learn.chatgpt.com/docs/agent-configuration/subagents). [Конфигурация ролей ECC](https://github.com/affaan-m/ECC/tree/3f14a103a8694e51c1df9a806217a6d0b5f7a6f7/.codex/agents).

Клиенты проверяются отдельно. Текущий desktop-сеанс принимает `agent_type`. В проверенном CLI-сеансе без селектора применим [контракт роли через текст поручения](../ai-devkit/agents.md#выбор-роли-и-проверка-запуска). Факт назначения нативной роли, факт загрузки конфигурации и результат текстового поручения учитываются отдельно.

Для отката восстановить только изменённые `developer_instructions` двух TOML и затронутые строки документации. Последующие правки сохранить через адресное сравнение. Остальные профили и проектный лимит используются как исходная конфигурация.

## D10. Проектные MCP и защита DBHub

Оставлены восемь проектных записей в `.codex/config.toml`. Полный ECC marketplace завёл бы второй Chrome DevTools, поэтому используются существующие имена, launcher и runtime lockfile NaPare. Локальные действия подтверждены для Context7, Playwright, Chrome DevTools и DBHub. GitHub через настроенный CLI transport, Figma и Sentry требуют отдельной авторизации. Next DevTools рассматривается после перехода на совместимый Next.js. [Матрица и способы повторной проверки](../ai-devkit/mcp.md).

Для DBHub наличие локального файла больше не служит единственным условием запуска. [Launcher](../../scripts/ai-devkit/mcp.mjs) принимает только единственный источник синтетической базы на закреплённом loopback-адресе, роль `devkit_reader` и два настроенных инструмента с `readonly=true` для SQL. [Bootstrap](../../scripts/ai-devkit/test-database.py) сверяет каталог PostgreSQL перед SQL-подготовкой. Это проверка случайных неверных настроек. Режим чтения отдельно обеспечивают ACL PostgreSQL и DBHub; программа не изолирует процессы с правами того же пользователя ОС.

Для адресного отката сверить и восстановить только изменения двух скриптов и документации этапа. При проблеме с локальным fixture сначала исключить DBHub из конкретного тестового запуска Codex. Использовать только выделенный кластер и генерируемую конфигурацию. Уже работавший кластер не останавливался. Новые записи подключения и глобальные авторизации на этом этапе отсутствуют.

## D11. Локальный hook ECC и офлайн-проверки

Подсказка ECC использует штатный `SessionStart` с `startup|resume` в [отдельном слое docs/ecc](.codex/hooks.json). Этот слой обнаруживается при запуске Codex из `docs/ecc`. Корневой RTK продолжает использовать свой `PreToolUse` с каноническим matcher `Bash`. Для нового hook пользовательский trust остаётся отдельным действием. [Схема и доверие Codex](https://learn.chatgpt.com/docs/hooks).

[Обработчик](../../scripts/ai-devkit/ecc-session-start.mjs) проверяет событие, рабочий каталог и наличие трёх документов. Он выдаёт только постоянную короткую подсказку, без содержимого документов. Установленный Codex объявляет событие `PostCompact`, отдельный обработчик для него не добавлен. Правило AGENTS.md действует независимо от запуска hook и покрывает перечитывание после compaction.

Офлайн-проверки встроены в [AI DevKit workflow](../../.github/workflows/ai-devkit.yml). Структуру ECC-документов, относительные ссылки и точную конфигурацию проверяет существующий verifier. Хеши проверяет собственный `--check` установщика, протокол обработчика — тесты Node. Сетевые вызовы и рабочий trust для этих трёх команд не требуются.

Отключение в конкретном окружении доступно через `/hooks` для ECC SessionStart. При откате из репозитория удалить только вложенную регистрацию по текущему diff. Чтобы оставить статические проверки после удаления регистрации, перенести проверку её схемы в тестовый fixture или сделать её условной при наличии файла. Корневой RTK и прежние правила доверия не редактировать.

## D12. Техническая память в репозитории

[Карта памяти](../ai-devkit/project-memory.md) связывает существующие ADR, глоссарий, руководство разработчика, runbooks и пять документов ECC. Новая запись указывает дату, статус, область, источник и связь с заменённым фактом. Память передаёт состояние, а право на переход к следующему этапу следует из команды пользователя. Публикация и обновление выполняются через обычный diff проекта. Vault runtime, автоматическая запись бесед и hosted storage для этой памяти не подключены.

## D13. Компактные инструкции и выбор инструментов

В AGENTS.md оставлены требования, которым нужно следовать в каждой задаче. Подробные проверки и правила делегирования открываются по ссылкам. Описания четырёх Skills сокращены с сохранением тем и исходных workflow. Ссылка на локальный `project-map.md` заменена ссылкой на версионируемое руководство разработчика.

MCP и делегирование выбираются под конкретную задачу. Параметры модели, compaction, бюджет каталога и лимит агентов сохраняют установленные значения. [Процедура выбора контекста и замеров](../ai-devkit/workflow.md#контекст-codex).

## D14. Приёмка и адресный откат

Для чистой проверки использованы архив базового коммита и публикуемые файлы DevKit из рабочего дерева. Это позволяет проверить ссылки и установку до коммита и отсеять локальные игнорируемые файлы. Браузеры проверены на отдельной loopback-странице, DBHub — на выделенном PostgreSQL. Вызов Playwright из автоматического CLI-прогона отменялся. Для воспроизводимой проверки действия используется прямой прогон через SDK из существующего smoke-скрипта. [Доказательства и повторный запуск](VERIFICATION.md#этап-10-комплексное-тестирование).

Перед откатом сверить текущий diff с выбранным этапом и сохранить рабочие изменения. В общих файлах отменять только относящиеся к этапу фрагменты.

| Этап | Действие при откате |
| --- | --- |
| 1 и 3 | В корневом AGENTS.md адресно отменить раздел ECC и изменения инструкций этапа. Если убирается документация ECC целиком, сначала убрать ссылки на неё в AGENTS.md, индексах и автоматических проверках. См. D7 |
| 2 | Сверить SHA-256 и убрать только принадлежащие установке справочные копии по манифесту. Сохранить чужие и изменённые файлы. См. D6 |
| 4 и 9 | Адресно вернуть затронутые строки в четырёх Skills, workflow DevKit и AGENTS.md. Сохранить действующие ссылки и материалы, которые ещё используются. См. D8 и D13 |
| 5 | Вернуть только адаптированные фрагменты двух контрактов и их описаний. См. D9 |
| 6 | Вернуть изменения launcher и bootstrap только совместно с проверкой ограничения DBHub. Для оперативного отключения исключить DBHub из конкретного запуска. См. D10 |
| 7 | Отключить ECC SessionStart в `/hooks`. При откате регистрации согласованно отменить относящиеся к ней handler, тесты и проверки. См. D11 |
| 8 | Убрать ссылку и карту технической памяти ECC. Сохранить первичные проектные ADR, glossary и runbooks. См. D12 |
| 10 | Проверки выполнены в отдельных рабочих деревьях. Записи этапа можно вернуть адресно. Ссылку в начале DECISIONS.md сохранять валидной для чистого дерева |

## D15. Проектная поставка полного ECC

Для расширения сохраняется базовая версия ECC 2.2.3 и полный SHA из существующего манифеста ссылок. Обновление upstream рассматривается отдельно от расширения состава. Перенос охватывает всё дерево релиза как источник. Для активного подключения каждого компонента нужен проверенный интерфейс Codex и совместимость с правилами NaPare.

Выбран проектный marketplace в `.agents/plugins/marketplace.json` и управление включением через `.codex/config.toml` доверенного проекта. Реализация и проверка с локальными клиентами относятся к этапу Р2. Команда upstream `codex plugin add ecc@ecc` меняет пользовательскую регистрацию, поэтому она не используется как проектный установщик. [Публикация плагина для репозитория](https://developers.openai.com/plugins/build/plugins#enable-or-disable-a-plugin-for-a-repo).

| Слой | Решение для переноса |
| --- | --- |
| Нативный манифест | Проверить проектную сборку манифеста на изолированном дереве. Сохранить ресурсы, необходимые его путям |
| Skills и роли | Сверить весь каталог. Для совпадающих имён сохранить действующие профили и дать ECC отдельное имя либо записать явное соответствие |
| Команды, правила и workflows | Для каждого определить нативную точку входа или адаптацию. Профили других клиентов хранить как исходную справку |
| MCP | Текущую запись Chrome DevTools использовать как проектный эквивалент. Остальные серверы сверять по транспорту, доступу и побочным эффектам, включая внешний перенос данных и оплату |
| Hooks | Разобрать зависимости и записи bootstrap. Проверить исполняемые действия и доверие Codex по отдельности. Текущий локальный hook NaPare сохраняется до успешного сравнения |
| Память и отдельные runtime | Сверить с технической памятью NaPare, правилами хранения и требованиями авторизации. Классифицировать совместимость и вести ссылку на исходную функцию |

В исходном дереве обработчик `SessionStart` использует `PLUGIN_ROOT`, прокидывает его в `CLAUDE_PLUGIN_ROOT` для bootstrap и может искать конфигурацию Claude. Покрытие веток разрешения пути и реальных записей требуется на Р4. Формат нативных ролей проверяется отдельно от манифеста плагина. [Проектные агенты Codex](https://learn.chatgpt.com/docs/agent-configuration/subagents#custom-agents).

### Реализованный проектный способ

Codex 0.146.0 обнаружил проектную запись через app-server. Флаг включения проекта не создал пользовательскую регистрацию. Поэтому рабочие точки входа установлены в `.agents/skills` и `.codex/agents`. Project marketplace представляет пакет и инструкцию. Его отдельная регистрация не нужна для проектных Skills или ролей. [Порядок установки и откат](FULL-TRANSFER.md).

Пробный прогон с неявным вызовом всех адаптеров вытеснил `napare-qa` из подсказки модели. Для 421 адаптера зафиксирована политика явного вызова. Общий входной Skill `ecc-catalog` остаётся виден модели. [Настройка доступности Skills](https://learn.chatgpt.com/docs/build-skills#optional-metadata).
