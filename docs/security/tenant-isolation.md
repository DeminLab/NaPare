# Изоляция данных вузов

Дата снимка: 22 октября 2026. Справочник для разработчика и оператора. Статус: реализация и локальная проверка в процессе; состояние production этим документом не подтверждается.

## Границы доступа

`universityId` для учебных маршрутов берётся из проверенного пользователя, а не из произвольного тела или query. ID пары, группы, пользователя и заявления не является ID вуза. Ресурсные методы загружают объект в своём вузе либо проверяют вуз связанной сущности. Личные записи дополнительно ограничены `userId`, преподавательские — своим преподавателем, кураторские — активными назначениями.

Платформа управляется отдельно: сохранённый grant определяет разрешение, доступные сервисы и `universityIds`. `NULL` означает глобальную область, `[]` — отсутствие вузов, список UUID — выбранные вузы. Основная роль разработчика сама по себе не даёт доступа к чужим данным. Карьерные данные также требуют проверки членства в компании, партнёрства и допуска; это не академическая роль с глобальным доступом.

Исходники: [JWT guard](../../apps/backend/src/common/guards/jwt-auth.guard.ts), [контекст запроса](../../apps/backend/src/common/tenant/tenant-context.ts), [проверка привязки](../../apps/backend/src/common/tenant/require-university.ts), [права платформы](../../apps/backend/src/platform/platform.service.ts).

## RLS на соединении PostgreSQL

[Миграция 29](../../apps/backend/src/migrations/1700000000029-TenantRowSecurity.ts) включает `ENABLE` и `FORCE ROW LEVEL SECURITY` для каждой существующей таблицы текущей схемы со скалярной колонкой `universityId` либо `university_id`. Обязательные `RESTRICTIVE`-политики ограничивают SELECT, INSERT, UPDATE и DELETE; чужая permissive-политика не отменяет эту границу. UPDATE проверяет область новой строки через `WITH CHECK`, поэтому нельзя перенести свою запись в другой вуз или снять её привязку. SELECT с блокировкой строки доступен при праве чтения и не даёт права изменить строку.

[Обёртка QueryRunner](../../apps/backend/src/common/tenant/tenant-database.ts) устанавливается для DataSource приложения. Она охватывает уже внедрённые Repository, QueryBuilder, обычный EntityManager, `DataSource.query()` и менеджеры явных TypeORM-транзакций. Для каждой SQL-команды `set_config(..., true)` задаёт `app.university_id`, `app.actor_id` и capabilities на **том же соединении**, которое исполняет команду. Внутри существующей транзакции её commit/rollback остаются у вызывающего сервиса; вне её создаётся короткая транзакция одной команды. Одновременные команды одного runner последовательно устанавливают свой scope. SSE не удерживает транзакцию до закрытия HTTP-соединения. SQL `stream()` отклоняется, пока у него нет отдельной реализации безопасного времени жизни scope.

Отсутствие пользователя означает отсутствие доступа к строкам вузов. SUPERADMIN и DEVELOPER не получают SQL-обхода по названию роли. При старте backend проверяет `NOSUPERUSER NOBYPASSRLS` **до** synchronize/migrations, затем проверяет RLS-покрытие всех tenant-колонок. Новая таблица без обязательных политик останавливает запуск. В режиме synchronize те же политики применяются после синхронизации; в production их устанавливает миграция.

Узкие исключения реализованы явно:

| Операция | Разрешённая область |
| --- | --- |
| Пароль, проверенный JWT/refresh и проверенные MAX initData | Чтение одной строки users по точному id/email/MAX ID; сопоставление MAX после проверки пароля — запись только проверенного id |
| Создание работодателя | Новая строка users с заранее выделенным UUID и ролью employer; нет чтения остальных пользователей |
| Права платформы | Только после чтения сохранённого grant/owner: таблицы конкретного permission, отдельно read/write, `NULL`/`[]`/UUID-список. Эта область заменяет обычный вуз актёра |
| Межвузовская компания | Активное собственное career_membership даёт доступ только к задачам/партнёрствам своей компании; профиль, допуск и пользователь кандидата доступны после его отклика на задачу этой компании. Управление членством требует доказанного владельца конкретной компании |
| Напоминания о сроках | Глобально только чтение pair_spaces/lessons; публикация событий и создание уведомлений ограничены вузом конкретной пары |
| Offline owner bootstrap | Только точное email существующего аккаунта; команда не создаёт и не повышает пользователя |
| Offline provisioning преподавателей | Только users/lessons выбранного `--university-id`; dry-run не получает write capability |
| Тестовые фикстуры | Только disposable локальная БД; отдельный Proxy для seed/assertions выдаёт явный scope. HTTP-запросы используют реальный защищённый DataSource |

Политики дополняют объектные проверки сервисов. У дочерних таблиц без собственной tenant-колонки нет прямой политики из этой миграции: доступ к ним ограничивают проверенные родительские объекты и SQL joins к защищённым таблицам. Custom GUC являются доверенным каналом приложения, а не защитой от администратора PostgreSQL или произвольного выполнения SQL с DDL-правами.

## Развёртывание RLS

Сначала сделайте резервную копию и проверьте миграцию на отдельной копии БД. Не запускайте backend от `postgres`, superuser или роли с `BYPASSRLS`: запуск теперь намеренно отклоняется. Для production используйте отдельного владельца схемы для миграций и runtime-роль без владения таблицами. Пример создания ролей администратором PostgreSQL; пароли задаются интерактивно и не попадают в репозиторий:

```sql
CREATE ROLE napare_migrator LOGIN NOSUPERUSER NOBYPASSRLS;
CREATE ROLE napare_runtime LOGIN NOSUPERUSER NOBYPASSRLS;
\password napare_migrator
\password napare_runtime
GRANT CONNECT ON DATABASE napare TO napare_migrator, napare_runtime;
GRANT USAGE, CREATE ON SCHEMA public TO napare_migrator;
GRANT USAGE ON SCHEMA public TO napare_runtime;
```

На существующей БД миграционная роль должна владеть конкретными таблицами приложения и создаваемыми функциями. Перенос владения выполняется администратором после инвентаризации объектов; не используйте общий `REASSIGN OWNED` для посторонних объектов. Runtime-роль не должна получать роль владельца, `CREATE` на схему либо право менять RLS. После миграций выдайте DML-права и настройте права будущих объектов:

```sql
GRANT SELECT, INSERT, UPDATE, DELETE ON ALL TABLES IN SCHEMA public TO napare_runtime;
GRANT USAGE, SELECT ON ALL SEQUENCES IN SCHEMA public TO napare_runtime;
ALTER DEFAULT PRIVILEGES FOR ROLE napare_migrator IN SCHEMA public
  GRANT SELECT, INSERT, UPDATE, DELETE ON TABLES TO napare_runtime;
ALTER DEFAULT PRIVILEGES FOR ROLE napare_migrator IN SCHEMA public
  GRANT USAGE, SELECT ON SEQUENCES TO napare_runtime;
```

Миграции запускаются из корня репозитория до старта новой версии backend. CLI [database.config.ts](../../apps/backend/src/config/database.config.ts) использует `DB_*`; задайте host, port, database, username миграционной роли и её пароль через защищённое окружение процесса. Не вставляйте значения паролей в shell history:

```powershell
pnpm --filter @napare/backend typeorm:migration:run
```

После успешных миграций запускайте production backend с `DATABASE_URL` runtime-роли либо соответствующими `DB_*`. Существующая настройка `migrationsRun` сохраняется: при предварительно выполненных миграциях у runtime-процесса нет ожидающих DDL-операций. Релизы с новыми миграциями сначала выполняет migrator. Проверка старта, авторизации и двух вузов на сервере остаётся отдельной процедурой; локальные результаты ниже её не заменяют.

Тест создаёт собственные `tenant_test_rls_*` database/role, использует NOSUPERUSER NOBYPASSRLS-владельца таблиц, затем удаляет только созданные объекты. Не указывайте production или общую рабочую БД:

```powershell
pnpm --filter @napare/backend exec jest --config ./test/jest-e2e.json tenant-rls --runInBand
```

Локально PostgreSQL 18 подтвердил 11 сценариев: FORCE для владельца, camel/snake-колонки, отсутствие scope, все основные TypeORM-пути, write/move запреты, rollback, 20 параллельных запросов через pool, границы grant/auth/company, readonly row locks, обязательность новых политик и устойчивость к добавленной permissive-политике. Это проверка отдельной disposable БД, не production.
