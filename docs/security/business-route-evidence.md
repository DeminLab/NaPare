# Наблюдаемые бизнес-маршруты в E2E

25 октября 2026. Инструмент аудита P0-1: связывает AST-инвентаризацию с фактическими HTTP-ответами тестовых AppModule. Это перечень наблюдений, **не verdict безопасности и не процент выполнения цели**. Предметные доказательства с положительным Б/отрицательным А и проверкой строк описаны [отдельно](business-tenant-probes-2026-10-25.md).

## Сбор

[Test-only middleware](../../apps/backend/test/http-route-evidence.ts) подключён к curation fixture (ею пользуются также platform и feature suites) и app.e2e-spec. Он выключен без `BUSINESS_ROUTE_EVIDENCE_FILE` и запрещён вне NODE_ENV=test. Guard-probe серверы и отдельные parser-серверы этим helper не инструментируются. Прямые service/SQL-вызовы в HTTP-отчёт не входят.

Запись делается один раз после finish либо close, если заголовки уже отправлены. Это позволяет учитывать закрываемый клиентом SSE без двойной записи обычного ответа. Статус такого потока подтверждает отправленные заголовки, а не полноту/правильность всех событий. Запись содержит только следующие поля:

| Поле | Состав |
| --- | --- |
| method/path | Метод и объявленный Express route template, без подставленных ID/query/originalUrl |
| status | Фактический код ответа |
| role | Enum роли либо anonymous/other; не имя пользователя |
| scope | primary/secondary для двух вузов fixture, other/none; UUID не записывается |
| suite | Только basename E2E-файла |
| caseId | Хеш названия test/setup; само название и параметры не сохраняются |

Тела, заголовки, bearer/refresh, пароли, endpoint push, IP, email и содержимое ответов не записываются. JSONL разрешён только внутри workspace `output/`; в Git он не включается. Это данные синтетических тестов, не production-телеметрия.

## Отчёт и CI artifact

[Генератор](../../scripts/report-business-route-evidence.cjs) проверяет закрытую схему каждой строки и роли по reviewed baseline, нормализует имена path parameters и транспортную метку AST `GET/SSE` в HTTP GET, затем сопоставляет наблюдения с текущим inventory. Неизвестные шаблоны перечисляются отдельно. В отчёте для каждого объявления есть число ответов, коды, роли, buckets вузов и ссылки-коды контекстов `suite:caseId`; отсутствующие наблюдения явно видны.

В job Backend E2E CI задаётся `BUSINESS_ROUTE_EVIDENCE_FILE=output/business-route-evidence.jsonl`. После тестов даже при их ошибке выполняется генератор с `--require-evidence`: полностью пустой сбор не проходит. Artifact `e2e-test-report` содержит обычный Jest log и только три точных файла evidence: JSONL, JSON и Markdown. Весь output-каталог не публикуется. JSON содержит проверенные публичные GITHUB_SHA/GITHUB_RUN_ID; PR SHA может быть synthetic merge commit. Локальный запуск помечается local-unpinned.

```powershell
$env:BUSINESS_ROUTE_EVIDENCE_FILE = 'output/business-route-evidence.jsonl'
# Запустить выбранный настоящий HTTP/PG suite на новой разрешённой test DB.
node scripts/report-business-route-evidence.cjs --require-evidence
```

Перед отдельным сбором использовать новый JSONL-файл внутри output либо удалить только свой прежний файл: append не отделяет повторные запуски автоматически. Для нестандартного имени передать одно и то же значение env тестам и генератору. Отчёт JSON/MD всегда создаётся в output с фиксированными именами.

## Что наблюдение не доказывает

Ответ 200 может быть пустым; 400 — ошибкой DTO; 403 — отказом guard до handler; 404 — отсутствующим fixture. Наличие 200 и 403 у шаблона не связывает их в корректную пару Б/А. Поэтому отчёт не помечает маршрут как изолированный/покрытый. Setup-запросы тоже включены; caseId не является числом тестов. Отсутствие строки может означать неинструментированный fixture, а не обязательно отсутствие любых тестов.

Для закрытия каждого бизнес-маршрута нужен разбор конкретного сценария: существующий объект Б, допустимый актёр Б, корректное тело, смысл отказа/пустого ответа А и проверка неизменности данных. Проверки отдельных состояний/ролей не переносятся автоматически на остальные. При красном CI artifact содержит также наблюдения неуспешного запуска; его нельзя выдавать за passed evidence. CI не разрешает подключение новых вузов по одному числу наблюдений.

Первый локальный сбор одного tenant suite: 100 HTTP/PG passed, 217 ответов, 76 объявлений из inventory375 наблюдались, 299 не наблюдались этим запуском, неизвестных шаблонов 0. Это **только один suite**, не итог полного E2E CI и не заявление, что остальные маршруты не проверяются другими suites. Полный результат CI фиксируется отдельно в журнале.

После учёта close для SSE и нормализации GET/SSE повтор под TZ=UTC: 100 passed, 219 ответов по 77 объявлениям, 298 без наблюдений этого suite, неизвестных шаблонов 0. Оба SSE-запроса записаны ровно по одному разу; обычные ответы не удвоены. Четыре отрицательных проверки генератора отвергли пустой сбор, лишнее поле, повреждённый JSON и недопустимый status без вывода значения неверного входа.
