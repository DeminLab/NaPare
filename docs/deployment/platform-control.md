# Установка управления платформой

Операционная процедура, 16 октября 2026. Выполняется оператором сервера; локальная реализация не устанавливает агент и не назначает владельца production автоматически.

## Первоначальный владелец

Сначала примените миграцию `1700000000021` штатным запуском backend. Существующие пользователи и роли сохраняются. Затем внутри backend-контейнера, где уже доступны DB-переменные, выполните:

```sh
node dist/platform/bootstrap-owner.js --email existing-owner@example.org
```

Вместо примера укажите подтверждённый email владельца. Команда требует ровно один существующий активный аккаунт developer/superadmin, сохраняет его UUID и отказывается заменять уже назначенного владельца. Она не создаёт пользователей, не повышает роль, не запускает миграции. Email не является последующим условием доступа. Смена email не передаёт владение другому аккаунту. Не публикуйте дампы настроек и персональные адреса в репозитории.

## Host-агент

Нужны Linux с systemd, Node.js 20+, Docker Compose и отдельный системный пользователь `napare-control` с группой `napare-control` и дополнительной группой docker. Членство docker даёт процессу широкие права на хосте: защитите код агента, checkout и EnvironmentFile от записи со стороны непривилегированных пользователей. Предоставьте агенту доступ на чтение checkout и `.env`, запись в Docker build cache и собственное хранилище состояния. Не выдавайте ему SSH-доступ для входа.

1. Установите `infrastructure/control/napare-control.service` в systemd. Исправьте `/opt/NaPare` и путь Node под реальную установку.
2. Создайте `/etc/napare-control.env` с правами root/napare-control 0640. Значения: `CONTROL_REPO` (абсолютный checkout), `CONTROL_PROJECT` (точное имя уже существующего Compose-проекта), `CONTROL_COMPOSE_FILES` (тот же набор Compose-файлов через запятую, включая control overlay), `CONTROL_SECRET` (отдельный случайный секрет минимум 32 символа), `CONTROL_SOCKET=/run/napare-control/agent.sock`, `CONTROL_STATE_DIR=/var/lib/napare-control`.
3. В защищённом Compose-окружении задайте `PLATFORM_AGENT_SECRET` тем же секретом и `PLATFORM_AGENT_GID` числовым GID группы napare-control. Эти значения нужны и окружению агента при повторном запуске Compose; при хранении в checkout `.env` не коммитьте его.
4. Включите unit через systemctl daemon-reload и enable --now napare-control. Проверьте unit и права сокета 0660, каталога 0750. systemd StateDirectory сохраняется между запусками. Не удаляйте каталог заданий при обновлении приложения.
5. Добавьте `-f docker-compose.control.yml` к **существующему** набору Compose-файлов и используйте прежнее project name при обновлении backend. Overlay монтирует только каталог Unix socket read-only и добавляет числовую группу. Не монтируйте docker.sock в backend.

Секрет агента и секрет API должны совпадать. Не используйте JWT_SECRET вместо отдельного CONTROL_SECRET. Не публикуйте сокет/управляющий порт наружу. При ротации обновите оба процесса вместе. Базовые Compose-файлы не заменяются overlay; потеря production overlay или смена project name может создать другой стек.

## Приёмка на сервере

Проверьте `docker compose ... config --quiet`, состояние unit/сокета, health API и открытие `/developer/control` владельцем. Начните с логов и рестарта некритичного frontend-сервиса. Проверьте реальное состояние контейнера, завершение задания и аудит. Затем выдайте тестовому разработчику только один сервис и убедитесь, что остальные запрещены API. После ребилда backend проверьте восстановление API и сохранение операции. Рестарт PostgreSQL/Redis/Nginx может прервать работу пользователей; он требует отдельного осознанного действия в панели.

Пока эта приёмка не выполнена, нельзя считать управление установленным на production. В текущем локальном окружении Docker engine недоступен, проверялись API/БД/транспорт с имитацией Docker-команд.
