# Эксплуатация, резервное копирование и восстановление NaPare

Практическая инструкция для оператора. Состояние реализации на 22 октября 2026: скрипты и шаблоны готовы к настройке; установка таймеров, внешнее хранилище, production и доставка алертов требуют отдельной проверки оператором. Эти процедуры не запускают production автоматически.

## Ежедневная зашифрованная копия

Исполняемый источник: [postgres-recovery.cjs](../../scripts/postgres-recovery.cjs). Требуются Node.js 20+, `pg_dump`, `pg_restore`, `psql` версии не ниже major-версии сервера и настроенный `rclone`. Дамп PostgreSQL не включает файлы attachments/uploads, конфигурацию сервера, роли кластера и секреты: их резервирование организуйте отдельно. Никогда не сохраняйте открытые секреты в Git.

1. На машине резервирования создайте отдельную системную учётную запись `napare-backup`, каталог `/etc/napare` и state-каталог `/var/lib/napare-backup` с доступом только этой учётной записи и оператору. Храните staging на зашифрованном диске. На Linux права каталогов — `0700`, файлов с секретами — `0600`; на Windows ограничьте ACL конкретной служебной учётной записью и администратором.
2. Создайте роль БД для полного чтения резервируемых таблиц. При FORCE RLS ей нужен BYPASSRLS, иначе полный дамп завершится ошибкой. Не используйте эту роль для веб-приложения. Ограничьте доступ в `pg_hba.conf` машиной резервирования и TLS. Учтите sequences и новые таблицы при выдаче read-only прав. Скрипт не создаёт роли и не меняет production.
3. Вне репозитория создайте `/etc/napare/backup.pgpass`: `host:port:database:user:password`. Экранируйте двоеточия и обратную косую черту по правилам libpq. На Linux используйте `chmod 600`. Не передавайте пароль в аргументах процесса, `PGPASSWORD` или URL.
4. Создайте случайный бинарный ключ из 32 байтов. Например, оператор может выполнить следующую команду из доверенной административной сессии, после чего ограничить владельца и права файла:

```bash
umask 077
openssl rand -out /etc/napare/backup.key 32
```

Ключ никогда не выводится в логи. Сохраните его вторую копию в отдельном защищённом хранилище с проверенной процедурой доступа: потеря ключа означает потерю восстановления. Храните архивы по периодам ключей; при ротации не удаляйте старый ключ, пока нужны соответствующие копии.

5. Настройте именованный rclone remote на **другой машине/внешнем объектном хранилище**. Разрешены прямые типы `sftp`, `s3`, `b2`, `azureblob`; local/alias/crypt/mount не принимаются. SFTP должен проверять host key; объектное хранилище должно использовать TLS. Credentials rclone лежат вне репозитория в `/etc/napare/rclone.conf`. Примените отдельные права, versioning/immutability и retention на стороне хранилища. Рекомендуемая отправная точка хранения — 35 ежедневных и 12 месячных копий; оператор утверждает срок по требованиям вуза.
6. Скопируйте [backup.environment.example](../../deploy/operations/backup.environment.example) в `/etc/napare/backup.environment`, замените значения. `BACKUP_DESTINATION=archive:napare/daily` — явное назначение. `BACKUP_OFFSITE_ACK=destination-is-on-another-machine` подтверждает проверку оператором. Скрипт отвергает известные локальные адреса, но не может доказать физическое размещение удалённого DNS-адреса.

Переменные `PGHOST`, `PGPORT`, `PGDATABASE`, `PGUSER`, `PGPASSFILE`, `BACKUP_KEY_FILE` обязательны для обеих операций. Для backup обязательны `BACKUP_WORK_DIR`, `BACKUP_DESTINATION`, `BACKUP_OFFSITE_ACK`. `PG_BIN_DIR` позволяет указать каталог PostgreSQL tools, `RCLONE_BIN` — путь rclone, `RCLONE_CONFIG` — конфигурацию rclone. `PGHOSTADDR`, `PGSERVICE`, `PGPASSWORD` запрещены, чтобы соединение не обходило явно заданную конфигурацию.

7. Запустите один контролируемый backup с окружением служебной учётной записи:

```bash
set -a
. /etc/napare/backup.environment
set +a
node /srv/NaPare/scripts/postgres-recovery.cjs backup
```

Успех — exit 0 и JSON с `status: ok`, `verifiedOffsite: true`, именем артефакта. `pg_dump --format=custom` потоком шифруется AES-256-GCM; открытый дамп на диск не записывается. Каждый архив получает случайный nonce. После загрузки скрипт читает ciphertext обратно и сравнивает SHA-256. Только после совпадения локальная зашифрованная копия удаляется. При сбое передачи она остаётся в staging для расследования; не считайте её внешним бэкапом. Ошибки дочерних программ не печатаются, чтобы не раскрыть секреты. Проверяйте доступ и инструменты отдельной закрытой диагностической сессией.

8. Проверьте пути и пользователей в [napare-backup.service](../../deploy/operations/napare-backup.service) и [napare-backup.timer](../../deploy/operations/napare-backup.timer), установите их в `/etc/systemd/system/` и только после успешного ручного прогона включите таймер:

```bash
sudo systemctl daemon-reload
sudo systemctl enable --now napare-backup.timer
sudo systemctl list-timers napare-backup.timer
sudo journalctl -u napare-backup.service --since today
```

Расписание — каждый день 01:00 UTC плюс случайная задержка до пяти минут. `Persistent=true` выполняет пропущенный запуск после старта. Это шаблон: системные пользователи и каталоги не создаются репозиторием. На Windows используйте отдельную Task Scheduler задачу с теми же переменными и проверкой exit code.

## Ежемесячное восстановление на отдельной машине

Выполняйте на изолированном recovery-хосте без production-секретов и сетевого доступа к production БД. Скрипт соединяется только с loopback, отказывается от `NODE_ENV=production`, требует префикс `napare_restore_` у БД и пользователя, проверяет фактическую identity, отсутствие SUPERUSER/CREATEDB/CREATEROLE, специальный comment и отсутствие пользовательских таблиц. Он не использует `--clean`, не удаляет БД и не выполняет восстановление в production. Не назначайте этот префикс и маркер рабочим базам.

1. Скачайте **конкретный последний успешный архив** из внешнего хранилища на recovery-машину. Не восстанавливайте непроверенный staging. Получите ключ по независимой процедуре. Каталог и временный диск должны быть зашифрованы и доступны только оператору/служебной роли; во время восстановления появляется открытый временный дамп, который удаляется в `finally`. После аварийного завершения процесса проверьте и удалите оставшиеся `napare-restore-*` в закрытом temp-каталоге.
2. Администратор recovery-кластера создаёт пустую базу и выделенную роль. BYPASSRLS разрешён только этой изолированной роли для восстановления архивов с FORCE RLS:

```sql
CREATE ROLE napare_restore_drill LOGIN NOSUPERUSER NOCREATEDB NOCREATEROLE BYPASSRLS;
-- Задайте пароль отдельной защищённой командой psql \password.
CREATE DATABASE napare_restore_drill OWNER napare_restore_drill TEMPLATE template0;
COMMENT ON DATABASE napare_restore_drill IS 'napare:isolated-restore';
```

3. Настройте [restore.environment.example](../../deploy/operations/restore.environment.example), приватный `restore.pgpass` и `RESTORE_BACKUP_FILE` на скачанный архив. `RESTORE_CONFIRM=isolated-empty-test-database` — обязательное подтверждение. Запустите:

```bash
set -a
. /etc/napare/restore.environment
set +a
node /srv/NaPare/scripts/postgres-recovery.cjs restore
```

Сначала проверяется GCM tag **полного** архива, затем `pg_restore --list`; SQL выполняется лишь после аутентификации ciphertext. Восстановление идёт одной транзакцией, с `--exit-on-error --no-owner --no-acl`; сбой SQL откатывает всю транзакцию. Успех — exit 0 и JSON `status: ok`, `restoredTables > 0`. Повторный запуск против непустой базы отклоняется.

4. Проверьте миграции, ожидаемые таблицы и контрольные количества на синтетических/разрешённых данных; поднимите backend с **recovery-конфигурацией** и проверьте health и несколько основных операций. Это отдельная прикладная проверка: наличие таблиц само по себе не доказывает восстановление всей функциональности. В журнале оператора запишите время начала/конца, идентификатор архива, RPO (возраст копии), RTO (время до работоспособности), результат и ответственного. Не включайте персональные строки в журнал.
5. После проверки оператор удаляет/пересоздаёт только эту явно названную тестовую БД для следующего прогона. Скрипт намеренно этого не делает. Автоматизацию [monthly service](../../deploy/operations/napare-restore-drill.service) и [timer](../../deploy/operations/napare-restore-drill.timer) включайте **на recovery-машине**, настроив отдельную загрузку архива и создание новой пустой базы до запуска. Без этих шагов таймер должен завершаться ошибкой, а не переиспользовать непустую базу.

## Health, очередь и оповещения

Публичный URL backend — `/api/v1/health` (контроллер `health` с глобальным API prefix). Проверяется `SELECT 1`, при зарегистрированном `HEALTH_QUEUE_PROBE` — также его `check()`. На каждую зависимость выделено не более трёх секунд ожидания. Это ограничивает HTTP-проверку; underlying driver query должен иметь собственный timeout/pool limits. БД недоступна или queue probe завершается ошибкой/таймаутом — HTTP 503. Нет queue provider — `queue: not_configured`, что не является доказательством наличия рабочей очереди. После подключения очереди экспортируйте probe из её модуля; probe должен делать реальный bounded ping, не отправлять уведомления.

[monitor-health.cjs](../../scripts/monitor-health.cjs) проверяет HTTP и поля зависимостей, принимает прямой JSON и оболочку `{ data: ... }`. Три последовательных сбоя вызывают одно событие `unhealthy`, первый успех после него — `recovered`. Network timeout — пять секунд; HTTP redirect не принимается. Внешний HTTPS webhook получает только `{service,event}` без URL, токенов или пользовательских данных. Ошибка доставки сохраняет прежнее состояние и повторяется на следующей проверке.

1. Разместите монитор на независимой машине. Скопируйте [health.environment.example](../../deploy/operations/health.environment.example), настройте URL API и generic JSON webhook. С `MONITOR_SEND_ALERTS=false` монитор делает реальные health GET, но **не отправляет** сообщения. Запустите его против локального/staging backend и проверьте `event`/exit code.
2. Явно включите `MONITOR_SEND_ALERTS=true` только после проверки получателя. Проведите тест против синтетического 503 в staging: событие на третьем запуске, отсутствие дубликатов, событие восстановления. Установите [health service](../../deploy/operations/napare-health.service) и [timer](../../deploy/operations/napare-health.timer) на мониторинговой машине. Не запускайте несколько экземпляров с одним `HEALTH_STATE_FILE`.
3. Внешняя система должна отдельно контролировать выполнение самого монитора, backup (последний успешный архив не старше 26 часов) и monthly restore (не старше 35 дней). Самопроверка на том же сервере не обнаруживает полное отключение сервера. На service failure настройте уведомление в вашей действующей системе мониторинга; шаблоны не создают внешние аккаунты или получателей.

`SENTRY_DSN` уже используется при запуске backend. Обработчик исключений отправляет сообщение `Backend request failed` для HTTP 5xx, если SDK настроен; поля события ограничены уровнем и тегами `http_status`, `http_method`. 4xx не отправляются, exception text/stack/SQL/body/query/user не передаются этим hook. Перед production проверьте фильтрацию PII также в настройках Sentry и иных SDK integrations.

В интерфейсе Sentry создайте monitor ошибок проекта для нужного environment: например, одна новая ошибка/регрессия и порог ≥ 5 событий за пять минут. Привяжите alert к реальному дежурному получателю, подтвердите доставку на staging. Названия экранов и доступность monitors зависят от установленной версии/тарифа. `SENTRY_DSN` не создаёт alert rules или каналы; без контрольного события нельзя считать алерт настроенным. Не создавайте публичный endpoint для синтетического исключения.

## При падении БД

1. Зафиксируйте время инцидента, health HTTP-код, состояние процесса БД, disk space/inodes и закрытые server logs. Не публикуйте DSN и SQL с данными. Ограничьте повторные записи/фоновые задания на время восстановления.
2. Проверьте сеть, DNS, TLS, срок сертификата, лимит подключений, диск и блокировки. Если данные целы, восстановите доступность службы по штатной процедуре хостинга и повторите health.
3. При подозрении на повреждение сохраните исходный volume/снимок, выберите последний проверенный backup. Сначала восстановите на изолированном хосте по процедуре выше. Оператор отдельно согласует RPO и переключение приложения на восстановленную БД.
4. После переключения проверьте миграции, health, login и ключевые операции; проверьте отложенные задания перед их возобновлением. Назначьте разбор причины и проверьте, что новый backup завершился вне сервера.

## При неудачной миграции

1. Остановите выпуск и зависимые записи. Не повторяйте миграцию бесконечно и не правьте вручную migration history.
2. Сверьте текущий backend commit, применённые миграции и полный лог. Проверьте, была ли миграция транзакционной: DDL/операции вне транзакции могли частично выполниться.
3. Воспроизведите на изолированной копии: либо безопасная forward-fix миграция, либо проверенный `down` с оценкой потери данных. Возврат старого backend образа допустим лишь при совместимой схеме.
4. Если схема/данные повреждены, используйте проверенный backup и согласованное переключение; рабочую базу не перезаписывайте этим drill-скриптом. После исправления повторите целевые тесты, migration run и health.

## При утечке ключа или токена

1. Определите тип: JWT/refresh secret, DB credentials, webhook, rclone или backup key. Отключите скомпрометированный доступ, сохраните audit evidence без копирования секретов в чат/Git.
2. Выпустите новый секрет в защищённом хранилище, обновите зависимые службы и проверьте новый доступ; отзовите старый. При утечке JWT/session credentials примените действующий механизм отзыва сессий и контролируемую повторную авторизацию.
3. При утечке backup key считайте доступные злоумышленнику старые архивы раскрытыми. Новый ключ защищает будущие копии; смена ключа не отзывает уже скачанные данные. Ограничьте доступ к старым архивам, примените новый ключ/версионирование и выполните новый off-server backup и drill.
4. Оцените объём инцидента с ответственным за данные и юристом, выполните действующие процедуры уведомления и сохранения доказательств. Сроки определяет применимая процедура, не этот runbook.

## Проверки и первоисточники

Перед допуском восстановленной копии к пользователям и внешним отправкам выполняется [сверка последующих удалений аккаунтов](../privacy/external-copies-procedure.md). Текущий restore script не выполняет replay tombstones/очистки автоматически. Если журнал неполон или проверенная процедура replay не готова, восстановление остаётся в карантине.

```powershell
node --test scripts/test-postgres-recovery.cjs
pnpm --filter @napare/backend exec jest src/health.controller.spec.ts src/common/filters/http-exception.filter.spec.ts --runInBand
pnpm --filter @napare/backend exec tsc --noEmit
node scripts/verify-ai-documentation.cjs
node scripts/verify-role-workspace-boundaries.cjs
pnpm lint
pnpm lint:docs
```

Unit-проверки не заменяют off-server upload, monthly drill и реальную доставку alert. Подтверждённые результаты локальных запусков фиксируйте отдельно с датой. PostgreSQL указывает, что [pg_dump](https://www.postgresql.org/docs/current/app-pgdump.html) создаёт логическую копию одной БД; параметры восстановления описаны в [pg_restore](https://www.postgresql.org/docs/current/app-pgrestore.html). Credentials — [password file libpq](https://www.postgresql.org/docs/current/libpq-pgpass.html). Передача — [rclone copyto](https://rclone.org/commands/rclone_copyto/). Настройка оповещений — [Sentry monitors and alerts](https://docs.sentry.io/api/monitors/).

Локальный снимок проверки 22 октября 2026: на отдельном disposable PostgreSQL 18 кластере выполнен реальный `pg_dump` → AES-GCM архив → `pg_restore`. Проверены две синтетические записи, сохранение FORCE RLS и отказ при повторном восстановлении в непустую БД; кластер затем остановлен. Девять safety/unit-проверок скриптов и семь Jest-проверок health/exception filter прошли. Этот прогон не проверял внешний rclone remote, systemd runtime, реальную доставку Sentry/webhook, Docker или production.
