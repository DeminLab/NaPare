# Путеводитель по документации НаПаре

Этот файл — карта документации: он указывает, какие документы проверять и обновлять. Источниками фактического поведения остаются код, OpenAPI, миграции и действующая конфигурация; планы и спецификации описывают ожидаемое поведение.

## Первые 15 минут

1. Прочитайте [01_ONBOARDING.md](01_ONBOARDING.md) и [02_GLOSSARY.md](02_GLOSSARY.md).
2. Найдите свой слой в таблице ниже.
3. Перед правкой кода откройте документ модуля из `modules/`, source card и сам код. `project-log/` — историческая хронология, не текущий статус.
4. Перед PR выполните чеклист из [process/definition-of-done.md](process/definition-of-done.md) и обновите нужную документацию в том же PR.

## Карта документов

| Где | Для чего | Что должно быть | Когда обновлять |
| --- | --- | --- | --- |
| `00_START_HERE.md` | Навигация по документации | Точки входа, структура `docs/`, ключевые принципы | При добавлении нового раздела документации |
| `01_ONBOARDING.md` | Старт нового разработчика | Проверенный setup, команды, минимальный путь до первого запуска | При изменении установки, переменных окружения или команд |
| `02_GLOSSARY.md` | Единый язык команды | Термины домена, краткие однозначные определения | При появлении нового бизнес-термина |
| `PROJECT_COLLABORATION.md` | Правила координации проекта | Источники правды, границы ответственности, обязательные проверки | При изменении процесса или ownership |
| `CHANGELOG.md` | Публичная история версий | Релизные изменения, миграции, breaking changes | Перед релизом или merge значимого изменения |
| `modules/<module>.md` | Поведение конкретного модуля | Цель, роли, сценарии, API-ссылки, правила, acceptance criteria, open questions | При изменении логики `auth`, `schedule`, `pair-space`, `absences` и т.д. |
| `api/` | Контракт API | OpenAPI и правила генерации клиента | При любом изменении endpoint, DTO, статуса или авторизации |
| `database/` | Схема и данные | Сущности, связи, миграции, seed-подход | При изменении TypeORM Entity или миграции |
| `architecture/` | Техническое устройство | Диаграммы, границы модулей, стек, модель прав, интеграции | При архитектурном изменении |
| `decisions/` | Необратимые технические решения | Контекст, варианты, решение, последствия, статус | До merge решения, которое сложно откатить |
| `clients/` | Поведение клиентских поверхностей | Пользовательские сценарии, платформенные ограничения, запуск | При изменении web, mobile или MAX Mini App |
| `ui/` | UX и дизайн-система | Tokens, экраны, flow, loading/error/empty states, accessibility | При изменении визуального поведения или user flow |
| `security/` | Безопасность и данные | Модель угроз, роли, персональные данные, меры защиты | При изменении доступа, хранения данных или внешних интеграций |
| `ops/` | Эксплуатация | Docker, CI/CD, мониторинг, rollback, runbooks | При изменении compose, Dockerfile, deploy или observability |
| `process/` | Как команда поставляет изменения | Contributing, DoD, ownership, review, ветки | При изменении командного процесса |
| `legal/` | Юридические тексты | Privacy, terms, согласия и ссылки поддержки | Только с владельцем продукта/юристом |
| `superpowers/specs/` | Сохранённые спецификации отдельных инициатив | Цель, user flows, ограничения, критерии приёмки; проверять дату и статус | Для инициативы, если она активна |
| `superpowers/plans/` | Планы отдельных инициатив | Предполагаемые задачи и проверки; завершённый план не является текущим backlog | Для активной многошаговой задачи |
| `project-log/` | Историческая хронология | Зафиксированные на дату решения и проверки | Не использовать как статус проекта |
| `SHARING_BUNDLE.md` | Правила передачи проекта | Состав архива, исключения, безопасный setup после распаковки | При изменении состава архива или Docker setup |
| `archive/` | Исторический контекст | Старые ТЗ и решения | Не редактировать; использовать только для справки |
| `project-audit.md` | Датированный снимок состояния репозитория | Проверенные файлы/конфигурация и ограничения проверки | При заметном изменении архитектуры или deployment |

## Как выбрать документ для изменения

| Если меняется | Обязательно обновить |
| --- | --- |
| Endpoint, DTO, код ответа, авторизация API | `api/`, документ модуля и соответствующие проверки |
| Entity, миграция, связь таблиц | `database/`, документ модуля |
| Роль, tenant, group или ownership | `security/`, `architecture/roles-and-permissions.md`, документ модуля и проверки доступа |
| Экран или пользовательский сценарий | `clients/` или `ui/`, документ модуля |
| Docker, nginx, CI/CD, переменная окружения | `docs/deployment/production.md`, `ops/`, `01_ONBOARDING.md` или `README.md` |
| Архитектурный компромисс | Новый ADR в `decisions/` и ссылка из затронутого документа |
| Текущая поставка или hackathon scope | Спецификация/план инициативы с датой и статусом; не заменять ими карту текущей реализации |

## Шаблон нового рабочего документа

Каждый новый документ вне `archive/` должен начинаться с понятного заголовка и включать только нужные разделы:

```md
# Название области

## Назначение
Что описывает документ и для кого он нужен.

## Источник правды
Код, OpenAPI, ADR или внешний документ, который имеет приоритет.

## Текущее состояние
Что реализовано, что ограничено, что отложено.

## Правила и сценарии
Конкретное поведение, роли, входы и ожидаемый результат.

## Проверка
Команды, тесты или ручной сценарий, подтверждающие документ.

## Изменения и открытые вопросы
Дата, краткое решение, владелец следующего действия.
```

Не добавляйте пустые разделы. Для ADR используйте существующий формат ADR; для OpenAPI источником правды остаётся контракт, а не дублирующий Markdown.

## Правила для команды

- Один факт — один источник правды. Остальные документы ссылаются на него.
- Не хранить пароли, токены, персональные данные или боевые URL с секретами.
- Не редактировать `archive/` как рабочую документацию.
- Документ должен описывать текущий код, а не желаемую версию. Нереализованные вещи помечаются как `deferred` или `blocker`.
- Новый user flow обязан описывать loading, error и empty states.
- Новое ограничение доступа обязано иметь позитивный и негативный regression test.
- Файл держим компактным: если он приближается к 500 строкам, разделяем по предметным областям.

## Единый формат записи в worklog

```md
- YYYY-MM-DD: <область> — <что изменили>; проверка: `<команда>` — passed. Блокер: <если есть>.
```

Пример исторической записи; `apps/max-miniapp` больше не является текущим клиентом MAX и не запускается стандартными командами `pnpm dev`/`pnpm build`:

```md
- 2026-09-16: MAX Mini App — добавлен static Docker runtime; проверка: `docker compose ... ps max-miniapp` — healthy. Блокер: нужен внешний HTTPS URL.
```

## Перед передачей задачи другому разработчику

1. Укажите точные пути затронутых файлов.
2. Сошлитесь на актуальный spec, plan и worklog.
3. Напишите, что уже проверено, точной командой и результатом.
4. Отделите факты от предположений и открытых блокеров.
5. Не передавайте секреты через Markdown, чат или git.
6. Для передачи копии проекта используйте правила из `SHARING_BUNDLE.md`, а не архив со всем содержимым рабочего каталога.
