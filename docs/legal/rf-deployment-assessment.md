# Размещение данных в РФ и on-premise

Дата: 22 октября 2026. Тип: инженерный вариант размещения и форма приёмки инфраструктуры. Это не подтверждение существующей площадки и не юридическое заключение.

## Доступные варианты

| Вариант | Границы ответственности | Что нужно подготовить | Ограничения |
| --- | --- | --- | --- |
| Установка у вуза | Вуз предоставляет площадку, сетевой доступ, администратора, backup и мониторинг; поставщик сопровождает приложение по договору | Отдельные PostgreSQL/Redis/files/logs, домен/TLS, закрытые data-порты, runtime DB role, процесс обновления/отката, ключи и аварийный доступ | Контроль инфраструктуры у вуза не подтверждает автоматически её соответствие; доступ поставщика отдельно согласуется и журналируется |
| Управляемый хостинг в РФ | Поставщик организует эксплуатацию; вуз определяет учебную обработку по согласованной модели ролей | Договор с конкретной площадкой, адреса/регионы всех копий, договор поручения, SLA, план выхода и возврата данных | Домен .ru, IP-геолокация, рублёвый счёт и Docker не доказывают место хранения |
| Общая многовузовская установка | Оператор определяет общий контур и разделение tenants | Применённая RLS, запрет superuser runtime, persisted scope для технических прав, общая модель угроз, учёт всех субъектов | Scope не превращает общую БД в независимые физические контуры; backup содержит несколько вузов |

Базовая конфигурация [docker-compose.prod.yml](../../docker-compose.prod.yml) описывает PostgreSQL, Redis, приложение и логические volumes. Она переносима на выбранную площадку, но **здесь не изменялась и не запускалась на сервере**. Даже локальный запуск Compose не был бы доказательством страны размещения.

## Реестр площадок, который заполняет оператор

| Компонент | Требуемые сведения / документ | Текущее подтверждение |
| --- | --- | --- |
| Основная PostgreSQL и реплики | Организация, физический адрес/регион, договор, список администраторов | Нет |
| WAL/dump/внешний backup | Площадка, шифрование, владелец ключа, срок/неизменяемость, изолированное восстановление | Локальный код backup — PR 2; реальный storage не подтверждён |
| Redis / очередь | Регион, persistence AOF/RDB, payload состав, TTL/dead-letter | Compose описывает volume; production не осмотрен |
| Файлы и CDN | Провайдер по fileUrl, origin/edge/cache/backups, удаление объекта и ссылки | Модель хранит URL; байты и регион не установлены |
| Логи / APM / аналитика | Сборщик, IP/идентификаторы, фильтрация, срок, страны | Состав production потоков не установлен |
| MAX / Telegram / push / Moodle | Получатели, адреса API, субподрядчики, страны, договоры | Код интеграций есть; юридическая/географическая оценка не завершена |
| Т-Касса | Договор терминала, состав Init/receipt, обработчики, возвраты | PR 4 выключен по умолчанию; настоящий терминал не использовался |
| Администрирование и поддержка | Кто/откуда подключается, MFA/запись действий, временные разрешения | Production доказательств нет |

Внешние интеграции нужно оценивать отдельно от основной БД: локальная БД не исключает отправку идентификаторов, текстов и файлов внешним получателям. Уведомление о трансграничной передаче не подменяет проверку требований к первичной обработке. Применимость конкретных обязанностей сверяет юрист по действующей редакции закона; исходная правовая проверка описана в [оценке ПД](personal-data-assessment.md).

## Процедура технической приёмки

1. Зафиксировать release SHA, схему контуров, договоры и заполненный реестр площадок. Секреты не прикладывать к акту.
2. Подтвердить применение миграций и RLS, отдельную runtime-роль без SUPERUSER/BYPASSRLS; выполнить negative tests двух вузов в изолированной тестовой БД, а не на рабочих данных.
3. Проверить закрытие PostgreSQL/Redis от публичной сети, TLS/доверенные прокси, управление секретами и резервирование ключей. Утвердить отдельный аварийный доступ с аудитом.
4. Настроить шифрованный backup вне основного узла и выполнить restore в помеченный изолированный контур. Записать фактические RPO/RTO, результат health и бизнес-сценария, вернуть сетевые ограничения.
5. Проверить состав логов/очередей/внешних запросов без публикации содержимого ПД. Сверить фактические получатели с договорами и документами.
6. Проверить отключение/удаление аккаунта, сроки по карте и процедуру, предотвращающую возвращение удалённых ПД после restore. Нынешняя деактивация не закрывает этот пункт.
7. Подписать акт ответственными вуза и поставщика только по полученным доказательствам. До этого статус площадки — «не подтверждена».

Порядок обновления, роли доступа, окна работ, поддержка, RPO/RTO и допустимость простоев становятся условиями договора; численные гарантии без нагрузочного и восстановительного испытания не обещаются. Серверные реквизиты у владельца в этой задаче не запрашивались и production не изменялся.
