# UX-аудит страниц NaPare и техническое задание на улучшения

**Дата:** 20 ноября 2026 г.
**Область:** активные web-приложения portal, student, staff, admin, developer.
**Тип документа:** датированный UX-аудит локального демо и проект ТЗ; не отчёт о production.

## Цель и границы

Проверить структуру и удобство маршрутов с точки зрения пользователя на мобильном и desktop размерах, сверить увиденное с исходниками, затем сформулировать проверяемые улучшения. Инвентарь включает все 76 активных экранных URL-шаблонов; служебные обработчики, API и legacy `apps/web` в эти 76 не входят.

Проверены два размера: **390×844** (mobile) и **1440×1000** (desktop). На каждом маршруте открывалась конечная страница после редиректов. Для portal просмотрены публичные страницы и страницы входа; закрытые маршруты всех ролей запрошены, однако без тестовых пользовательских аккаунтов большая часть завершилась общим экраном входа. Поэтому таблицы точно фиксируют наблюдённый результат, но не выдают его за проверку внутреннего рабочего экрана.

Локальный demo Compose был доступен: **9 из 9 контейнеров healthy**, `/api/v1/health` сообщил `status=ok`, `database=ok`, `queue=not_configured`; применены 52 миграции. В локальной базе есть один bootstrap-вуз и **0 пользователей, групп и занятий**. Учётных записей для тестовых ролей нет. Выход внешней сети отключён; получение расписания из внешней интеграции не проверялось. Действия с реальными данными, отправка форм, полномочия разных ролей, интеграции и межвузовская изоляция этим UX-проходом не подтверждены.

Источники: текущие маршруты и исходники приложений, `AI_CONTEXT.md`, проектная карта и правила безопасности изменений; локальный browser pass через общий вход и доступные публичные страницы; статический анализ кода страниц. Ни плановые документы, ни наличие маршрута сами по себе не считаются доказательством работающего сценария.

## Краткая оценка

- **Публичный portal:** в целом ясная иерархия, узнаваемый вход, хорошие объясняющие блоки и понятный путь регистрации работодателя. Мобильный главный экран не переполняется по ширине. На desktop секция возможностей оставляет одну карточку отдельно во втором ряду; длинная главная повторяет близкие объяснения шагов работы.
- **Страница `/career`:** мобильный снимок показывает сырой английский `Unauthorized` внутри красного сообщения, кнопку «Обновить» и рядом призывы войти/зарегистрироваться работодателем. Состояние доступа объяснено не тем языком и не в той иерархии, которая помогает посетителю выбрать следующий шаг.
- **Публичные входы staff/admin:** отдельные исходники содержат тематические landing pages с ясным CTA. Но общие маршруты через локальный Nginx перенаправляют `/staff` и `/deanery` на закрытые рабочие экраны, далее без сессии — на общий `/login`. В итоге публичные landing pages не достигаются по основным URL.
- **Student:** исходник `/student/` содержит публичную главную, но `StudentShell` требует сессию и перенаправляет на `/login`. Это несогласованность назначения маршрута и его защищающей оболочки.
- **Рабочие пространства:** общий login доступен и не имеет горизонтального переполнения на двух размерах. Реальные внутренние экраны и последовательности действий не удалось увидеть без ролевых аккаунтов и данных. Давать по ним безусловную оценку структуры/деловой логики нельзя.

## Подтверждённые находки

Приоритет означает предполагаемое влияние на доступность основного сценария, а не оценку количества пользователей.

### P1 — согласовать публичные страницы и защиту маршрутов

**Наблюдение:** публичный исходник `apps/web-student/src/app/page.tsx` вложен в layout, где `StudentShell` отправляет пользователя без сессии на `/login`. Аналогично, исходники landing pages staff и admin существуют, однако общие URL `/staff` и `/deanery` через Nginx направляются на рабочие маршруты и затем на общий login. В браузере пользователь не достигает соответствующего публичного объяснения и CTA.

**Риск для пользователя:** посетитель без учётной записи не понимает, что предлагает площадка, кому она предназначена и как получить доступ. Для Student фактическое поведение маршрута расходится с публичным содержимым, которое разработчики ожидают увидеть.

**Требование:** определить единое назначение каждого корневого URL. Для публичного продукта root отображает landing page без сессии, а защищённые функции отдельно требуют входа. Если URL по замыслу закрытый, убрать из него недостижимую public landing page и не объявлять его публичным входом. Сохранить совместимость существующих role routes и серверную проверку авторизации; редиректы Nginx, Next layouts и links должны описывать одну схему.

**Критерии приёмки:** анонимный переход на `/student`, `/staff`, `/deanery` предсказуемо показывает согласованную публичную страницу либо общий вход с объяснением продукта; активная сессия попадает в свой разрешённый workspace; ручной запрос защищённого API без полномочий остаётся запрещённым; прямые ссылки и trailing slash дают тот же ожидаемый результат.

### P1 — локализовать и объяснять состояние доступа на `/career`

**Наблюдение:** на мобильном `/career` API вернул `Unauthorized`, и текст ошибки отображается по-английски. Рядом видны действие «Обновить» и ссылки входа/регистрации, но порядок и объяснение не отделяют отказ API от действия, доступного гостю.

**Требование:** не выводить raw API error пользователю. Для гостя показать локализованное состояние «для просмотра заданий войдите в аккаунт» с приоритетной ссылкой входа. Регистрацию работодателя предложить как отдельный сценарий, если он соответствует этой странице. Для временной ошибки API показывать отдельное понятное сообщение и повторную попытку. Зафиксировать фактический контракт эндпоинта — гостевой список или сессионный — прежде чем менять серверную авторизацию.

**Критерии приёмки:** `401`, `403`, сетевая ошибка и пустой успешный ответ визуально различимы и локализованы; гостю доступно следующее действие; «Обновить» повторяет запрос только при восстанавливаемой ошибке; проверены mobile и desktop, клавиатура и объявление статуса скринридеру; права API не ослаблены.

### P2 — упорядочить длинную публичную главную

**Наблюдение:** на desktop в блоке возможностей одна карточка переносится на следующий ряд без визуально сбалансированной композиции; на длинной главной рядом расположены блоки «Что нужно для начала работы» и «Четыре шага до рабочего дня» с похожей функцией объяснения.

**Требование:** собрать карточки в равномерную сетку на широком экране и логичную одноколоночную последовательность на мобильном. Убрать смысловое дублирование двух блоков: объединить их либо явно разделить предварительные условия и процесс после подключения.

**Критерии приёмки:** ни одна карточка не остаётся случайным orphan-элементом на 1440px; на 390px порядок читается без горизонтального скролла; каждый блок отвечает на отдельный вопрос пользователя; основные CTA видны и не конкурируют.

### P2 — довести обратную связь в действиях и интеграциях

**Основание:** статический просмотр. В `apps/web-student/src/app/(student)/absences/page.tsx` успешная отправка заявления очищает форму и обновляет список, но явное подтверждение успеха не задаётся. В `apps/web-portal/src/app/connections/page.tsx` ошибка обновления статуса MAX поглощается и оставляет состояние `unknown` без причины. Это два разных сценария, где пользователь не получает надёжной обратной связи.

**Требование:** после успешно принятого заявления показать подтверждение с понятным следующим шагом и не считать ошибку успешной отправкой. В статусе MAX различать загрузку, подключён/не подключён, временную ошибку и неизвестный результат; предусмотреть безопасный retry. Не раскрывать технические детали/секреты.

**Критерии приёмки:** заявление имеет явные submitting/success/error состояния; данные формы сохраняются при ошибке; повторная отправка не создаёт дубликат без объяснения; MAX статус содержит понятную причину/повтор только когда это безопасно; состояния доступны с клавиатуры и скринридера.

### P2 — исправить название и ожидаемое действие `/student/attendance/check-in`

**Основание:** статический просмотр: экран сообщал, что история недоступна и следует обратиться к преподавателю; пользовательский сценарий отметки посещения на странице с названием `check-in` не обнаружен.

**Требование:** продуктово выбрать фактическое назначение: либо реализовать разрешённый сценарий отметки и объяснить его условия, либо переименовать/переместить страницу так, чтобы название соответствовало справочному содержимому. Не показывать несуществующую возможность и не обходить серверные правила преподавателя/времени/занятия.

**Критерии приёмки:** название, навигация, заголовок и CTA согласованы; закрытая отметка объясняет причину и следующий шаг; применяются проверки текущего пользователя, занятия и окна отметки; история и пустое состояние не выглядят как поломка.

### P3 — сократить когнитивную нагрузку в developer control

**Основание:** статический анализ: `/developer/control` объединяет 26 операционных вкладок из нескольких семейств. Сам факт числа вкладок не доказывает usability-дефект, но повышает риск затруднённого поиска действия.

**Требование:** сгруппировать действия по работе/ресурсу, показать краткое назначение, роль/область доступа и последствия перед опасным действием; оставить быстро доступными частые задачи. Сохранить существующие API и фактическую авторизацию.

**Критерии приёмки:** представитель developer роли может найти каждую операцию по понятной группе/названию; запрещённое действие не показывается как доступное; подтверждение и итоговая обратная связь присутствуют для разрушительных/широких операций; все 26 прежних операций учтены в карте соответствия.

## Общие требования к реализации и приёмке

- Не менять без необходимости существующие публичные URL, API-контракты, роли, университетские границы данных и бизнес-правила. Если изменение маршрута нужно, добавить совместимое перенаправление и проверить deep links.
- Проверять разрешения на сервере/API. Скрытие кнопки в UI не является авторизацией. В сценариях данных использовать только синтетические университеты, пользователей, группы, занятия и заявления.
- Для каждой изменённой страницы проверять: loading, empty, success, validation error, API 401/403, сетевую/серверную ошибку, retry и повторное действие.
- Desktop 1440px: главная навигация и контент иерархичны, нет сиротских элементов/лишнего дублирования. Mobile 390px: нет горизонтального overflow, CTA доступны, длинные поля/тексты не ломают сетку. Дополнительно проверять промежуточные ширины, особенно 768px.
- Клавиатура: логичный порядок Tab, видимый фокус, Escape/закрытие диалогов, нет ловушек фокуса. Формы имеют programmatic labels; сообщения статуса объявляются assistive technology; ошибки связаны с полями.
- Проверять реальный сценарий роль за ролью: публичный переход → вход → стартовый экран → основное действие → подтверждение/отказ → повторный вход по прямой ссылке. Для каждой роли — разрешённое действие и отказ в чужом ресурсе/вузе.
- Для импорта, заявления и любых действий с побочным эффектом отдельно проверять, что UI сообщает о фактическом принятии сервером; не очищать введённое до подтверждённого успеха.

## Что остаётся непроверенным

1. Структура, визуальная иерархия и удобство закрытых экранов Student, Staff, Admin и Developer для авторизованных пользователей на обоих размерах.
2. Вход/выход и роль-зависимый redirect на тестовых аккаунтах; реальные ошибки неправильного пароля и истечения сессии.
3. Сценарии с данными: расписание, absence, посещаемость, задания, группы, уведомления, модерация/жалобы/отчёты и импорт расписания.
4. Негативные проверки доступа к чужому университету, группе, занятию, пользователю и developer-операциям.
5. Внешние MAX/расписание интеграции, доставка уведомлений, мобильный браузер на устройстве, keyboard/screen-reader поведение и производительность.
6. Юридическая корректность публичной privacy страницы и актуальность контента Team не оценивались.

Текущее прохождение подтверждает только браузерное поведение локального demo и перечисленные статические свойства исходников. Оно не подтверждает acceptance нового ТЗ, deployment или production.
