# ТЗ на улучшение страниц NaPare по ролям

**Дата:** 20 ноября 2026 г.
**Среда:** локальный Docker demo, `http://127.0.0.1:8081`; синтетические аккаунты `example.test`.
**Назначение:** результаты входа во все тестовые роли и маршрутное ТЗ по рабочим страницам. Документ не описывает production и не содержит паролей.

## 1. Что проверено

Через правое окно браузера выполнен вход во все 11 локальных ролей: студент, преподаватель, куратор, декан факультета, заведующий кафедрой, администратор вуза, superadmin, разработчик, работодатель, сотрудник и руководитель карьерного центра. Все вошли в ожидаемый рабочий контекст. Для неверного пароля и внешних провайдеров в этом проходе отдельные проверки не повторялись.

В текущем браузерном окне наблюдения сделаны при его доступном размере около 789×927 CSS px. Это не отдельный мобильный и не широкий desktop viewport. Все страницы не открывались поочерёдно под каждой ролью. Поэтому:

- **«Браузер»** ниже означает фактически увиденное состояние конкретного экрана/роли.
- **«Исходник»** означает маршрут и поведение из кода/предыдущего маршрутного аудита; это основание для требования, но не доказательство визуального дефекта.
- Нулевые списки и пустые расписания в основном отражают пустой synthetic demo. ТЗ требует объяснимые empty states, но не предполагает, что пустота сама по себе — ошибка.
- Полный маршрутный перечень взят из исходников и ранее составленного [базового UX-аудита](UX-AUDIT-2026-11-20.md): 76 URL-шаблонов из того снимка плюс пять публичных страниц, появившихся в текущем рабочем дереве (`/career-center`, `/employers`, `/pricing`, `/schedule`, `/universities`), всего 81 шаблон. Базовый аудит был выполнен до создания локальных ролей; его прежние «login wall / пользователей нет» для текущего состояния устарели. Они сохранены там только как историческая фиксация того прохода.

## 2. Приоритетные общие требования

### P1. Дать каждому стартовому экрану ясный следующий шаг

На студенческом `/student/today` показан свободный день без занятий; преподавателю `/staff/today` — отсутствие занятий; работодателю и центру — пустые списки задач. Это ожидаемо для базы без данных, но каждый пустой экран должен сообщать, почему данных нет, кто может их добавить/назначить и куда перейти. Не показывать пользователю действия, которые его роль выполнить не может.

**Приёмка:** для каждой роли проверены загрузка, ошибка, пустой список и заполненный synthetic сценарий; текст называет источник пустоты и разрешённое действие; обновление не стирает фильтры и выбранный период.

### P1. Показывать фактическую роль и вуз в административных оболочках

В админке пользователи `university_admin` и `superadmin` попали в один и тот же видимый `/deanery/dashboard`; предыдущий маршрутный анализ зафиксировал одинаковую подпись «Сотрудник ВУЗа» для разных ролей. Разделить визуальное обозначение роли и область управления, не ослабляя серверные ограничения. Особенно ясно показывать, когда пользователь находится в пространстве одного вуза.

**Приёмка:** имя роли, текущая область/вуз и доступные действия совпадают с реальными полномочиями; прямой URL и API для чужого вуза остаются запрещены.

### P1. Сделать переходы между близкими ролями предсказуемыми

У преподавателя переход в `/staff/absences` вернул «Нет доступа к очереди обращений», тогда как куратор получил страницу очереди. Отказ — корректный контроль доступа, но пользователю нужен краткий смысл и путь к доступному действию.

**Приёмка:** отказ объясняет отсутствие полномочия, указывает подходящую роль/контакт или возвращает на доступную страницу; скрытие ссылки дополняет, но не заменяет проверку API.

### P2. Улучшить плотность навигации на мобильных и крупных рабочих местах

У студента часть действий скрыта в «Ещё разделы», у staff основные рабочие разделы и коммуникации разнесены, у admin на мобильном набор быстрых ссылок уже desktop-меню, developer/control содержит 26 вкладок. Это требует ролевой приоритизации и сохранения текущего раздела, а не механического копирования desktop-меню.

**Приёмка:** на ширинах 390, 768 и 1440 px доступны главные ролевые сценарии, активный пункт заметен, нет горизонтальной прокрутки, второстепенные пункты можно найти по смысловой группе.

### P2. Подтверждать результат изменения данных

Для отправки заявления об отсутствии статический аудит не нашёл явного подтверждения успеха; проверить и обеспечить аналогичную обратную связь в формах профиля, посещаемости, вакансий, задач, модерации, импорта и настроек.

**Приёмка:** показывать отправку/успех/ошибку; при ошибке сохранять введённые значения; при успехе сообщать, что сохранено и что дальше; повтор не создаёт дубликат без явного решения пользователя.

## 3. ТЗ по страницам

Общие требования responsive, доступности, сохранения API/прав и серверных проверок из раздела 5 распространяются на каждую строку. Если браузерное наблюдение не указано, рекомендация сформулирована как задача уточнить/проверить сценарий и улучшить его при обнаружении проблемы, а не как утверждение о дефекте.

## 5. Общие критерии приёмки

1. Для каждой страницы из таблиц подтвердить desktop 1440×1000, mobile 390×844 и промежуточный 768 px; фактический браузерный проход этого документа эти три ширины не покрывает.
2. Проверить клавиатуру: последовательность Tab, видимый фокус, подписи полей, диалоги и Escape; сообщения статуса доступны screen reader.
3. Проверить состояния loading, empty, populated, validation error, API 401/403, offline/server error, retry и повторное действие.
4. Использовать синтетические данные для каждого пути. Проверить разрешённое и запрещённое действие в каждом tenant-роли; данные одного вуза не видны другой роли без разрешения.
5. Сохранять действующие маршруты и API-контракты, пока отдельное изменение не согласовано архитектурно; server-side авторизацию не заменять скрытием кнопок.
6. Для форм и операций показывать фактически подтверждённый сервером результат. Не трактовать отсутствие данных в demo как подтверждение некорректного алгоритма.

## 6. Что проверено и что осталось

**Подтверждено в локальном браузере:** аутентификация 11/11 синтетических ролей и ожидаемые стартовые контексты; студент today; страницы staff today/week/groups/assignments/attendance и отказ teacher на absence queue; curator absence queue; faculty dean curation; university admin dashboard/users/structure; developer API health; employer tasks/vacancies/applications; career staff tasks/moderation. Ссылки на отчёт и модерацию видны в кабинете центра; различия полномочий career_staff и career_admin на каждой операции отдельно не проверялись.

**Не подтверждено:** отдельный визуальный проход каждой страницы в мобильном и desktop viewport; keyboard/screen reader; реальные заполненные сценарии каждой сущности; действия с побочным эффектом; чужой вуз/ресурс; интеграции и production. Полные визуальные оценки по маршрутам требуют следующего QA прохода на 390/768/1440 px и синтетических наполненных сценариях.

Локальная Docker-среда и данные были синтетическими. Внешние системы и production не затрагивались.
