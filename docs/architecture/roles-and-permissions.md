# Роли и границы доступа

Коды всех 11 ролей совпадают с `UserRole` в `apps/backend/src/auth/interfaces/user-role.ts`. Этот документ описывает смысл ролей; конкретное разрешение API задают controller decorators, guards и проверки сервисов. [Проверяемая матрица разрешений и входного контроля всех маршрутов](../security/role-matrix.md) фиксирует текущую реализацию.

## Роли

| Код | Название продукта | Назначение |
|---|---|---|
| `student` | Студент | Собственная группа, расписание, Pair Space, посещаемость и личные настройки |
| `employer` | Работодатель | Карьерные задачи и взаимодействие с кандидатами; проверки владения компанией выполняет карьерный сервис |
| `career_staff` | Сотрудник карьерного центра | Карьерные процессы своего вуза в рамках сервисных проверок |
| `career_admin` | Администратор карьерного центра | Управление карьерными процессами своего вуза в рамках сервисных проверок |
| `teacher` | Преподаватель | Назначенные занятия и учебные действия в пределах backend resource checks |
| `curator` | Прежняя основная роль куратора | Вход сохранён для совместимости; доступ к назначенным группам через дополнительные назначения, без права редактирования посещаемости |
| `faculty_dean` | Декан факультета | Действия в разрешённой области факультета, если конкретный endpoint их поддерживает |
| `department_head` | Заведующий кафедрой | Действия в разрешённой области кафедры, если конкретный endpoint их поддерживает |
| `university_admin` | Администратор ВУЗа | University cabinet и endpoints управления своим вузом |
| `superadmin` | Суперадминистратор | Операционное управление платформой и управление аккаунтами более низкого уровня |
| `developer` | Разработчик | Операционное управление платформой и аккаунтами ниже своего уровня; не управляет ролями/статусами разработчиков и суперадминистраторов |

В текущей entity/API у пользователя одно значение `role`. Клиентская навигация помогает открыть нужную поверхность, но не заменяет backend authorization.

С 15 октября 2026 года в рабочей копии кураторство реализовано отдельными назначениями на существующие аккаунты студента/сотрудника. Основная роль и сессия не меняются. Назначения и снятия доступны деканату и администраторам своего университета; группы и кураторы связаны отношением многие-ко-многим. Подробные права, миграция и API: [кураторство на аккаунте](../product/account-curatorship.md). Это описание реализации, а не подтверждение её публикации.

## Клиентские поверхности

| Поверхность | Типичная роль | Доступ |
|---|---|---|
| Student workspace | `student` | Персональные данные и группа пользователя |
| Staff workspace | `teacher`, `curator` | Назначенные занятия/группы и разрешённые действия |
| University cabinet | `university_admin`, `faculty_dean`, `department_head` | Только функции, предоставленные отдельным endpoint и его проверками |
| Developer workspace | `developer` | Техническая документация и диагностика |

`superadmin` входит в `web-admin` вместе с администраторами вузов, но оболочка показывает «Панель платформы», область «Весь проект» и раздел «Университеты». Пункт «Настройки университета» и экран `/university` доступны администратору вуза; для `superadmin` пункт скрыт, а прямой переход уводит на обзор платформы. Привязка `organizationId` у существующего аккаунта не меняет роль и не ограничивает `superadmin` областью одного вуза; backend-guards разрешают этой роли обращаться к любому вузу.

## Где проверять разрешения

- Ролевой enum: `apps/backend/src/auth/interfaces/user-role.ts`.
- Route policy: `@Roles(...)` в соответствующем controller.
- Общие проверки: `apps/backend/src/common/guards/roles.guard.ts` и `university.guard.ts`.
- Ресурсные/tenant проверки: профильный service и соответствующие тесты.
- Сгенерированный API-контракт: `/api/v1/docs`.

PostgreSQL RLS policies отсутствуют. Tenant isolation выполняется приложением; проверяйте tenant + resource ownership в каждом новом endpoint. Не переносите матрицы из старых спецификаций как фактические ACL без сверки с текущим controller/service.

## Владелец и делегированное управление платформой

Полный операционный доступ панели по умолчанию получают developer и superadmin; явный грант заменяет этот набор. Эти роли не становятся владельцами автоматически, а раздел «Контур доверия» остаётся доступен только владельцу. Старые полномочия superadmin не отменяются. [Реализация](../product/platform-control.md).

Developer может управлять аккаунтами всех вузов и менять роли/статусы пользователей ниже своего уровня. Он не может менять собственную роль/статус или управлять ролями/статусами разработчиков и суперадминистраторов. Superadmin может менять роль и статус developer, включая повышение до superadmin; собственный аккаунт и аккаунты своего уровня остаются недоступны для изменения. Владелец сохраняет исключительное управление «Контуром доверия»: назначение полномочий и экстренный отзыв платформенного доступа. Владельца нельзя заблокировать или сбросить ему пароль через делегированное управление аккаунтами.

## Платформенные права

Помимо `UserRole`, платформенные аккаунты получают набор `permissions.*` в `PlatformGrant`. Права задаются в `apps/backend/src/platform/platform.dto.ts` (`PLATFORM_PERMISSIONS`) и проверяются в сервисе через `PlatformService.require(...)` — это отдельный от `@Roles` слой.

| Право | Назначение |
|---|---|
| `services.read` / `services.restart` / `services.rebuild` | Чтение и управление сервисами Compose |
| `logs.read` | Логи агента |
| `accounts.read` / `accounts.write` | Чтение/изменение аккаунтов, блокировка, **отзыв сессий** |
| `identity-links.read` / `identity-links.write` | MAX/Telegram привязки |
| `universities.read` / `universities.write` | Университеты |
| `student-data.read` / `student-data.write` | Отсутствия и посещаемость |
| `personal-data.read` / `personal-data.write` | Личные настройки, избранное, заметки, прогресс ДЗ |
| `homework-data.read` / `homework-data.write` | Сдачи ДЗ |
| `notification-data.read` / `notification-data.write` | Уведомления, inbox, push-устройства |
| `curation-data.read` / `curation-data.write` | Кураторские назначения |
| `academic-data.read` / `academic-data.write` | Академические курсы и серии |
| `career-data.read` / `career-data.write` | Карьерные задачи, портфолио, тесты |
| `discussion-data.read` / `discussion-data.write` | Обсуждения |
| `pairspace-content.read` / `pairspace-content.write` | Пространства пар и объявления |
| `events-data.read` | Системные события |
| `attachments-data.read` / `attachments-data.write` | Вложения PairSpace |
| `settings.read` / `settings.write` | Настройки платформы |
| `audit.read` | Аудит |
| `analytics.read` | **Витрина загрузки платформы** (`/platform/analytics/overview`) |
| `telemetry.read` | **Журнал событий, наблюдаемые пользователи, журнал сессий** (`/platform/events`, `/platform/monitored-users`, `/platform/sessions`) |

Права `analytics.read` и `telemetry.read` открывают доступ к [платформенной телеметрии и аналитике](../modules/platform-telemetry.md). Bootstrap-аккаунт Developer получает полный набор прав при инициализации; университетные операторы эти права не получают.
