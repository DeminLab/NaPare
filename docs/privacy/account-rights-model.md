# Экспорт и удаление аккаунта: модель для реализации

Дата: 23 октября 2026. Статус: согласованная модель P2-1; серверная реализация находится в отдельной рабочей ветке. Пользователь выбрал сохранение индивидуальной истории без имени и контактов. [Контракт удаления](account-deletion.md) перечисляет фактическую очистку, архив и исключения. Production не изменяется.

## Подтверждённое состояние

Раньше `DELETE /users/me` только устанавливал `isActive=false`: ФИО и контакты оставались. Новая серверная операция очищает профиль, привязки и приватные наборы в транзакции, сохраняя внутренний код и допустимые учебные записи. Обычная административная деактивация остаётся отдельным действием. Перечень классов приведён в [карте данных](data-map.md).

## JSON-экспорт

Аутентифицированный пользователь получает данные только своего аккаунта. Идентификатор берётся из проверенной сессии, а не из параметров клиента. Экспорт включает все страницы выбранных наборов и описание состава/исключений. Парольные хеши, коды привязки, push-токены, секреты интеграций и полные журнальные JSON с данными других людей не выдаются. Прямые ссылки на файлы не означают выгрузку их байтов. Moodle, резервные копии и внешние сервисы требуют отдельной процедуры; файл не выдаёт локальную выборку за полный архив этих сервисов.

## Решение, которое требуется для учебного архива

Вариант А: после удаления аккаунта сохраняются только агрегаты без идентификатора человека, свободного текста, точных дат и малых групп. Индивидуальные посещения, ответы и заявления уничтожаются в активной БД. Нельзя обещать сохранение индивидуального учебного досье.

Вариант Б: сохраняются индивидуальные учебные записи под случайным архивным кодом. ФИО, контакты, внешние привязки и доступ удаляются, но состав записей может позволить повторную идентификацию. Это псевдонимизация; такой архив нельзя называть полностью обезличенным. Для него нужны определённые вузом основания, состав, срок и доступ.

Оба варианта требуют отдельных правил для обязательных финансовых документов, внешнего Moodle, файлов по URL, журналов и резервных копий. При наличии таких исключений API и интерфейс должны перечислять их, а не сообщать «все данные удалены». Владельцу платформы и последнему ответственному представителю компании сначала требуется передать управление. Все проверки удаления выполняются на синтетических локальных данных.

Пользователь выбрал вариант Б: «Да: оставить историю без имени и контактов». В реализации внутренний UUID становится архивным кодом; доступ, контакты и внешние привязки удаляются. Это псевдонимизация, а не доказанное необратимое обезличивание. Учебный архив и перечисленные исключения должны быть явно показаны перед подтверждением удаления.
