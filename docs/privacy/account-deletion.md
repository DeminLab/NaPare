## Что делает операция

В активной БД аккаунт превращается в неизменяемую архивную запись: ФИО заменяются на «Архив» и короткий код, email — на технический адрес в `.invalid`; телефон, avatar URL, MAX/Telegram/sourceTeacherId и lastLoginAt очищаются. Пароль заменяется случайным невыдаваемым хешем, `isActive=false`, `sessionVersion` увеличивается. В `personalDataDeletedAt` фиксируется время. Прежние access/refresh JWT больше не принимаются. Обычная административная деактивация в `UsersService.deactivate()` остаётся отдельной операцией.

UUID, вуз, группа, роль и даты учётной записи сохраняются как связь учебного архива. В нём остаются посещаемость, отсутствия, учебные ответы/работы, результаты и заявления с историей. По группе, датам и текстам человека иногда можно узнать. Поэтому API возвращает `archiveModel: pseudonymous`, а не `anonymous`.

Удаляются личные заметки, избранное, устройства/push-токены, настройки/история собственных уведомлений, Telegram challenges, Moodle identities, карьерный профиль, доступность, опубликованные портфолио, собственные career notices/AI request metadata и platform grant. Выборка включает собственные строки прежнего вуза; общий лимит в первую страницу отсутствует.

Удаление device tokens включает технические отметки разрешения WebPush. После серверного подтверждения браузер дополнительно удаляет подписку только своего worker; ошибки локальной очистки показываются как частичный результат. Это не удаляет копии у внешнего провайдера, в логах или backup. Подробности и границы проверки — [WebPush](../clients/webpush.md).

Собственные сообщения в обсуждениях заменяются отметкой об удалении с сохранением дерева ответов; текст отклика и evidence/reason карьерного допуска очищаются. Собственные файловые вложения отзываются, их имя и URL очищаются; это не уничтожает байты на внешнем файловом сервисе. Прямые ссылки в сохранённых учебных ответах и тексты учебного архива требуют отдельной проверки оператором. Собственные audit old/new/IP/userAgent очищаются; собственные event payload заменяются `redacted: true`, идентификатор автора остаётся архивным кодом.

Личные назначения куратора/учебного офиса/карьерного центра отзываются, ссылки curator/dean в структуре очищаются, созданные QR-сессии отзываются. Исторические ссылки на архивный код сохраняются. API не удаляет учебные записи других людей и не принимает целевой `userId` для выбора чужого аккаунта.

## Что остаётся вне автоматического уничтожения

- Платёжные записи компании и документы банка, включая ранее указанный email для чека. Удаление аккаунта не отменяет оплату и не делает возврат. Реальные сроки/основания хранения определяет оператор; API не устанавливает их сам.
- Учебный архив, журналы других участников, уже доставленные уведомления и общий контент с прежними упоминаниями. Собственное сообщение может остаться цитатой в чужом сообщении.
- Внешний Moodle, имена из вузовских источников расписания, байты файлов по URL, серверные логи, WAL/backup и архивы внешних сервисов. Начатую внешнюю отправку нельзя считать отозванной только из-за очистки локальной БД.
- Копии на устройствах и в браузерах. Сервер не может гарантировать их удаление на другом устройстве. Клиентская очистка текущего устройства проверяется отдельно.

Эти исключения возвращаются в preview и квитанции. Запрос оператору по оставшимся копиям остаётся необходимым; функция не выдаёт очистку активной БД за юридически полный ответ на любой запрос субъекта ПД. См. [карту данных](data-map.md).

## API и подтверждение

`GET /api/v1/users/me/deletion-preview`, Bearer JWT: свой `accountId`, удаляемые классы, сохраняемые классы, blockers и URL предварительного JSON-экспорта. Ответ `Cache-Control: no-store, private`. Условия заново проверяются в транзакции удаления.

`DELETE /api/v1/users/me`, Bearer JWT. Тело:

```json
{
  "expectedUserId": "UUID аккаунта с экрана подтверждения",
  "currentPassword": "текущий пароль",
  "confirmed": true,
  "acknowledgeRetention": true
}
```

ID из JWT выбирает аккаунт. `expectedUserId` только проверяет совпадение, чтобы смена аккаунта в другой вкладке не направила подтверждение другому человеку. Без пароля/подтверждений операция не выполняется. Текущий пароль проверяется заново по заблокированной строке; секрет не сохраняется в журнал или квитанцию. Rate limit — три попытки в минуту на tracker глобального ThrottlerGuard (сейчас IP), не распределённый персональный лимит.

Результат: `success`, архивный код, время удаления, `removedCounts` удалённых наборов и перечень сохранённого. 409 возвращает необходимые передачи обязанностей; 401 — неподтверждённый пароль/отозванная сессия; 403 сохраняет существующую защиту платформенных аккаунтов. Тело без подтверждений теперь получает 400 вместо прежней деактивации. Старый пользовательский UI этим изменением не называется готовым.

## Передача обязанностей

Владелец платформы сначала передаёт владение. Единственный действующий владелец компании обращается к оператору для передачи управления: отдельного self-service transfer API компании сейчас нет. Последний администратор вуза сначала обеспечивает другого администратора. Сотрудника нужно заменить в настроенных маршрутах и незавершённых этапах согласования; учебный офис уже поддерживает reassign. Новые решения/маршруты текущего вуза и удаление используют один office advisory lock.

Данные не уничтожаются частично при таком отказе. Preview может устареть: финальная операция повторяет проверку полномочий и обязанностей. Платформенная защита `protectLegacyMutation` сохраняется; для делегированного технического аккаунта может потребоваться действие владельца, даже если обычных офисных blockers нет.

## Транзакция и защита от возврата данных

Миграция 38 добавляет tombstone column, узкую capability записи по доказанным сервером IDs и триггеры. Список IDs строится из фиксированных self selectors, не принимается из HTTP. INSERT policies не расширяются; остальные политики дополнены разрешением только на выбранные строки, без tenant-wide write grant.

Удаление берёт общий platform mutation lock, затем lock учебного офиса текущего вуза, затем user row lock. Повторно проверяются активность, версия сессии, роль/вуз и пароль. Поэтому отозванная во время ожидания сессия не завершает операцию. Любая ошибка откатывает профиль и все изменения связанных таблиц.

Приватные записи не создаются повторно для удалённого получателя. Обычная запись от текущего actor берёт SHARE lock строки пользователя; при уже выполненном удалении отклоняется. Account tombstone нельзя обычным UPDATE снова активировать или переписать. Для scoped platform operations с заменой actor университетскими grants применяются прежние права и отдельная проверка получателя приватных наборов; это не доказательство отмены каждого уже начатого бизнес-действия во всех сервисах.

Down миграции запрещён, если уже существуют tombstones: откат схемы не должен автоматически снимать защиту архива. Операторская процедура восстановления backup также должна учитывать удалённые аккаунты; такой server/offsite drill этим модулем не подтверждён.

## Проверка

Для файлов, Moodle, внешних сообщений, логов и backup применяется [операторская процедура](external-copies-procedure.md). Автоматического replay удалений после восстановления старого dump сейчас нет; до допуска пользователей и внешних отправок требуется сверка с защищённым журналом последующих удалений.

Локальная база — новая disposable `curation_test_*` на loopback, runtime NOSUPERUSER NOBYPASSRLS; записи синтетические. [E2E suite](../../apps/backend/test/account-erasure.e2e-spec.ts) проверяет подтверждение/пароль/чужой expected ID, фактическую очистку, прежний вуз, сохранение посещаемости/отсутствий, отзыв JWT, финансовые исключения, владельцев, rollback, неизменяемый архив и конкурирующие записи/отзыв сессии. Он подключается к CI через `ACCOUNT_ERASURE_TEST_DATABASE_URL`. Фактические итоговые результаты и браузерный UI фиксируются отдельно, по завершении проверок.

Локальный результат 23 октября: 42 backend unit suites / 430 tests passed; 10 предметных JWT/HTTP/PostgreSQL сценариев удаления прошли, включая настоящий office route → submit → accept → approve → reassign и чтение архивного заявления администратором после удаления студента. Отдельно прошли 4412 guard-probe tests по 357 объявлениям маршрутов. Это не доказательство бизнес-изоляции каждого маршрута: guard probe использует синтетический обработчик. Backend и portal typecheck, root lint/docs lint и repository guards прошли. Браузерный экран ещё не добавлен, production не менялся.
