# Управление данными своего аккаунта

23 октября 2026. Справочник реализации в отдельной ветке; production не изменён. Экран `/privacy/account` доступен из содержимого политики конфиденциальности и предназначен для владельца аккаунта любой роли. Заголовки, навигация и исходники student-приложения не меняются.

## Пользовательский процесс

Если сессии нет, пользователь входит непосредственно на странице. Клиент загружает профиль и preview удаления параллельно и проверяет совпадение ID. Смена сессии в другой вкладке отменяет текущие запросы и требует загрузить сведения заново; сервер дополнительно сравнивает `expectedUserId` с JWT.

Кнопка скачивания получает [полный JSON-экспорт](personal-data-export.md), проверяет формат, версию, `complete: true` и единственную собственную запись `datasets.users`, затем предлагает файл через браузер. Сообщение «подготовлен для скачивания» не подтверждает сохранение файла на диске. JSON содержит личные данные; его защита после скачивания зависит от пользователя.

Перед удалением показаны возвращённые сервером удаляемые и сохраняемые категории, включая учебный архив, потенциальную идентификацию по группе/датам/текстам, платёжный email и внешние копии. При blockers форма удаления скрыта и показана необходимая передача обязанностей. Нужны текущий пароль и два явных подтверждения. Двойное нажатие блокируется синхронным флагом; при ошибке пароль и подтверждения сохраняются. DELETE автоматически не повторяется ни после 401, ни при сетевой ошибке. При потере ответа интерфейс предлагает проверить состояние, поскольку операция могла завершиться на сервере.

Успех отображает архивный код и время из [квитанции сервера](account-deletion.md). Только при совпадении текущей сессии очищаются `accessToken`, `refreshToken` и известный кэш `napare-student-schedule-v1`; зарегистрированным worker со scope `/student/` отправляется существующее сообщение `NAPARE_CLEAR_OFFLINE`. Вход в другой аккаунт во время асинхронной очистки прерывает дальнейшую очистку с предупреждением. Не используются `localStorage.clear()`, удаление всех кэшей или обещание очистить другие устройства. Ошибка CacheStorage/worker отдельно показана пользователю.

GET может один раз обновить истёкшие токены через существующий refresh-контракт; ответ refresh не записывается поверх изменившейся сессии. DELETE требует действующей сессии и не имеет автоматического повторения. Запросы no-store, загрузка отменяется при смене аккаунта/уходе; сетевой запрос ограничен двумя минутами. Приватные данные не помещаются в новый постоянный клиентский кэш.

## Фактические проверки

24 октября добавлена очистка WebPush после подтверждённого удаления: helper отписывает только собственный worker `/notifications/push-worker.js` с точным scope `/notifications/`, повторно проверяет отсутствие новой сессии и сообщает о частичной очистке при ошибке. Настоящий browser → Next/Nest/PostgreSQL сценарий удаления подтвердил очистку сессии и подписки; PushManager подменён, реальное устройство не проверялось. См. [WebPush](../clients/webpush.md).

- Настоящий последний администратор вуза увидел blocker передачи обязанностей; кнопки удаления не было. Снимок 1440 px просмотрен. axe-core 4.10.3 для `main` этого состояния после исправления подчёркивания ссылок: 0 violations, 0 incomplete по WCAG 2/2.1 A/AA. Это один автоматически проверенный экран, не полная ручная аттестация доступности.

- Отдельный браузерный сценарий подтвердил refresh при недействующем access token и рабочем refresh token; при неверном пароле DELETE отправлен ровно один раз, черновик формы сохранён.
- Негативный сценарий с подменённым только export-ответом `complete: false` не создал скачивание. Реальное удаление токенов в другой вкладке убрало старую форму и открыло вход. Подмена использовалась только для проверки неполного экспорта; основной процесс выше выполнялся с реальным API.

- Portal typecheck выполнен; browser-сценарий использовал реальный Next 15.5.28, Nest и отдельную PostgreSQL 18 с синтетическими аккаунтами и NOSUPERUSER/NOBYPASSRLS.
- Проверены вход, скачивание настоящего JSON: 69 наборов, `complete: true`, один собственный пользователь, отсутствие секретных полей в его проекции; неверный пароль сохраняет форму, правильный завершает удаление и показывает квитанцию.
- Проверена очистка двух ключей сессии и заранее созданного CacheStorage namespace. Это проверка браузерного хранилища, а не отдельный тест реального student service worker или другого устройства.
- На ширинах 320/768/1024/1440 px переполнение документа отсутствовало; снимок 320 px визуально просмотрен. Ошибок JavaScript `pageerror` в основном сценарии не было. Ожидаемые HTTP 401 при неверном пароле не выдаются за отсутствие сетевых ошибок.

Нативные устройства, живые внешние провайдеры, удалённые backup, полная ручная проверка WCAG и production этим сценарием не проверяются. После любых последующих изменений транспортных/сессионных правил их отдельные негативные сценарии нужно повторять.
