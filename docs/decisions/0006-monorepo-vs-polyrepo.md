# ADR-0006: Монорепозиторий vs Полирепозиторий

## Статус
Принято

## Контекст
Команда из 2 человек. Нужно решить: один репозиторий или несколько? Факторы: размер команды, сложность деплоя, общие зависимости, кодогенерация.

## Решение
Использовать **монорепозиторий** с Turborepo.

### Структура
```
napare/
├── apps/
│   ├── backend/        # NestJS
│   ├── mobile/         # Flutter (отдельный pubspec)
│   ├── web/            # Next.js
│   └── max-miniapp/    # React + Vite
├── packages/
│   ├── shared/         # Общие типы, zod-схемы, константы
│   ├── api-client/     # Сгенерированный API-клиент
│   └── ui/             # Общие UI-компоненты
├── docs/
├── infrastructure/
└── scripts/
```

### Инструменты
- **Turborepo** — оркестрация сборки, кэширование
- **pnpm workspaces** — управление зависимостями
- **Shared packages** — общие типы и компоненты

## Преимущества
1. **Атомарные коммиты** — один PR может содержать изменения во всех приложениях
2. **Общий API-клиент** — генерируется из OpenAPI, используется везде
3. **Единый CI/CD** — одна конвейерная сборка
4. **Простота рефакторинга** — изменения в API сразу видны клиентах
5. **Общие типы** — типобезопасность между backend и клиентами

## Недостатки
1. **Размер репозитория** — будет расти со временем
2. **Сложность CI** — нужно кэшировать сборку
3. **Flutter в монорепо** — требует отдельного pubspec

## Решения для Flutter
- Flutter проект живёт в `apps/mobile/`
- Имеет собственный `pubspec.yaml`
- Не зависит от pnpm workspaces
- Общие типы дублируются вручную или через code generation

## Альтернативы
| Вариант | Причина отказа |
|---------|----------------|
| Полирепо | Сложность синхронизации API-клиента, дублирование кода |
| Turborepo + pnpm | Оптимальный баланс для маленькой команды |
| Nx | Избыточная сложность для команды из 2 человек |
