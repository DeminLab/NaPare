# Т-Касса: оплата услуг платформы

Дата: 22 октября 2026. Назначение: настройка утверждённой владельцем интеграции и проверка платёжного заказа. Код принимает оплату услуг платформы; выплаты студентам и хранение реквизитов карт не входят в этот модуль. Production-терминал не подключался.

## Путь пользователя и граница услуги

Работодатель открывает «Компании» в карьерном кабинете, выбирает компанию и видит стоимость с сервера. Кнопка ведёт на форму Т-Кассы. Возвращение в браузер не означает оплату: подтверждение приходит через подписанный webhook и серверный GetState либо через кнопку проверки. Платёж доступен только активным членам компании; техническая роль сама по себе не даёт читать её историю. Возврат оформляет владелец платформы.

`career_access` — код услуги в текущем каталоге. Цена задаётся оператором после согласования договора; она не берётся из тела запроса. До подключения договора и терминала панель показывает, что оплата недоступна. Факт успешного платежа сохраняется в реестре; модуль не вводит новые ограничения существующих учебных/карьерных прав. Условия и период фактически оказываемой услуги должны соответствовать опубликованной оферте оператора.

## Настройка

Используйте защищённое окружение backend. Ключи нельзя передавать браузеру, включать в Git или логи. Для первого запуска применяются sandbox-терминал и подменённый транспорт в тестах.

| Переменная | Значение |
| --- | --- |
| `TKASSA_SEND_REQUESTS` | По умолчанию выключено; только строка `true` разрешает исходящие банковские вызовы |
| `TKASSA_TERMINAL_KEY`, `TKASSA_PASSWORD` | Серверные реквизиты собственного терминала |
| `TKASSA_LIVE` | По умолчанию sandbox; `true` выбирает live endpoint |
| `TKASSA_LIVE_APPROVED` | Дополнительное явное `true` для live; без него запрос отклоняется |
| `TKASSA_PUBLIC_ORIGIN` | HTTPS origin платформы без пути, логина, query или fragment |
| `TKASSA_CAREER_ACCESS_PRICE_MINOR` | Согласованная цена услуги в целых копейках, от 1 до 999999999; значения по умолчанию нет |
| `TKASSA_TERMINAL_CURRENCY` | Обязательно `RUB`; подтвердить валюту терминала в договоре |
| `TKASSA_TAXATION`, `TKASSA_ITEM_TAX` | Согласованные бухгалтером параметры чека из справочника API; значения по умолчанию нет |

Валидация параметров чека использует актуальный [справочник Init](https://developer.tbank.ru/eacq/api/init), включая поддерживаемые значения Tax/Taxation. Оператор выбирает ставку и систему налогообложения по своему договору и правовым основаниям; код этого не определяет. Для чека банк получает email плательщика, название услуги и сумму. Email хранится в поле `receiptEmail` без выдачи в обычных API-ответах; учесть его в политике и сроках хранения.

Настройте NotificationURL в кабинете банка на `/api/v1/career/payments/notification` своего HTTPS origin. Это endpoint без JWT с проверкой подписи и последующим запросом в банк. При сетевой ошибке он не подтверждает обработку успешным ответом: банк сможет доставить уведомление повторно.

## Надёжность и безопасность

- Идемпотентность привязана к компании и UUID команды; сумма заказа неизменна. Конкурентные повторы создают один заказ и одну попытку Init.
- До запроса в банк транзакция сохраняет `unknown`. Если процесс завершится или ответ потеряется, повтор не отправляет новый Init. Сверка использует CheckOrder и GetState для того же OrderId.
- Webhook проверяет terminal, SHA-256 подпись, OrderId, PaymentId и сумму. Фактический статус получается server-to-server; позднее событие не открывает оплаченный/возвращённый заказ заново. Нормализованная история событий дедуплицируется.
- Возврат сначала сохраняется как неопределённый intent. Только один незавершённый возврат разрешён на платёж. При таймауте повтор Cancel автоматически не выполняется; новый возврат заблокирован до ручной сверки с банком. Это защищает от двойного возврата.
- Банк вызывается только по фиксированным HTTPS endpoints; redirects запрещены, timeout — 10 секунд. Ссылка формы проверяется по разрешённым хостам. Карта вводится на стороне банка.

Если Init уже принят банком, но ссылка формы потеряна, GetState может подтвердить попытку без возврата ссылки. Оператор находит заказ в кабинете банка по OrderId; модуль не создаёт новую попытку автоматически. Для неопределённого возврата оператор сверяет реальную операцию и сумму в кабинете; автоматическая повторная отправка запрещена. В этом выпуске нет API ручного изменения бухгалтерского результата: такая корректировка требует отдельной проверяемой процедуры.

## API

Все пути начинаются с `/api/v1/career/payments`.

| Метод / путь | Назначение |
| --- | --- |
| `GET ?companyId=UUID` | Последние 100 заказов своей компании |
| `GET options?companyId=UUID` | Доступность и согласованная серверная цена |
| `POST` | Создание: companyId, product=`career_access`, idempotencyKey; сумма от клиента запрещена |
| `GET :id`, `GET :id/history` | Заказ и последние 200 нормализованных событий своей компании |
| `POST :id/refresh` | Сверить состояние с банком |
| `POST :id/refund` | Команда владельца платформы: idempotencyKey, amountMinor, reason |
| `POST notification` | Подписанное банковское уведомление, ответ `OK` после сверки |

Исходники: [провайдер](../../apps/backend/src/career-billing/tkassa.provider.ts), [транзакционный сервис](../../apps/backend/src/career-billing/payment.service.ts), [миграция 35](../../apps/backend/src/migrations/1700000000035-CareerBilling.ts), [панель работодателя](../../apps/web-portal/src/app/career/CareerPayments.tsx).

```powershell
pnpm --filter @napare/backend exec jest --runInBand tkassa.provider.spec.ts
pnpm --filter @napare/backend exec jest --config ./test/jest-e2e.json --runInBand career-billing.e2e-spec.ts
pnpm --filter @napare/backend exec tsc --noEmit

```

Для HTTP suite задайте `PAYMENT_TEST_DATABASE_URL` новой отдельной локальной БД с именем `curation_test_*`; тест не работает с production и проверяет миграцию на пустых тестовых платёжных таблицах. Внешний fetch полностью заменён mock-банком: 7 HTTP/БД сценариев и 10 проверок протокола прошли локально. Это не проверка реального sandbox/live терминала, чеков ФНС или доставки webhook через публичный домен.

Перед live оператор подключает юридическое лицо/ИП и терминал, публикует условия услуги/возвратов, согласует чек, проверяет настоящий sandbox, TLS и публичный webhook. Для Android WebView отдельного приложения следует соблюдать [требования Т-Кассы к открытию формы](https://www.tbank.ru/kassa/dev/webview/); проверка нативного платёжного открытия этим веб-модулем не выполнена.

Протокол подписи: [официальный Token](https://developer.tbank.ru/eacq/intro/developer/token). Статусы/возвраты: [официальный протокол платежей](https://www.tbank.ru/kassa/dev/payments/). Состояние провайдера и договорные условия проверяются оператором перед подключением.
