# Импорт расписания для вуза

Справочник текущей реализации ветки P1-2 на 22 октября 2026. Администратор своего вуза загружает файл или запускает настроенный источник. Импорт не создаёт группы, преподавателей или назначения по совпадению ФИО. Сначала заведите структуру вуза. Существующая синхронизация СИБИТ через `schedule/sync` сохранена.

## Подготовьте выгрузку

Используйте постоянный ID занятия из своей системы: исправление предмета, времени или аудитории не должно менять этот ID. Один источник (`sourceKey`) принадлежит одному потоку выгрузок, например `faculty-main`; повторные загрузки этого потока обновляют его занятия. Файл другого факультета должен иметь другое имя источника.

| Поле CSV/XLSX/JSON | Значение |
| --- | --- |
| `id` | Обязательный стабильный ID, до 200 символов |
| `date` | Локальная дата `YYYY-MM-DD` |
| `startTime`, `endTime` | `HH:mm`, окончание позже начала в тех же сутках |
| `pairNumber` | Целое 1–30 |
| `subject` | Предмет, до 500 символов |
| `group` | Точное имя существующей группы своего вуза, регистр несущественен |
| `teacher`, `room` | Необязательный текст, до 500 символов |
| `status` | Необязательно: `scheduled` или `cancelled` |

CSV: UTF-8, допустим BOM, разделитель запятая или точка с запятой, кавычки по обычным правилам CSV. Неизвестные и повторные колонки, некорректные даты и строки разной ширины отклоняются целиком. [Пример CSV](../../apps/backend/test/fixtures/schedule.csv).

XLSX: один непустой лист с такими же заголовками, текстовые даты/время и обычные числа. Передайте содержимое файла в base64 без `data:`. Формулы, гиперссылки, объекты и типизированные Excel-даты отклоняются: экспортируйте их как текст. Бинарный файл до 2 MiB, ZIP до 100 entries и 8 MiB фактически распакованных данных. Зашифрованные, многотомные и повреждённые архивы не принимаются.

JSON: массив объектов с указанными полями в строке `content`. Для старого интерфейса сохранён `rows` с `format: csv/json`; если ID отсутствует, он равен `fileName:номер_строки`. Это совместимость старого интерфейса: при перестановке строк такие ID меняются, поэтому для регулярной синхронизации используйте явный `id` в файле.

CSV/XLSX/JSON требуют `utcOffset`, если локальное время отличается от UTC: для Омска `+06:00`. По умолчанию `+00:00`; смещение постоянное, сезонные переходы не вычисляются. Время сохраняется как UTC instant, день недели вычисляется по локальной дате. Смена смещения существующего источника требует проверки администратора перед `replace`.

## ICS

Экспортируйте календарь `VCALENDAR` с `VEVENT`, `UID`, `SUMMARY`, `DTSTART` и `DTEND` в UTC DATE-TIME с `Z`. Floating time, `TZID`, целые дни и `RECURRENCE-ID` overrides отклоняются с объяснением: предварительно разверните исключения в отдельные события со стабильными UID. Нельзя молча заменить часовой пояс локальной зоной сервера.

Группа: `X-NAPARE-GROUP`, либо `groupName` в запросе. Номер пары: `X-NAPARE-PAIR-NUMBER`, либо `pairNumber` в запросе. Аудитория: `LOCATION`, преподаватель: необязательный `X-NAPARE-TEACHER`. `STATUS:CANCELLED` отменяет существующий ID. Даты ICS и границы диапазона считаются по UTC. Нужны одни UTC сутки и точность до минуты.

`RRULE`/`RDATE` разворачиваются в указанном диапазоне `startDate/endDate`; ID повторения содержит UID и исходную дату повторения. Максимум 1000 занятий и 10000 шагов развёртки. Исключения `EXDATE` обрабатывает ical.js. [Пример ICS](../../apps/backend/test/fixtures/schedule.ics). Это поддерживаемое подмножество [RFC 5545](https://www.rfc-editor.org/rfc/rfc5545), не обещание поддержки всех календарных расширений.

## Загрузите и проверьте результат

Все пути ниже имеют префикс `/api/v1` и требуют JWT администратора вуза. Университет берётся из проверенной учётной записи, не из тела запроса.

```json
{
  "fileName": "schedule.csv",
  "format": "csv",
  "sourceKey": "faculty-main",
  "utcOffset": "+06:00",
  "queued": true,
  "idempotencyKey": "d2d9428c-f9db-423f-91f1-c8a46faf5e95",
  "content": "id,date,startTime,endTime,pairNumber,subject,group\nlesson-1,2026-10-22,09:00,10:30,1,Математика,ИН-25"
}
```

1. Отправьте `POST /admin/schedule/upload`. `format`: `csv`, `json`, `xlsx`, `ics`, `sibit` или `moodle`. Файлы до 2 MiB, до 1000 занятий. Только этот маршрут принимает JSON до 3 MiB для base64; остальные сохраняют прежний предел тела.
2. Сохраните `jobId`. При `queued: true` ответ содержит `status: queued`; файл уже нормализован и надёжно сохранён в PostgreSQL. При отсутствии флага обработка пытается завершиться в том же запросе; ответ завершённого задания содержит `imported`, `updated`, `deleted`, `unchanged`, `jobId`, `status`.
3. Читайте `GET /admin/schedule/imports/:jobId`: статус, число попыток, итог и безопасное описание ошибки. Чужой ID возвращает 404. Исходное содержимое и токены в ответ не входят.
4. Читайте `GET /admin/schedule/imports/:jobId/changes?page=1&limit=50`: `{data, meta}` существующей модели `academic_schedule_changes`, значения до/после и `changeType: added/updated/deleted`. Неизменённая запись не создаёт лишний журнал.

Один `idempotencyKey` в одном вузе возвращает то же задание. Другое нормализованное содержимое с тем же ключом даёт 409. Для повторного запроса используйте прежний ключ; для следующей версии файла — новый. Разные ключи с неизменённым содержимым не дублируют занятия. Одновременно нельзя передавать `rows` и `content`.

### Полный снимок и отмены

По умолчанию отсутствующие в файле занятия сохраняются. Для полного снимка добавьте `replace: true`, постоянный `sourceKey`, обе даты `startDate/endDate` и явный непустой `groupNames`. Максимальный диапазон — 366 дней. Пустой снимок `content: []` для JSON с этими параметрами допустим.

Отсутствующие занятия отменяются мягко только у этого источника, указанных групп и дат; ручные занятия и другие источники сохраняются. Отмена фиксируется в журнале, данные остаются в БД, обычные запросы Lesson скрывают `deletedAt`. Повторное появление стабильного ID восстанавливает занятие и создаёт `updated`. Дубли ID, неизвестные/неоднозначные группы и несовпадение границ отклоняют весь импорт, частичного сохранения нет.

## Moodle и СИБИТ

Moodle требует `connectorType: moodle`, уже настроенное защищённое HTTPS-подключение через `POST /admin/connectors/moodle/configure`. Токен шифруется существующим механизмом. Через `PATCH /admin/connectors/moodle` задайте `config.scheduleGroupMap` (числовой ID Moodle → точное имя группы НаПаре) и `config.schedulePairTimes` (`HH:mm` → номер пары). Не меняйте зашифрованные поля подключения вручную.

```json
{"config":{"scheduleGroupMap":{"101":"ИН-25"},"schedulePairTimes":{"09:00":1,"10:40":2}}}
```

Отправьте импорт `format: moodle` без `content/rows`, с `startDate/endDate` и `utcOffset`. Нужна разрешённая сервисная функция `core_calendar_get_calendar_events` и права сервисного пользователя на указанные группы. Загружаются только групповые календарные занятия с длительностью; задания модулей не превращаются в пары. Неизвестный group ID, предупреждения, некорректная или слишком большая выдача останавливают импорт. URL проходит существующую защиту от SSRF; произвольный URL импорта не принимается. Контракт проверен по [исходному коду Moodle](https://github.com/moodle/moodle/blob/MOODLE_405_STABLE/calendar/externallib.php), реальный вуз требует отдельной проверки прав и версии Moodle.

СИБИТ: адаптер оборачивает существующий `RaspScraperService.getCatalog`, не меняет парсинг или его локальную конверсию времени. Сохраняет строковые numeric `groupId`, `teacherId` и ID занятия; многогрупповое занятие имеет отдельную запись для каждой группы без изменения ID источника. Группа сопоставляется по `externalId` своего вуза; при неизвестном внешнем ID запрещён fallback к совпадающему имени. `sourceTeacherId` сохраняется, `teacherId` не назначается по ФИО. Старый путь `POST /admin/schedule/sync` остаётся отдельным, прежним процессом СИБИТ. Не запускайте два потока для одних занятий без согласования владельца источника.

## Очередь, запуск и восстановление

Очередь этого блока — PostgreSQL `schedule_import_jobs`; Redis не нужен для надёжности импорта. Это независимая очередь от доставки уведомлений. Воркеры выбирают `queued` через `FOR UPDATE SKIP LOCKED`, каждые 2 секунды. Блокировка и изменение занятий/журнала/статуса находятся в одной транзакции: при аварии процесса транзакция откатывается и задание остаётся в очереди. По источнику применяется advisory lock, поэтому разные задания одного потока не создают дубли.

`SCHEDULE_IMPORT_WORKER_ENABLED=false` отключает только фонового воркера. В тестах он выключен по умолчанию; для проверки фонового запуска установите `true`. Синхронный запрос без `queued` может обработать своё задание и при выключенном воркере. Временная ошибка повторяется через 30 секунд, максимум 3 попытки; ошибки валидации/отзыва доступа терминальные. Перед записью заново проверяются активность и роль автора. Завершённое задание очищает payload; неуспешные задания оставляют payload для диагностики и должны попадать в согласованную политику хранения вуза.

Миграция `1700000000033` добавляет мягкую отмену Lesson и таблицу очереди с внешними ключами/уникальным ключом идемпотентности. Она применяет обязательные restrictive `FORCE RLS` политики migration29. Приложение работает только под `NOSUPERUSER NOBYPASSRLS`. Воркер получает cross-tenant capability исключительно на таблицу очереди, затем отдельный capability на точный вуз для занятий/групп/автора/журнала. Production этим блоком не изменялся.

## Проверки

Локально: 11 тестов адаптеров с файлами fixtures и настоящим XLSX архивом; HTTP/JWT/PG сценарии включают tenant A/B, RLS таблицы, очередь, конкурентный захват, идемпотентность, обновление/отмену/восстановление, сохранение ручного источника, ошибки/повторы и отзыв прав. E2E включается `SCHEDULE_IMPORT_TEST_DATABASE_URL` только для нового loopback `curation_test_*` под ограниченной ролью; CI создаёт отдельную БД. Это не доказательство работы внешнего Moodle, live СИБИТ или production. Импорт новых форматов в существующем веб-интерфейсе относится к следующему блоку onboarding; здесь готов серверный контракт.
