## 1. Обзор продукта

**НаПаре** — операционная система учебного дня студента. Один экран вместо десяти разрозненных источников: расписание, задания, материалы, коммуникация и учёт отсутствий — всё вокруг конкретной пары (занятия).

### Три клиентские поверхности

| Клиент | Платформа | Аудитория | Приоритет |
|--------|-----------|-----------|-----------|
| **Mobile App** | iOS + Android (Flutter) | Студенты, преподаватели | Критический |
| **Web App** | Браузер (Next.js, адаптивный) | Кураторы, админы, преподаватели, студенты на ПК | Критический |
| **MAX Mini-App** | Мессенджер MAX (React + Vite) | Студенты (быстрый доступ) | Высокий |

### Ключевые модули MVP

| Модуль | Описание |
|--------|----------|
| Расписание | Надёжное получение, хранение, детект изменений, история |
| Пространство пары | Объявления, ДЗ, файлы, обсуждение — привязаны к конкретной паре |
| Отсутствия | Статусы (болен, работа и т.д.) + дашборд куратора |
| Мой день | Персональная сводка: пары сегодня, изменения, дедлайны, новые материалы |
| Уведомления | Push (FCM + APNs) + in-app центр |
| Роли и доступ | Student / Teacher / Curator / UniversityAdmin / SuperAdmin |

### Что НЕ входит в MVP

- AI-сводки
- Модуль занятости и конфликтов расписания
- Сложная аналитика
- White-label
- Множество коннекторов (только СИБИТ + Excel/CSV)

## 2. Видение и проблема

### Проблема

Учебный процесс студента разбросан:

| Что нужно | Где сейчас |
|-----------|------------|
| Расписание | Сайт вуза (часто неудобный) |
| Изменения расписания | Telegram / VK / объявления |
| Домашние задания | Чаты, устно, Google Docs |
| Материалы | Облака, почта, флешки |
| Отсутствие / болезнь | Личные сообщения куратору |
| Работа / занятость | Нигде не учитывается |
| Коммуникация с преподавателем | Десятки чатов без структуры |

**Итог:** студент тратит время на поиск информации об учёбе, а не на учёбу. Куратор и преподаватель не видят полной картины.

### Решение

Формула:
```
Расписание → Конкретная пара → Контекст пары
                          (преподаватель, группа, файлы,
                           задания, объявления, обсуждение,
                           история изменений, посещаемость)
```

### Уникальные механики

1. **Пространство пары** — у каждого занятия своя страница со всем контентом
2. **Мой день** — персональная сводка без AI
3. **Центр статуса студента** — статусы с автоматическим расчётом пар и подтверждением куратора
4. **Мультивузовость с рождения** — архитектура для подключения любого вуза
5. **AI-ассистент** (план после MVP)

## 4. Технологический стек

### Сводная таблица

| Слой | Технология | Обоснование |
|------|------------|-------------|
| **Mobile** | Flutter 3.x + Riverpod + go_router + dio | Один кодобаза iOS + Android |
| **Web** | Next.js 14+ (App Router) + TypeScript + Tailwind | SSR, отличный DX, адаптивность |
| **MAX Mini-App** | React + Vite + TypeScript + MAX SDK | Стандарт для мини-приложений MAX |
| **Backend** | NestJS (Node.js) или FastAPI (Python) | Модульный монолит, OpenAPI из коробки |
| **БД** | PostgreSQL 16 | Надёжность, JSONB, полнотекстовый поиск |
| **ORM** | TypeORM / Prisma (NestJS) или SQLAlchemy (FastAPI) | Миграции, типы |
| **Кэш / очереди** | Redis | Сессии, очереди уведомлений, rate limiting |
| **Файлы** | S3-совместимое (Yandex Object Storage / MinIO) | Файлы ДЗ и материалов |
| **Push** | Firebase Cloud Messaging + APNs | Стандарт |
| **Auth** | JWT (access + refresh) | Stateless |
| **API Docs** | OpenAPI 3 | Единый контракт между клиентом и сервером |
| **Аналитика** | PostHog / Amplitude | Продуктовые события |
| **Мониторинг** | Sentry | Ошибки |

### Принципы выбора

1. Один язык на клиенте где возможно (TypeScript для web + max)
2. Модульный монолит на старте
3. Всё, что можно сгенерировать из OpenAPI — генерировать
4. Мультивузовость закладывается сразу через `university_id`

## 6. Модель данных

### Ключевые сущности

Все сущности (кроме справочников) имеют `university_id` для мультивузовости.

| Сущность | Поля | Описание |
|----------|------|----------|
| **User** | id, phone/email, password_hash, first_name, last_name, avatar_url, roles[], university_id, group_id, created_at | Пользователь системы |
| **University** | id, name, city, connector_config, status | Учебное заведение |
| **Faculty** | id, university_id, name | Факультет / институт |
| **Group** | id, faculty_id, name, curriculum_year | Учебная группа |
| **Teacher** | id, user_id, university_id, groups[], lessons[] | Привязка преподавателя |
| **Lesson** (Пара) | id, university_id, group_id, teacher_id, subject, room, day_of_week, start_time, end_time, week_type, start_date, end_date | Центральная сущность |
| **LessonChange** | id, lesson_id, type, old_values, new_values, created_at | Изменение пары |
| **PairSpace** | id, lesson_id, active_until | Пространство пары (живёт +30–60 дней) |
| **Announcement** | id, pair_space_id, author_id, text, created_at | Объявление преподавателя |
| **Homework** | id, pair_space_id, title, description, deadline, created_by | Домашнее задание |
| **HomeworkSubmission** | id, homework_id, user_id, status (not_submitted/submitted), submitted_at | Статус сдачи ДЗ |
| **FileAttachment** | id, pair_space_id, homework_id, file_url, file_type, size, uploaded_by | Файл / материал |
| **DiscussionMessage** | id, pair_space_id, user_id, text, parent_id, created_at | Сообщение обсуждения |
| **AbsenceStatus** | id, user_id, type, start_date, end_date, comment, created_at | Статус отсутствия |
| **AbsenceConfirmation** | id, absence_id, curator_id, status (pending/approved/rejected), comment, updated_at | Подтверждение куратора |
| **Notification** | id, user_id, type, title, body, deep_link, is_read, created_at | Уведомление |
| **DeviceToken** | id, user_id, platform (ios/android/web), token, updated_at | Токен push-устройства |
| **AuditLog** | id, user_id, action, entity, entity_id, ip, created_at | Аудит действий |

### Статусы отсутствий

| Статус | Код | Цвет |
|--------|-----|------|
| Учусь | `learning` | 🟢 зелёный (по умолчанию) |
| Болен | `sick` | 🤒 оранжевый / красный |
| Работа / занятость | `work` | 💼 синий |
| Другой город | `other_city` | ✈️ фиолетовый |

| Роль | Код | Описание | Кто |
|------|-----|----------|-----|
| Студент | `student` | Основной пользователь | Студент вуза |
| Преподаватель | `teacher` | Публикует контент в пространство пары | Преподаватель вуза |
| Куратор | `curator` | Видит и подтверждает отсутствия группы | Куратор / староста |

| Суперадмин | `superadmin` | Управление платформой | Команда НаПаре |

| Преподаватель | `teacher` | Публикует контент в пространство пары |
| Куратор | `curator` | Видит отсутствия группы, подтверждает |
| Админ вуза | `university_admin` | Управляет структурой и расписанием |
| Суперадмин | `superadmin` | Платформа |

Пользователь может иметь несколько ролей.

### Flow регистрации студента (полный)

```
[1] Экран приветствия
    ↓ "Зарегистрироваться"
[2] Ввод телефона (+7) → "Получить код"
    ↓
[3] Ввод SMS-кода (4-6 цифр)
    ↓
[4] Согласие на ПДн (чекбокс обязателен)
    ↓
[5] Выбор вуза (поиск + список)
    ↓
[6] Выбор факультета → курса → группы (каскад)
    ↓
[7] Заполнение профиля (Имя, Фамилия, аватар опционально)
    ↓
[8] Онбординг-тур (3-4 экрана)
    ↓
[9] Экран "Мой день"
```

**Целевое время:** ≤ 2 минуты

### Flow для преподавателя / куратора

```
[1] Регистрация (телефон или email)
    ↓
[2] Экран "Ожидание назначения роли"
    ↓ [Админ назначает роль и привязывает к парам]
[3] Уведомление о назначении роли
    ↓
[4] Вход → "Мои пары" (преподаватель) или "Дашборд" (куратор)
```

### Технические требования

- JWT: access token (15–30 мин) + refresh token (30–60 дней)
- Refresh token: Secure Storage (mobile), HttpOnly cookie (web)
- Rate limiting на SMS и попытки входа
- Возможность удалить аккаунт (с подтверждением)
- Логирование входов в AuditLog

### 13.1. Расписание и коннекторы

**Сущности:** University, Faculty, Group, Teacher, Room, Lesson, LessonChange

**Источники (Connectors Layer):**

1. Ручной импорт (Excel / CSV / iCal) через админку
2. Парсер сайта СИБИТ (HTML + cron)
3. Расширяемый интерфейс коннектора

**Контракт коннектора:**

```typescript
interface ScheduleConnector {
  id: string;
  universityId: string;
  fetchSchedule(period: { from: Date; to: Date }): Promise<NormalizedLesson[]>;
  healthCheck(): Promise<{ ok: boolean; lastSuccessAt?: Date; error?: string }>;
}
```

**Детект изменений:**

При каждом обновлении сравниваем с предыдущей версией:
- Отмена пары
- Перенос (дата / время)
- Смена аудитории
- Смена преподавателя
- Добавление новой пары

Фиксируем `LessonChange` → генерируем событие для Notification Service.

### 13.2. Пространство пары (Pair Space)

Каждая **Пара (Lesson)** имеет одно **Пространство пары (PairSpace)**.  
Пространство живёт +30–60 дней после окончания пары.

**Разделы:**

1. Объявления — короткие сообщения преподавателя
2. Домашние задания — название, описание, дедлайн, статус у студента
3. Файлы / материалы — pdf, doc, ppt, изображения, ссылки
4. Обсуждение — тред, привязанный к этой паре
5. Состав — список студентов (опционально)

**Права:**

| Роль | Доступ |
|------|--------|
| Преподаватель пары | Полный доступ на запись |
| Студенты группы | Чтение + обсуждение + отметка сдачи ДЗ |
| Куратор | Чтение |

### 13.3. Модуль отсутствий

**Статусы:**

| Статус | Код | Цвет |
|--------|-----|------|
| Учусь | `learning` | 🟢 зелёный |
| Болен | `sick` | 🤒 оранжевый / красный |
| Работа / занятость | `work` | 💼 синий |
| Другой город | `other_city` | ✈️ фиолетовый |
| Другая причина | `other` | ⚠️ серый |

**Логика:**

1. Студент ставит статус на период (с–по) или на конкретные дни
2. Система автоматически определяет, какие пары попадают под период
3. Уведомление уходит куратору
4. Куратор подтверждает или отклоняет
5. Статус отображается в дашборде

**Приватность:**

| Роль | Что видит |
|------|-----------|
| Студент | Только свои статусы |
| Куратор | Статусы своей группы |
| Преподаватель | Факт отсутствия на своей паре (причину — ограничить) |
| Админы | По необходимости + с аудитом |

### 13.4. Экран «Мой день»

Главный экран студента. Автособираемая персональная сводка **без AI**.

**Логика агрегации:**

```
todayLessons = lessons where date == today AND group == user.group
changes = LessonChange where lesson in todayLessons AND createdAt > lastView
hotDeadlines = homeworks where deadline in [today, tomorrow] AND status != submitted
newContent = announcements + files where createdAt > lastView AND pair in user.group
```

**Требования:**
- Pull-to-refresh
- Время загрузки ≤ 1.5–2 сек
- Понятные пустые состояния
- Тёмная тема
- Кэш последнего состояния (работает при слабом интернете)

### 13.5. Уведомления

**Типы уведомлений (MVP):**

| Событие | Для кого | Пример текста |
|---------|----------|---------------|
| Изменение расписания | Студент | «Пара «Программирование» перенесена на 14:00, ауд. 305» |
| Новое объявление | Студент | «Новое объявление в паре «Математика»» |
| Новое ДЗ | Студент | «Новое задание: Лабораторная №3 (дедлайн 10.09)» |
| Новый файл | Студент | «Преподаватель загрузил файл в «Физика»» |
| Приближение дедлайна | Студент | «Завтра дедлайн: Лабораторная №3» |
| Решение по отсутствию | Студент | «Куратор подтвердил ваш статус «Болен»» |
| Новое отсутствие | Куратор | «Иванов А. установил статус «Болен» на 05–07.09» |

**Каналы:**

1. Push (FCM + APNs) — основной
2. In-app центр уведомлений
3. Email / SMS — НЕ входят в MVP

**Техническая схема:**

```
Бизнес-событие → Event Bus / очередь → Notification Service →
  создание записи + отправка push → лог доставки
```

**Антиспам:**
- Группировка однотипных уведомлений
- Настройки по типам событий
- «Тихие часы»

1. Минимизация данных — собираем только необходимое

- HTTPS everywhere

- Шифрование чувствительных полей (причины отсутствий)
- Разграничение доступа на уровне API
- Логи без лишних персональных данных
- Резервное копирование с защитой
- Soft-delete + политика хранения

## 17a. Бизнес-логика и edge-cases

### 17a.1. Конфликт расписания

**Сценарий:** У студента две пары одновременно.

**Логика:**
1. При загрузке расписания backend проверяет пересечения
2. Если конфликт обнаружен:
   - Студент получает уведомление: «Обнаружен конфликт: {предмет1} и {предмет2} в {время}»
   - В расписании конфликтующие пары подсвечиваются красным
   - Кнопка «Сообщить куратору»
3. Куратор получает уведомление с деталями конфликта
4. Куратор может:
   - Подтвердить конфликт (попросить студента решить)
   - Снять конфликт (если одна из пар отменена)

### 17a.2. Отмена пары за 5 минут

**Сценарий:** Преподаватель отменяет пару за 5 минут до начала.

**Логика:**
1. При создании `LessonChange` с типом `cancelled` за ≤ 15 минут до начала:
   - Push-уведомление отправляется СРАЗУ (приоритет high)
   - В «Мой день» пара помечается красным крестом
   - Статус: «ОТМЕНЕНО»
2. Если пара отменена за > 15 минут:
   - Push-уведомление отправляется в обычном режиме
   - В «Мой день» пара помечается оранжевым значком
   - Статус: «ОТМЕНЕНО»

### 17a.3. Повторяющееся ДЗ

**Сценарий:** Преподаватель создаёт ДЗ, которое повторяется каждую неделю.

**Логика:**
1. При создании ДЗ преподаватель выбирает:
   - «Без повторения»
   - «Каждую неделю»
   - «Каждые 2 недели»
   - «Каждую чётную неделю»
   - «Каждую нечётную неделю»
2. Система создаёт серию ДЗ с разными дедлайнами
3. Студент видит одно ДЗ в списке, но при тапе — все повторения
4. Отметка «Сдано» для одного повторения не отмечает другие

### 17a.4. Расписание на каникулы

**Сценарий:** Периоды без пар (каникулы, каникулы перед экзаменами).

**Логика:**
1. Админ может отметить период как «Каникулы»
2. В этот период:
   - Расписание пусто
   - В «Мой день» показывается сообщение: «Каникулы! 🎉»
   - Уведомления отключены (если нет ДЗ с дедлайном)
3. Можно отметить «Лёгкая неделя» (1-2 пары)

### 17a.5. Смена преподавателя

**Сценарий:** Преподаватель одной пары сменился.

**Логика:**
1. Админ меняет преподавателя в расписании
2. Создаётся `LessonChange` с типом `teacher_changed`
3. Студенты получают уведомление: «Преподаватель {предмет} изменён: {old} → {new}»
4. Старое пространство пары остаётся доступным (живёт +30 дней)
5. Новое пространство пары создаётся для будущих занятий

### 17a.6. Чередование недель (нечётная/чётная)

**Сценарий:** Пара проходит через неделю.

**Логика:**
1. При создании пары админ выбирает:
   - «Каждую неделю»
   - «Нечётные недели»
   - «Чётные недели»
2. Backend рассчитывает расписание с учётом week_type
3. В «Мой день» пары, которых нет на этой неделе, не показываются
4. В календаре пары отображаются только в нужные недели

### 17a.7. Гибкий доступ (студент на обмене)

**Сценарий:** Студент учится в одном вузе, но проходит обмен в другом.

**Логика:**
1. Админ может добавить студента во временную группу
2. Студент видит:
   - Основное расписание (родная группа)
   - Временное расписание (группа обмена)
   - Переключатель между расписаниями
3. Уведомления приходят из обоих расписаний
4. После окончания обмена временная группа автоматически снимается

### 17a.8. Таймаут сессии

**Сценарий:** Пользователь не активен долгое время.

**Логика:**
1. Access token истекает через 15 минут
2. Refresh token истекает через 30 дней
3. При истечении access token:
   - Mobile: автоматический refresh через refresh token
   - Web: автоматический refresh через HttpOnly cookie
   - Если refresh не удался → редирект на login
4. При истечении refresh token:
   - Полная повторная авторизация

### 17a.9. Offline-режим

**Сценарий:** Нет интернета.

**Логика:**
1. Кэш последнего состояния:
   - Расписание на сегодня + завтра
   - Непрочитанные уведомления
   - Последнее состояние «Мой день»
2. При отсутствии сети:
   - Показ кэшированных данных
   - Баннер: «Нет сети. Показаны сохранённые данные»
   - Pull-to-refresh показывает ошибку
3. Офлайн-действия (очередь):
   - Отправка сообщения в обсуждение → очередь → отправка при восстановлении
   - Отметка ДЗ как сданного → очередь → отправка при восстановлении

```yaml
  test:

    services:
      postgres:
        image: postgres:16
        env:
          POSTGRES_USER: napare

          POSTGRES_DB: napare_test
      redis:
        image: redis:7
    steps:
      - uses: actions/checkout@v3
      - run: pnpm install
      - run: pnpm run test:ci
        env:
          DATABASE_URL: postgresql://napare:napare@localhost:5432/napare_test
          REDIS_URL: redis://localhost:6379

  build:
    runs-on: ubuntu-latest
    needs: test
    steps:
      - uses: actions/checkout@v3
      - run: pnpm install
      - run: pnpm run build
        env:
          DATABASE_URL: ${{ secrets.DATABASE_URL }}
          JWT_SECRET: ${{ secrets.JWT_SECRET }}

  deploy-staging:
    runs-on: ubuntu-latest
    needs: build
    if: github.ref == 'refs/heads/develop'
    steps:
      - uses: actions/checkout@v3
      - run: ./scripts/deploy.sh staging
        env:
          SSH_KEY: ${{ secrets.STAGING_SSH_KEY }}

  deploy-production:
    runs-on: ubuntu-latest
    needs: build
    if: github.ref == 'refs/heads/main'
    steps:
      - uses: actions/checkout@v3
      - run: ./scripts/deploy.sh production
        env:
          SSH_KEY: ${{ secrets.PRODUCTION_SSH_KEY }}
```
