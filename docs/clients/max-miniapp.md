# MAX: единый вход через сайт

## Обзор

MAX открывает существующий сайт NaPare и его кабинеты. Отдельный интерфейс на `apps/max-miniapp` больше не является пользовательским входом.

1. В MAX для бизнеса после одобрения бота укажите корневой HTTPS URL вашего опубликованного NaPare и настройте кнопку открытия «Открыть»; например, текущий production origin проекта — `https://napare.sano.ru/`. MAX запускает сайт внутри MAX. Эти параметры задаются для самого MAX-бота на платформе, а не кодом этого репозитория. См. официальные [инструкции по подключению приложения](https://dev.max.ru/docs/webapps/introduction) и [управлению ботом](https://dev.max.ru/docs/chatbots/bots-create/manage). Совместимый адрес `/max/` также ведёт на сайт.
2. В обычном браузере посетитель видит публичную главную сайта.
3. При запуске внутри MAX сайт ждёт MAX Bridge (он загружается с CDN) до 15 секунд. Он сначала читает `window.WebApp.initData`; если Bridge не загрузился, использует исходный `#WebAppData=...` fragment, переданный MAX. Строка отправляется на `POST /api/v1/auth/max` без клиентской проверки; backend валидирует её подпись и срок действия.
4. Если MAX уже привязан, пользователь сразу попадает в кабинет своей роли.
5. Если MAX ещё не привязан, портал проверяет, есть ли активная сессия сайта; при истёкшем access token пробует обновить её по refresh token. Пользователь явно выбирает: связать MAX с открытым аккаунтом (перед подтверждением портал показывает имя и email) или войти по email и паролю, выданным университетом.
6. Если MAX уже привязан к другому аккаунту, сервер авторизует именно связанный аккаунт; локальная сессия сайта не перехватывает вход и не вызывает ошибочную попытку перепривязки.

## Реализация и безопасность

- MAX Bridge подключается в корневом layout `apps/web-portal`; клиент предпочитает `window.WebApp.initData` и использует fragment только как fallback. Сервер валидирует данные независимо от клиентского источника, поэтому подмена fragment не даёт авторизацию. Если данные запуска недействительны или устарели, пользователь получает инструкцию закрыть приложение и открыть его снова кнопкой бота; при временной ошибке сети сохранённые в памяти данные можно отправить повторно. См. официальную [документацию MAX Bridge](https://dev.max.ru/docs/webapps/bridge) и [проверку initData](https://dev.max.ru/docs/webapps/validation).
- MAX Bridge также загружается в корневых layout всех role-приложений. Нативная кнопка «Назад» MAX отображается на вложенных страницах и перемещается по внутренней истории Next.js; на начальной странице кабинета и формах входа она скрыта. Обычный браузер продолжает работать без MAX API.
- Для сценария посещаемости студент может открыть `/student/attendance/check-in` из кабинета. Страница предпочитает нативный MAX QR reader; если он недоступен в MAX Web, запускает камеру браузера с локально упакованным ZXing QR decoder. QR принимается только для того же origin и текущего маршрута; затем действуют обычные JWT-, tenant-, group- и TTL-проверки backend. Доступ к камере браузера требует HTTPS и разрешения пользователя. Учитель по-прежнему может показывать тот же QR для обычной камеры телефона.
- На недельном расписании студент может открыть нативный экран отправки MAX и поделиться выбранной неделей. Если сайт открыт вне MAX, используются системный Web Share или копирование; интерфейс сообщает, открылось ли меню или расписание скопировано, и не заявляет, что получатель уже получил сообщение.
- `apps/web-portal/src/components/MaxLaunchAuth.tsx` содержит только обработку состояния входа и маршрутизацию по роли; API остаётся источником авторизации.
- Launch data никогда не считается подтверждённой личностью без серверной HMAC-проверки и проверки срока действия.
- Production по умолчанию принимает launch data не старше 15 минут; то же значение используется в backend configuration, root `.env.example` и Compose.
- Привязка возможна только если аккаунт ещё не связан с MAX; атомарная запись защищает от одновременных попыток и не позволяет заменить привязанный MAX другим.
- Для явной привязки существующей сессии используется `POST /api/v1/auth/max/link`: endpoint требует JWT, повторно проверяет подпись и срок действия initData и связывает только текущего пользователя. MAX, связанный с другим аккаунтом, не переносится.
- Пароль передаётся только по HTTPS, не сохраняется в браузере и используется сервером для проверки текущей учётной записи.
- Backend возвращает обычные access/refresh JWT. Портал сохраняет их под теми же ключами, что и текущий сайт, затем открывает уже существующий role workspace.
- В репозитории нет отдельного процесса создания Telegram-бота; backend принимает его webhook и отвечает через Bot API. Telegram-сессия сама по себе не подтверждает MAX-идентичность: привязка MAX выполняется из MAX WebApp по проверенному `initData`.
- Аккаунт NaPare можно отдельно привязать к Telegram через одноразовую ссылку в `/connections`; эта связь не авторизует MAX и не заменяет проверку MAX `initData`. Настройка описана в [руководстве Telegram](telegram-bot.md).
- Роли маршрутизируются так: `student` → `/student/today`; преподаватель/куратор → `/staff/today`; администрация ВУЗа → `/deanery/dashboard`; `developer` → `/developer/api`.
- Без MAX Bridge публичная главная и обычный вход сайта продолжают работать без изменений.
- При временной ошибке входа кнопка повтора заново отправляет текущее значение `WebApp.initData`; если Bridge не дал данные, использует строку из памяти. Если сервер отклоняет данные как устаревшие или недействительные, интерфейс просит закрыть мини-приложение и снова открыть его кнопкой MAX-бота.
- Нативная кнопка «Назад» использует `WebApp.BackButton`; она не заменяет и не меняет навигацию сайта.
- В отметке посещаемости MAX mobile использует `WebApp.openCodeReader(false)`. Если метода нет или нативный сканер недоступен у конкретного MAX клиента, страница запускает камеру браузера через HTTPS и локальный ZXing; поток можно отменить, повторная отправка защищена backend.

## Настройка и выпуск

1. Указать `MAX_BOT_TOKEN` в окружении backend. Без него `/api/v1/auth/max` отвечает `MAX_NOT_CONFIGURED`.
2. В настройках MAX-бота указать корневой HTTPS URL развернутого сайта как кнопку открытия приложения. При замене домена настройте его также в `.env` и reverse proxy по [инструкции деплоя](../../DEPLOY.md#using-a-different-public-domain).
3. Если кнопку отправляет бот API в сообщении `/start`, используйте тип `open_app` и укажите в `web_app` публичное имя или ссылку именно на MAX-бота с привязанной Mini App. Обычная кнопка `link` открывает внешний URL. Настраивать ответ `/start` через отдельный backend этого проекта не требуется: кнопку можно включить в MAX для бизнеса или в уже используемом обработчике бота. См. официальные разделы [типы кнопок](https://dev.max.ru/docs-api/use-cases/sending-messages/keyboard) и [поле `web_app`](https://github.com/max-messenger-bot/max-bot-api-schemas/blob/main/schema_2026_07_01.json).
4. Развернуть обновлённые `web-portal` и Nginx; `/max/` проксируется в тот же `web-portal`.
5. Проверить запуск главной из обычного браузера, запуск из MAX, первую привязку тестового аккаунта и повторный вход без пароля. Затем проверить сканирование активного QR камерой MAX уже вошедшим студентом и отправку расписания через MAX share sheet.

До выпуска можно отдельно проверить, что токен принадлежит доступному MAX-боту, не выводя его в команду или журнал. Официальный `GET /me` возвращает объект бота при успешной авторизации:

```powershell
$headers = @{ Authorization = $env:MAX_BOT_TOKEN }
Invoke-RestMethod -Method Get -Uri 'https://platform-api2.max.ru/me' -Headers $headers
```

В ответе проверьте `is_bot: true`; токен должен оставаться только в переменной окружения. Эта проверка не подтверждает URL мини-приложения в настройках MAX и не заменяет запуск на устройстве.

Если PowerShell завершает запрос ошибкой TLS до получения HTTP-статуса, проверьте цепочку доверия сертификата по [официальным требованиям MAX API](https://dev.max.ru/docs-api). Не отключайте проверку TLS-сертификата для обхода этой ошибки.

Для portal typecheck: `pnpm --filter @napare/web-portal exec tsc --noEmit`.

## Историческая мини-апка

Исходники `apps/max-miniapp` оставлены в репозитории для исторической справки и возможного ручного отката. Они не используются маршрутом `/max/` и исключены из стандартных `pnpm dev` и `pnpm build`. Для MAX запускайте только существующий сайт NaPare; архивный Vite-клиент не собирайте и не подключайте к боту.

Серверная проверка MAX initData описана в [модуле авторизации](../modules/auth.md#5-ux--экраны) и закреплена тестами `apps/backend/src/auth/max-init-data.spec.ts` и `apps/backend/src/auth/auth.service.spec.ts`.
