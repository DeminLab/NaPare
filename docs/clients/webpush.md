# Уведомления браузера WebPush

Текущая реализация отдельной feature-ветки, 24 октября 2026. Выбран предусмотренный планом канал WebPush для PWA; подключение RuStore SDK к Android APK этим блоком не выполняется. Это руководство для пользователя и оператора тестовой среды. Production и реальная доставка на устройство не подтверждены.

## Подключить уведомления

Откройте «Подключения аккаунта → Настроить уведомления этого браузера» или `/notifications/setup` на общем портале. Student-файлы, shared navigation/header/Avatar/logo и Docker не меняются.

1. Войдите в аккаунт. Экран показывает именно его имя/email, состояние браузера и связь подписки с текущим аккаунтом.
2. Если оператор ещё не настроил WebPush, кнопка недоступна. Отправка может быть выключена отдельно: в этом случае подписку можно подготовить, но получение сообщений не обещается.
3. Прочитайте текст разрешения, отметьте checkbox и нажмите «Подключить уведомления браузера». Только этот жест вызывает запрос разрешения браузера. Открытие страницы, вход, чтение статуса и reload не создают подписку автоматически.
4. При согласии браузера создаётся PushSubscription и сохраняются её принадлежность аккаунту, дата и версия пользовательского разрешения. При отказе браузера подключение не выполняется. Снятие запрета делается в настройках сайта браузера, затем состояние обновляется здесь.
5. Для отключения нажмите «Отключить подписку браузера»: серверное разрешение отзывается и локальная подписка удаляется. Если сервер недоступен, локальная отписка всё равно выполняется, а отсутствие подтверждения сервера явно сообщается.

На экране блокировки worker показывает только название НаПаре и нейтральный текст об обновлениях. Текст уведомления, имя, учебные сведения и произвольный deepLink из payload не отображаются и не используются для перехода. Нажатие открывает фиксированный адрес `/notifications/setup` своего origin; личные сведения читаются после входа. Сообщение по-прежнему приходит через WebPush-провайдера в зашифрованном payload: отсутствие личного текста на экране не является обещанием отсутствия данных в транспортном payload или серверном inbox.

Нужны поддерживаемые браузером Push API, Notification API, Service Worker и secure context. Localhost подходит для разработки; фактическая поддержка мобильной PWA, режимов браузера и разрешений проверяется на целевых устройствах. См. [PushManager.subscribe](https://developer.mozilla.org/en-US/docs/Web/API/PushManager/subscribe), [showNotification](https://developer.mozilla.org/en-US/docs/Web/API/ServiceWorkerRegistration/showNotification) и [Push API — текущий Working Draft W3C](https://www.w3.org/TR/push-api/). Наличие API не доказывает доступность регионального push-сервиса.

## Выход, смена аккаунта и удаление

Подтверждённый сервером logout атомарно увеличивает sessionVersion и отзывает все WebPush-устройства этого аккаунта. При сбое отзыва обе операции откатываются; успешного logout не возвращается. Другие пользователи и провайдеры не изменяются. Выход без сети не гарантирует серверный отзыв: на общем устройстве подписку следует отключить вручную. Уже начавшийся внешний запрос нельзя гарантированно остановить; worker всё равно показывает нейтральное сообщение.

Смена токенов в другой вкладке немедленно скрывает имя/email, статусы и действия; для нового аккаунта требуется reload. Подписка другого аккаунта не перепривязывается автоматически. Сервер сравнивает endpoint независимо от порядка JSON-полей и не отдаёт чужие токены. При смене VAPID-ключа старую подписку нужно отключить и создать заново; простая отметка наличия токена не подтверждает совместимость ключа.

После подтверждённого self deletion сервер физически удаляет собственные device tokens и их opt-in метаданные. Общая страница удаления дополнительно отписывает текущий браузер от **собственного** worker `/notifications/push-worker.js`; чужие worker и новая появившаяся сессия не очищаются предположительно. Неудачная локальная очистка возвращает частичный результат, а не сообщение о полном уничтожении. Операторские журналы/backup имеют отдельные сроки и процедуру.

## Подготовить тестовую среду

1. Примените миграцию 43 обычной процедурой. Она добавляет nullable `webPushConsentedAt`, `webPushConsentVersion`, `webPushRevokedAt` к device_tokens; старые токены не превращаются в согласие задним числом. Разрушительный rollback запрещён.
2. Настройте `PUSH_PROVIDER=webpush|both`, соответствующую пару `WEBPUSH_VAPID_PUBLIC_KEY`/`WEBPUSH_VAPID_PRIVATE_KEY` и `WEBPUSH_VAPID_SUBJECT` (контактный mailto или HTTPS без credentials). Приватный ключ хранится только в защищённой конфигурации backend. Он не возвращается клиенту, в audit или в Git.
3. Разрешённые endpoint hosts настраиваются по [серверному контракту](../integrations/notification-delivery.md). Не добавляйте произвольные или внутренние адреса: подписка определяет адрес исходящего запроса.
4. Сначала оставьте `NOTIFICATIONS_DELIVERY_ENABLED=false`. Проверьте подписку, владельца и отзыв на изолированной среде. Статус API отдаёт только публичный ключ, readiness/отправку и хеши endpoint собственных активных подтверждённых устройств.
5. Для реальной доставки отдельно подготовьте Redis/queue и только затем включайте общий delivery flag в разрешённой тестовой среде. Применяются прежние пользовательские настройки событий/тихих часов. `delivered` означает принятие провайдером, не показ/прочтение на устройстве.
6. Выполните реальный device drill: подключение после пользовательского жеста, закрытый браузер/PWA, locked screen без личного текста, click, quiet hours, отзыв, logout, сеть offline/online и смена аккаунта. Зафиксируйте ОС/браузер/версию, дату, конфигурационный профиль без секретов и фактический результат. Эти действия сейчас остаются открытыми: пользователь сообщил, что внешние подключения не подготовлены.

## Серверный контракт и данные

| Метод | Назначение |
| --- | --- |
| GET /devices/webpush | Только свой статус, публичный VAPID key и хеши подтверждённых endpoint |
| POST /devices/webpush | `token`, `confirmed:true`, актуальный `version`; явное разрешение и каноническая регистрация |
| DELETE /devices/webpush | `token`; отзыв собственных endpoint-строк, повтор безопасен |

Все три route требуют JWT и private/no-store. Узкое исключение для карьерных аккаунтов без вуза допускает **только** `/devices/webpush`, не соседние device/academic routes. Администратор вуза не получает доступ к чужим подпискам через этот self API.

Стандартные `/devices/token` сохраняют прежний контракт. Но WebPush-токен без актуальных opt-in полей не становится целью доставки; повторная legacy-регистрация отозванной строки не отменяет отзыв. Worker повторно проверяет согласие непосредственно перед отправкой ожидающей задачи. JSON поля нормализуются, а конкурентная регистрация одного endpoint сериализуется advisory lock. Повторное явное подтверждение обновляет дату; audit сохраняет действие/версию и код устройства без endpoint/ключей.

Версия технического разрешения: `webpush-browser-2026-10-24`. Device token содержит секреты подписки и не входит в JSON export. Собственные provider/platform/deviceName/isActive и три opt-in поля экспортируются. Официальные основания/сроки обработки и юридическую достаточность текста должен утвердить оператор; техническая отметка не является таким заключением.

Worker регистрируется только в `/notifications/`, не имеет fetch handler и не читает CacheStorage. Он не управляет `/student/` и не заменяет offline worker. Activation wait ограничен 15 секундами. При неудаче регистрации новая локальная подписка отписывается; исходная существующая подписка не уничтожается автоматически.

## Что проверено

- 11 настоящих JWT/HTTP/PostgreSQL сценариев: disabled/config/no secret leakage, обязательное разрешение/версия, endpoints, concurrent/canonical ownership, чужие аккаунты двух вузов, own export, inert legacy registration, отзыв ожидающей задачи, узкий career exception, атомарный rollback logout при принудительной ошибке БД и self deletion. Две гонки воспроизводят регистрацию, заблокированную до logout, и legacy-запись, прочитанную до отзыва: первая получает 401 после снятия блокировки, вторая не восстанавливает согласие. VAPID и p256dh ключи генерируются только для disposable fixture; отправка провайдера подменена, исходящий HTTP запрещён.
- 8 unit-сценариев политики и 4 VM-сценария **фактического worker script**: нейтральный текст, повреждённый payload, фиксированный переход/фокус и отсутствие fetch handler. VM использует mocked Notification/clients API; это не OS display.
- Browser Next/Nest/PostgreSQL зарегистрировал **настоящий service worker** с точным scope, прошёл explicit opt-in/register/revoke, keyboard, четыре ширины и scoped axe 0 violations/0 incomplete без page errors. Notification permission и PushManager в этом прогоне **подменены**: внешняя подписка и получение через FCM/Apple/Mozilla этим не проверены.
- Browser также прошёл отказ разрешения без subscribe, очистку новой подписки после ошибки POST, forced unsupported browser, mocked unconfigured response, смену аккаунта и reload. Отдельное настоящее удаление аккаунта через API очистило сессию и подписку собственного worker; PushManager оставался подменённым. Итоговые проверки, PR/CI и интеграция фиксируются отдельно в [журнале](../project-log/improvement-progress-2026-10-22.md).

Для HTTP suite требуется собственный `WEBPUSH_TEST_DATABASE_URL` новой локальной БД curation_test_* под NOSUPERUSER/NOBYPASSRLS. Redis/BullMQ остаётся отдельным прежним integration suite; его успех не выводится из ручного вызова process в новых PostgreSQL тестах.
