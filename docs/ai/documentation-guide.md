# Руководство по документации NaPare

## Сначала определите читателя и задачу

Перед правкой зафиксируйте, кому нужен документ и что читатель должен сделать или понять. Выберите подходящий тип:

| Тип | Задача читателя | Как строить текст |
| --- | --- | --- |
| Учебное руководство | Освоить процесс на примере | Дайте исходные условия, последовательные действия и проверяемый результат |
| Практическая инструкция | Решить конкретную задачу | Начните с цели, перечислите предпосылки, точные шаги и восстановление при сбое |
| Справочник | Найти точное значение или контракт | Организуйте по сущностям; фиксируйте параметры, ответы, ошибки и ограничения |
| Объяснение | Понять устройство или причину решения | Опишите контекст, границы, причины и связи с соседними компонентами |

Это применение [Diátaxis](https://diataxis.fr/) к нуждам читателя. Не создавайте пустые разделы и не переносите весь архив только ради новой классификации. Сохраняйте текущую структуру проекта, если она отвечает задаче.

## Достоверность и границы утверждений

- Для описания текущего поведения сверяйтесь с кодом, актуальными API-схемами, миграциями, командами пакетов, CI и Compose. Исторический документ не заменяет эти источники.
- Отделяйте реализованное поведение от планов, локальных наблюдений и состояния production. Указывайте дату для снимков состояния и помечайте устаревшие инструкции.
- В процедурах приводите исполняемые команды и конкретные ожидаемые признаки успеха. Уточняйте, что доказывает проверка: статический анализ, локальный запуск, браузер, сервер или production.
- Не включайте секреты, реальные пароли, токены, частные данные и локальные диагностические артефакты.
- Ссылайтесь на канонический документ или исходный файл вместо копирования больших фрагментов. Если копия нужна пользователю, обозначьте источник истины.

## Структура и оформление

- Начинайте с заголовка, который называет тему и область действия. В первых строках дайте назначение и ключевое ограничение.
- Используйте короткие смысловые разделы и заголовки с последовательной иерархией. Не перескакивайте уровни ради визуального оформления.
- Пишите шаги глаголами действия. Для команд указывайте рабочую папку, необходимые переменные и безопасный порядок выполнения.
- Используйте таблицу для сопоставления полей или вариантов, список — для однотипных пунктов, нумерацию — для обязательной последовательности.
- Подписывайте язык каждого блока кода. Не прячьте важные условия или предупреждения только в комментариях к коду.
- Делайте ссылки описательными и проверяйте локальные пути. Внешние ссылки оставляйте только там, где читателю действительно нужен первоисточник.
- Удаляйте дублирующие вводные, общие обещания и подробности, которые уже поддерживаются в другом месте.

## Документация для Codex

- Держите `AGENTS.md` коротким: постоянные границы, точка входа и обязательные проверки. Подробности направляйте в тематические документы.
- Используйте `AI_CONTEXT.md` как короткий маршрут к карте проекта и нужной тематике. Не загружайте все справочники в каждый запрос.
- Для исходного файла сначала найдите соответствующую source card, затем прочитайте сам файл и необходимые импорты. Карточка помогает найти код, но не заменяет первоисточник.
- Обновляйте source card и индекс только при добавлении, перемещении или удалении исходного файла; не размножайте карточки ради документации продукта.
- Предпочитайте один актуальный источник истины нескольким почти одинаковым инструкциям.

## Перед завершением

1. Сверьте каждое утверждение о поведении с первоисточником.
2. Проверьте команды, ссылки, пути, даты и обозначение статуса.
3. Запустите `pnpm lint:docs` и относящиеся к изменению проверки из `docs/ai/change-safety.md`.
4. В отчёте назовите изменённые документы и укажите, какие проверки действительно прошли.
