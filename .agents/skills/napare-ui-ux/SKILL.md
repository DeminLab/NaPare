# Проектирование интерфейсов NaPare

## Назначение и применение

Проектировать и улучшать пользовательские сценарии и композицию экранов NaPare по реальным данным, ролям и дизайн-системе. Применяйте автоматически при соответствующей задаче; загрузите только этот навык и необходимые профильные документы. Начните с `AI_CONTEXT.md` и текущего `AGENTS.md`. Все пути ниже относительно корня репозитория; команды выполняются из корня, если не указано иное.

## Источники проекта

- `docs/ui/flows.md`

- `docs/ai/project-map.md`

## Рабочий процесс

1. Опишите роль, задачу экрана, частоту использования и главное действие. Откройте текущий экран и запишите наблюдаемую проблему с screenshot/viewport.
2. Сопоставьте каждый блок и действие с фактическим API/правом; отделите новые предложения от доступного функционала.
3. Определите иерархию: заголовок, контекст, основное действие, данные, вторичные действия. Используйте читаемую русскую типографику и существующую сетку.
4. Применяйте UI/UX Pro Max для выбора паттерна, Impeccable для critique, Taste для композиции, Frontend Design для исполнения — только релевантный приём. При конфликте выбирайте задачу пользователя и токены NaPare.
5. Спроектируйте mobile, keyboard, длинные списки, loading/error/empty и ограничения прав. Анимация нужна для обратной связи, учитывает reduced motion.
6. После реализации сравните до/после в браузере на тех же данных; проверьте действия и server response, зафиксируйте непроверенные состояния.

## Правила разработки

- Не выдумывайте отзывы, клиентов, метрики, пользователей и полезность недоступных функций.
- Не меняйте бренд, маршруты, auth, доступ к данным или бизнес-правила ради композиции.
- Не загружайте одновременно все сторонние skills; выбирайте один ведущий подход под конкретную проблему.

## Типичные ошибки

- Спрятать важную таблицу ради hero/cards: приоритет у учебной задачи и читаемости.
- Назвать экран готовым по Figma или screenshot без проверки навигации и empty/error states.

## Критерии качества и проверка

- [ ] Есть цель, список реальных данных/действий и порядок визуальных приоритетов.
- [ ] Desktop/mobile, переполнение, focus и touch targets проверены на изменённых маршрутах.
- [ ] Кнопки, ссылки, retry, ограничения доступа и ошибки действительно работают; evidence содержит маршрут и viewport.
- [ ] Итог перечисляет изменённые файлы, подтверждённые результаты и пробелы. Source/static, build, browser, database, device, deployment и production evidence различаются.

## Пример NaPare

При улучшении расписания сотрудника сохраните реальные занятия, фильтры и href; уменьшите визуальный шум, проверьте длинные названия дисциплин и отсутствие занятий.

## MCP и внешние инструменты

Figma — структура и предоставленный reference; Playwright — реальный flow; Chrome DevTools — overflow, network и layout. Не передавайте в Figma/MCP реальные данные студентов; используйте синтетический контент. Используйте только реально доступный и настроенный инструмент. Если нужна авторизация или перезапуск клиента, завершите независимые локальные этапы и укажите точный blocker; не утверждайте, что подключение проверено. При спорной или меняющейся семантике используйте актуальный первичный источник и указывайте проверенную версию.
