# Архитектура NaPare

## Назначение и применение

Проектировать изменения архитектуры NaPare, границ модулей и масштабирования при межсервисных, межролевых или контрактных задачах. Применяйте автоматически при соответствующей задаче; загрузите только этот навык и необходимые профильные документы. Начните с `AI_CONTEXT.md` и текущего `AGENTS.md`. Все пути ниже относительно корня репозитория; команды выполняются из корня, если не указано иное.

## Рабочий процесс

1. Определите пользовательский сценарий, роли, владельца данных и измеримый результат. Найдите существующий модуль до предложения нового.
2. Проследите путь от одного из пяти действующих web-приложений через API-клиент к NestJS controller/service, Entity и tenant context; запишите фактические границы.
3. Сопоставьте решение с модульным монолитом, organizationId/RLS и множеством эффективных ролей пользователя. Отделите власть университета от platform owner.
4. Сравните минимум необходимый вариант и альтернативу по совместимости, миграциям, стоимости эксплуатации и отказам; ADR нужен при существенном архитектурном выборе.
5. Разделите реализацию по контрактам и непересекающимся файлам. Параллельные агенты получают конкретные пути и условия завершения; один интегратор меняет общие контракты.
6. Проверьте затронутые контракты, права и сценарий целиком; документируйте откат, оставшиеся риски и отдельно подтверждённые уровни проверки.

## Правила разработки

- apps/web и apps/max-miniapp — legacy; не расширяйте их по аналогии с активными приложениями без требования задачи.
- Не создавайте второй auth, generic backend или новый API-клиент, если существующий слой поддерживает сценарий.
- Схема, сервисные проверки и RLS совместно защищают tenant; интерфейс сам по себе не является границей доступа.

## Типичные ошибки

- Считать user.role единственным источником полномочий: просмотрите RolesGuard и активную организацию.
- Объявлять полное изучение проекта по карте: перечислите реально прочитанные модули и непроверенные границы.

## Критерии качества и проверка

- [ ] Контракт frontend/API/Entity и миграции согласован; обратная совместимость или переход описаны.
- [ ] pnpm typecheck; node scripts/verify-role-workspace-boundaries.cjs; затронутые unit/integration tests.
- [ ] Есть проверка чужой организации, отсутствующих данных и отказа зависимости; ADR содержит источник решения.
- [ ] Итог перечисляет изменённые файлы, подтверждённые результаты и пробелы. Source/static, build, browser, database, device, deployment и production evidence различаются.

## Пример NaPare

Добавление университетской функции в requests: сначала проверить academic-office и OfficeAssignment, затем предложить расширение существующих API вместо отдельного кабинета с новой моделью ролей.

## MCP и внешние инструменты

Context7 — версии NestJS/TypeORM/Next из manifest/lockfile; GitHub — читать связанные PR и CI; DBHub — только схема из отдельной синтетической БД. Инструмент не даёт разрешения на push, production или изменение данных. Используйте только реально доступный и настроенный инструмент. Если нужна авторизация или перезапуск клиента, завершите независимые локальные этапы и укажите точный blocker; не утверждайте, что подключение проверено. При спорной или меняющейся семантике используйте актуальный первичный источник и указывайте проверенную версию.
