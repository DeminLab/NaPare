# Code Review NaPare

## Назначение и применение

Проверять diff NaPare на реальные дефекты, регрессии, права, совместимость контрактов и достаточность проверок без расширения scope. Применяйте автоматически при соответствующей задаче; загрузите только этот навык и необходимые профильные документы. Начните с `AI_CONTEXT.md` и текущего `AGENTS.md`. Все пути ниже относительно корня репозитория; команды выполняются из корня, если не указано иное.

## Источники проекта

- `AI_CONTEXT.md`

- `scripts/verify-role-workspace-boundaries.cjs`

## Рабочий процесс

1. Определите base/head и полный diff, git status и цель запроса. Не перезаписывайте работу автора и не исправляйте код при review-only scope.
2. Прочитайте изменённый код и callers, соседние тесты и документ модуля. Проверяйте конкретный путь отказа, а не общий stylistic вкус.
3. Проследите API DTO/client, effective roles/organizationId, транзакции/RLS, cache lifecycle, nullable/empty/error и retry/idempotency.
4. Для UI сопоставьте route, shared tokens, action/backend, mobile и accessibility. Для migrations/infra проверьте совместимость и откат.
5. Сверьте доказательства по [циклу проверки изменений](../../../docs/ai-devkit/workflow.md#цикл-проверки-изменений). Подтвердите замечание воспроизводимым примером или цепочкой кода, оцените влияние и приоритет. Предположение без доказанного триггера обозначайте вопросом.
6. Выдайте actionable findings с файлом и узкой строкой, объяснением риска и минимальной рекомендацией; отдельно укажите реально выполненные и отсутствующие проверки.

## Правила разработки

- Не превращайте review в автоматическое переписывание и не смешивайте unrelated cleanup с дефектом.
- Не сообщайте о проблеме как о новой, если diff её не вводит/не усугубляет; baseline gaps можно отметить отдельно.
- Отсутствие findings не означает runtime/security/production certification.

## Типичные ошибки

- Флагировать совместимый fallback user.role как баг без чтения ADR-0009.
- Принять зелёный CI другого SHA или skipped integration за доказательство текущего head.

## Критерии качества и проверка

- [ ] git diff --check; соответствующие typecheck/tests при необходимости для подтверждения.
- [ ] Каждый finding содержит trigger → observed code → impact; file/line проверены на current head.
- [ ] Права, контракт и миграции рассмотрены в изменённом scope; пробелы браузера/DB отражены.
- [ ] Итог перечисляет изменённые файлы, подтверждённые результаты и пробелы. Source/static, build, browser, database, device, deployment и production evidence различаются.

## Пример NaPare

Review изменения RolesGuard требует проверить множество ролей активной организации, fallback и HTTP tests, а не только новый enum в UI.

## MCP и внешние инструменты

GitHub — diff и CI конкретного head; Context7 — спорная семантика framework; Playwright — конкретная UI регрессия на synthetic данных. Наличие инструмента review не разрешает публиковать комментарий/approve без инструкции пользователя. Используйте только реально доступный и настроенный инструмент. Если нужна авторизация или перезапуск клиента, завершите независимые локальные этапы и укажите точный blocker; не утверждайте, что подключение проверено. При спорной или меняющейся семантике используйте актуальный первичный источник и указывайте проверенную версию.
