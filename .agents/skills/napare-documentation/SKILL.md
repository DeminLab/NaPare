# Документация NaPare

## Назначение и применение

Создавать и актуализировать техническую документацию NaPare по исходникам и проверкам без дублирования источников правды и выдуманных статусов. Применяйте автоматически при соответствующей задаче; загрузите только этот навык и необходимые профильные документы. Начните с `AI_CONTEXT.md` и текущего `AGENTS.md`. Все пути ниже относительно корня репозитория; команды выполняются из корня, если не указано иное.

## Источники проекта

- `AI_CONTEXT.md`
- `docs/README.md`
- `docs/DEVELOPER_GUIDE.md`
- `docs/ai/project-map.md`
- `docs/modules/_TEMPLATE.md`
- `docs/process/definition-of-done.md`
- `docs/decisions/0004-openapi-source-of-truth.md`

## Рабочий процесс

1. Определите тип документа: module behavior, API, architecture/ADR, ops runbook, UI или датированный evidence report. Найдите действующий документ прежде создания нового.
2. Прочитайте код/конфигурацию и команды package.json, на которые ссылается текст. Планы и project-log используйте как историю, не текущую реализацию.
3. Пишите цель, источник правды, текущее поведение, роли/ошибки, проверку и открытые вопросы только там, где они нужны. Отмечайте implemented/partial/proposed/unverified.
4. Указывайте безопасные команды для ОС и placeholders вместо credentials; опасные/production действия требуют обозначенных предусловий и разрешения.
5. Обновите индекс/связанные ссылки при новом разделе; не копируйте OpenAPI вручную и не создавайте второй файл с тем же фактом.
6. Проверьте относительные ссылки, команды, markdownlint и git diff; итог сообщает реальные checks и gaps без выдуманной runtime готовности.

## Правила разработки

- docs/archive не превращайте в текущую инструкцию; dated evidence не переписывайте как универсальную гарантию.
- В worklog укажите дату, изменение, точную проверку и blocker; не записывайте secrets/PII/diagnostic dumps.
- Если документ приближается к 500 строкам, разделяйте по предмету с понятной навигацией.

## Типичные ошибки

- Упомянуть удалённый verify-ai-documentation.cjs как текущую обязательную команду.
- Обновить API guide без кода/DTO либо docs link на несуществующий module.

## Критерии качества и проверка

- [ ] pnpm lint:docs или targeted markdownlint; ссылки проверены по filesystem.
- [ ] Команды сверены с текущим package.json/config; проверенные результаты имеют дату/уровень.
- [ ] Новый файл виден из нужного индекса; отсутствуют placeholders scaffold, секреты и неподтверждённые обещания.
- [ ] Итог перечисляет изменённые файлы, подтверждённые результаты и пробелы. Source/static, build, browser, database, device, deployment и production evidence различаются.

## Пример NaPare

Новый endpoint учебного офиса описывается в docs/modules/academic-office.md со ссылкой на controller/DTO; общий API guide остаётся картой и не дублирует generated OpenAPI.

## MCP и внешние инструменты

Context7 — первичные framework API; GitHub — подтверждение exact SHA/CI; Figma — только предоставленный spec. Не выдавайте прочитанный макет/PR за реализованный runtime. Используйте только реально доступный и настроенный инструмент. Если нужна авторизация или перезапуск клиента, завершите независимые локальные этапы и укажите точный blocker; не утверждайте, что подключение проверено. При спорной или меняющейся семантике используйте актуальный первичный источник и указывайте проверенную версию.
