# Дизайн-система NaPare

## Назначение и применение

Развивать общие дизайн-токены и UI-компоненты NaPare при системных изменениях визуальных примитивов и повторяющихся паттернов. Применяйте автоматически при соответствующей задаче; загрузите только этот навык и необходимые профильные документы. Начните с `AI_CONTEXT.md` и текущего `AGENTS.md`. Все пути ниже относительно корня репозитория; команды выполняются из корня, если не указано иное.

## Источники проекта

- `packages/design-tokens/styles.css`
- `packages/design-tokens/tailwind.preset.js`
- `packages/design-tokens/src/index.ts`
- `packages/ui/src/index.tsx`
- `packages/ui/src/WorkspaceShell.tsx`
- `packages/ui/content-styles.css`
- `docs/design/role-workspace-tokens.md`
- `docs/ui/design-system.md`

## Рабочий процесс

1. Определите, является ли задача общей или локальной: новый токен оправдан повторяющейся семантикой, локальный экран не требует новой системы.
2. Прочитайте CSS variables, TS export и Tailwind preset вместе; найдите consumers через rg перед изменением имени или значения.
3. Выберите semantic token: brand, surface, text, focus, status. Сохраните НаПаре, назначение ролей, плотность и существующую типографику.
4. Измените общий компонент с совместимыми props. Предусмотрите focus-visible, disabled/loading, длинный русский текст, mobile и reduced motion.
5. Сверьте все действующие приложения, использующие primitive; не применяйте массовый редизайн к student или portal без scope.
6. Проверьте typecheck потребителей, контраст и скриншоты representative states; запишите визуальные регрессии и обновите документ токенов.

## Правила разработки

- Три представления токенов должны соответствовать одной семантике; CSS является runtime-источником переменных.
- Сторонние Taste/Impeccable/UI UX советы — инструмент оценки, приоритет имеет дизайн-система NaPare и пользовательский reference.
- Не добавляйте компонент с тем же поведением под новым именем; проверьте packages/ui и app-local компоненты.

## Типичные ошибки

- Исправить общий token ради одного экрана и сломать контраст в остальных: проверяйте consumers.
- Подменить button ссылкой или сломать доступное имя при унификации визуального стиля.

## Критерии качества и проверка

- [ ] Экспорт компонента и типов согласован; существующие consumers компилируются.
- [ ] pnpm typecheck; pnpm lint; node scripts/verify-role-workspace-boundaries.cjs.
- [ ] Desktop/mobile, keyboard, focus, contrast, loading/error/empty и длинные подписи проверены.
- [ ] Итог перечисляет изменённые файлы, подтверждённые результаты и пробелы. Source/static, build, browser, database, device, deployment и production evidence различаются.

## Пример NaPare

Новый статус в RecordQueue получает semantic success/warning/danger из packages/design-tokens; не вводите независимые hex-цвета в каждом кабинете.

## MCP и внешние инструменты

Figma — соответствие variable/component реальному токену; Playwright — потребители общего компонента; Chrome DevTools — computed variables, layout и rendering. Context7 нужен для изменяемого framework/API, не для подмены бренда. Используйте только реально доступный и настроенный инструмент. Если нужна авторизация или перезапуск клиента, завершите независимые локальные этапы и укажите точный blocker; не утверждайте, что подключение проверено. При спорной или меняющейся семантике используйте актуальный первичный источник и указывайте проверенную версию.
