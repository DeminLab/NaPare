# Проверка качества NaPare

## Назначение и применение

Планировать и выполнять проверку изменений NaPare через unit, HTTP/PostgreSQL, реальные браузеры и отдельные Android сценарии. Применяйте автоматически при соответствующей задаче; загрузите только этот навык и необходимые профильные документы. Начните с `AI_CONTEXT.md` и текущего `AGENTS.md`. Все пути ниже относительно корня репозитория; команды выполняются из корня, если не указано иное.

## Источники проекта

- `docs/ops/testing.md`

- `apps/web-student/test/offline-worker.test.cjs`
- `.github/workflows/ci.yml`

## Рабочий процесс

1. Составьте матрицу изменённого поведения: роль/tenant, route, input, output, зависимость и риск регрессии. Выберите минимально достаточный уровень проверки.
2. Прочитайте тест и fixture перед запуском: некоторые e2e пересоздают схему, браузерные scripts имеют собственные предусловия. Используйте только изолированные synthetic data.
3. Примените [цикл проверки изменений](../../../docs/ai-devkit/workflow.md#цикл-проверки-изменений) к затронутому слою. Для API добавьте HTTP с позитивным и негативным контролем на изолированных данных.
4. Для UI проверьте действия через реальный браузер, console/network, mobile/desktop, reload, loading/error/empty, keyboard и отзыв прав.
5. Для производительности измерьте baseline и после на одинаковом окружении; для Android выделите JVM/build/device отдельно.
6. Зафиксируйте точные команды, окружение, assertions, skips и ошибки. Исправьте вызванные изменением проблемы и повторите соответствующие проверки; не повторяйте неизменные проверки без причины.

## Правила разработки

- Fixture/mocked HTTP доказывает только проверенный слой; не называйте его подтверждением production.
- Отсутствие env или DB приводит к skip, а не к прохождению интеграции.
- Не стартуйте destructive reset скрипты и не используйте реальные аккаунты/сессию пользователя без нужного scope.

## Типичные ошибки

- Проверить лишь HTTP 200: нужны содержание, права и сохранённый результат после reload.
- Объявить все маршруты проверенными по одному screenshot; сохраняйте route-specific evidence.

## Критерии качества и проверка

- [ ] pnpm test:unit; pnpm typecheck; pnpm lint — по существенному scope.
- [ ] node scripts/verify-role-workspace-boundaries.cjs; git diff --check.
- [ ] pnpm test:e2e — при доступной отдельной БД; Playwright evidence для изменённых routes; gaps явно перечислены.
- [ ] Итог перечисляет изменённые файлы, подтверждённые результаты и пробелы. Source/static, build, browser, database, device, deployment и production evidence различаются.

## Пример NaPare

Для новой кнопки в расписании: проверить allowed role → запрос → DB результат → reload; чужой tenant → отказ/неизменность; сеть недоступна → понятная ошибка и retry.

## MCP и внешние инструменты

Playwright — воспроизводимые браузерные действия и screenshots; Chrome DevTools — console/network/performance; DBHub — read-only проверка результата тестовой БД; GitHub — CI статусы именно проверяемого SHA. Используйте только реально доступный и настроенный инструмент. Если нужна авторизация или перезапуск клиента, завершите независимые локальные этапы и укажите точный blocker; не утверждайте, что подключение проверено. При спорной или меняющейся семантике используйте актуальный первичный источник и указывайте проверенную версию.
