# Безопасность NaPare

## Назначение и применение

Проводить запрошенный аудит безопасности NaPare и защищать авторизацию, tenant isolation, персональные данные и внешние интеграции. Применяйте автоматически при соответствующей задаче; загрузите только этот навык и необходимые профильные документы. Начните с `AI_CONTEXT.md` и текущего `AGENTS.md`. Все пути ниже относительно корня репозитория; команды выполняются из корня, если не указано иное.

## Рабочий процесс

При проверке доступа или секретов в Codex MCP начните со [статической проверки зависимостей MCP](../../../docs/ai-devkit/mcp.md#статическая-проверка-зависимостей-mcp). Отдельно оцените разрешённые данные, права и доступ к credentials. Фиксируйте путь, поле и риск без значения секрета.

1. Зафиксируйте область и угрозу: субъект, данные, точка входа, доверенная граница и возможное действие атакующего. Для обычной правки проверяйте затронутую границу без расширения в полный аудит.
2. Проследите JWT/session, effective roles, organizationId, service ownership и RLS. Проверяйте существование объекта и все связанные identifiers.
3. Изучите payload validation, upload/URL handling, ограничение частоты, секреты и логи; не запускайте эксплуатацию против production.
4. Воспроизведите проблему безопасным regression test или синтетическим HTTP на отдельном окружении. Фиксируйте позитивный контроль и негативный запрос другого tenant.
5. Сделайте минимальное исправление, проверьте обход альтернативным route, bulk operation и прямым repository query.
6. Отчёт содержит severity, путь/строку, воспроизводимость, влияние, исправление и остаточный риск; юридическое соответствие не выводится из инженерных тестов.

## Правила разработки

- Не отправляйте токены, auth bodies, .env, дампы или студенческие документы во внешние MCP и вывод.
- Удаление аккаунта согласуйте с текущими privacy contracts: деактивация, архив и стирание отличаются.
- Для DB tests используйте разрешённые fixture-базы; никаких боевых payloads, массовой чистки или credential rotation без scope.

## Типичные ошибки

- Считать RolesGuard достаточным tenant-filter либо считать RLS работающей без проверки runtime DB role.
- Считать запрет UI доказательством запрета HTTP; тестируйте endpoint и неизменность бизнес-данных.

## Критерии качества и проверка

- [ ] Затронутые security/unit specs, pnpm typecheck, pnpm lint; node scripts/security-route-inventory.cjs --check.
- [ ] Cross-tenant A/B контроль, revoked role/session и отсутствие утечки через ошибки/списки.
- [ ] git diff --check; секреты и персональные данные отсутствуют в diff и evidence.
- [ ] Итог перечисляет изменённые файлы, подтверждённые результаты и пробелы. Source/static, build, browser, database, device, deployment и production evidence различаются.

## Пример NaPare

Для доступа к чужому PairSpace проверьте HTTP отказ и неизменность вложений/сообщений в синтетической PostgreSQL; глобальные telemetry writes учитывайте отдельно.

## MCP и внешние инструменты

GitHub — read-only advisories/CI для затронутой зависимости; Context7 — официальная защита конкретной версии; DBHub — только тестовая БД с минимальными правами; Sentry — обезличенные traces. Отсутствующий доступ фиксируется, не обходится. Используйте только реально доступный и настроенный инструмент. Если нужна авторизация или перезапуск клиента, завершите независимые локальные этапы и укажите точный blocker; не утверждайте, что подключение проверено. При спорной или меняющейся семантике используйте актуальный первичный источник и указывайте проверенную версию.
