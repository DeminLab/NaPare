# Frontend NaPare

## Назначение и применение

Разрабатывать страницы и клиентскую логику действующих Next.js приложений NaPare с сохранением маршрутов, авторизации и контрактов API. Применяйте автоматически при соответствующей задаче; загрузите только этот навык и необходимые профильные документы. Начните с `AI_CONTEXT.md` и текущего `AGENTS.md`. Все пути ниже относительно корня репозитория; команды выполняются из корня, если не указано иное.

## Источники проекта

- `apps/web-portal/src/app`
- `apps/web-student/src/lib/api.ts`
- `apps/web-staff/src/lib/api.ts`
- `apps/web-admin/src/lib/api.ts`
- `apps/web-developer/src/lib/api.ts`
- `packages/api-client/src/client.ts`
- `packages/ui/src/WorkspaceShell.tsx`
- `packages/ui/src/useWorkspaceQuery.ts`
- `docs/ui/ui-states.md`

## Рабочий процесс

1. Выберите приложение по роли и существующему маршруту. Прочитайте ближайший layout, api.ts, component и связанный controller; определите SSR/client границу.
2. Уточните реальные DTO, статусы и ошибки. Используйте существующий клиент и lifecycle токенов; перенесите тип в shared package лишь при действительном совместном использовании.
3. Соберите UI из существующих компонентов и токенов. Для WorkspaceShell проверьте href, activePaths, mobileHrefs, права и команды поиска.
4. Реализуйте loading/empty/error/success, отмену устаревших запросов и защиту от повторной отправки. Состояние ошибки не должно заменяться выдуманным успехом.
5. Проверьте обновление сессии, выход и очистку account cache, особенно student offline schedule. Проверьте отсутствие данных предыдущего пользователя.
6. Запустите typecheck затронутого приложения и lint, затем браузерный сценарий с реальным API, desktop/mobile и keyboard. Отчёт указывает, где использовался fixture.

## Правила разработки

- Сохраняйте basePath и действующие login redirects; изменение URL должно учитывать Nginx и другие клиенты.
- Не добавляйте работающую на вид кнопку без backend-сценария; недоступное действие оформите явно и объяснимо.
- Не обращайтесь к localStorage/window при серверном рендеринге; не публикуйте секреты через NEXT_PUBLIC_*.

## Типичные ошибки

- Копировать api.ts в новую абстракцию без изучения refresh: это меняет поведение входа.
- Показывать бесконечный skeleton после 403/500 или падения JSON: проверяйте отдельный error state и retry.

## Критерии качества и проверка

- [ ] pnpm --filter @napare/web-student exec tsc --noEmit (замените пакет выбранным); pnpm lint.
- [ ] node scripts/verify-role-workspace-boundaries.cjs; браузерные ошибки и переполнение проверены.
- [ ] Переход, submit, reload, revoked role, empty/error и чужая организация проверены по затронутому сценарию.
- [ ] Итог перечисляет изменённые файлы, подтверждённые результаты и пробелы. Source/static, build, browser, database, device, deployment и production evidence различаются.

## Пример NaPare

Для поиска в кабинете сотрудника изучите WorkspaceShell.onSearch и useWorkspaceQuery; подключите фактический поиск API и отмену запроса, сохранив существующие href.

## MCP и внешние инструменты

Figma — макет только по предоставленному файлу и правам; Context7 — App Router для установленной версии; Playwright — сценарий и viewport; Chrome DevTools — ошибки, network, performance. Скриншот без успешного запроса не подтверждает API. Используйте только реально доступный и настроенный инструмент. Если нужна авторизация или перезапуск клиента, завершите независимые локальные этапы и укажите точный blocker; не утверждайте, что подключение проверено. При спорной или меняющейся семантике используйте актуальный первичный источник и указывайте проверенную версию.
